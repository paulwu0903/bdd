# Rule 1 - 答案依類型路由到既有區塊 [MUST]
- 每個拍板結果依下表寫入 spec.md 既有區塊；新增條目接續該區塊的既有編號與格式，不重排既有條目。回寫模式由呼叫者傳入的修訂，依同一張表路由。
- 一個答案可同時落到多個區塊（例如新 FR 加上對應的 Acceptance Scenario），但每個區塊只寫一次。

| 答案類型 | 落點 |
|---|---|
| 功能歧義 | 所屬 User Story 的 Functional Requirements；跨兩個以上 User Story 則放 Global Requirements |
| 角色 / 互動方式 | 該 User Story 的敘述或 Acceptance Scenarios |
| 資料形狀、實體、關係 | Key Entities |
| 非功能品質 | 該 User Story 或 Global 的 NFR，並在 Success Criteria 補可量化指標（形容詞轉成數字或明確目標） |
| 邊界、負面流程 | Edge Cases，敘述 MUST 時指回承載它的 FR / NFR |
| 術語衝突 | 全文改為正規用語；只在第一次出現處標一次 `(formerly referred to as "X")` |
| 修改或刪除現行需求（其他 plan 的 `NNN/FR-nnn` 等） | `## 既有需求異動` 的新列或改寫既有列（見 Rule 7）；不在本 spec 另寫 FR / NFR / SC |

## Good Example
- 「重疊假期不得重複申請」是功能歧義，落到 US1 的 FR 並補 Acceptance Scenario；其資料含意再落到 Key Entities。

```
US1 Functional Requirements：
- **FR-007**: 系統 MUST 拒絕與同一員工既有未撤回申請日期重疊的新申請。
US1 Acceptance Scenarios：
4. **Given** 員工已有 5/1–5/3 的待審申請，**When** 再送出 5/3–5/4，**Then** 系統顯示重疊提示且不建立新申請。
Key Entities：
- **LeaveRequest**: …；同一員工的有效申請日期區間彼此不重疊。
```

## Bad Example
- 答案被寫成 Assumptions 底下的一段敘述，FR 與驗收情境都沒有更新，下游讀 FR 時看不到這個決策。

```
Assumptions：
- **重疊假期不得重複申請**（使用者於 2026-10-28 釐清選擇 1）：系統要拒絕重疊申請並顯示提示。
（FR、Acceptance Scenarios、Key Entities 均未改動）
```

# Rule 2 - 回寫內容最小且可測 [SHOULD]
- 每條新增或改寫的敘述只寫答案本身帶來的約束，長度以一句可驗收的陳述為度。
- 不把訪談中的背景、理由、替代方案寫進 FR / NFR / Edge Cases；理由只留在 Assumptions 的說明。

## Good Example
- 一句話、可直接寫成測試。

```
- **FR-007**: 系統 MUST 拒絕與同一員工既有未撤回申請日期重疊的新申請。
```

## Bad Example
- 把訪談理由與替代方案塞進 FR，測試人員要先讀完一段才找到要驗什麼。

```
- **FR-007**: 因為使用者認為重複申請會造成 HR 核對困難，且之前討論過允許重疊再由主管退回的做法但覺得太麻煩，所以系統要拒絕重疊申請。
```

# Rule 3 - Assumptions 留痕格式與 taxonomy [MUST]
- 每題拍板結果在 `## Assumptions` 恰有一條，格式沿用 specify：`- **<決策摘要>**（使用者於 YYYY-MM-DD 釐清選擇 X）：<說明>`，X 為選項編號或使用者的短答。
- 說明結尾以括號附該題的 taxonomy 類別：`（Taxonomy：<類別>）`。
- 回寫模式的每項修訂同樣恰有一條，決策來源寫 `使用者於 YYYY-MM-DD 修訂`（日期為使用者拍板日），說明結尾改附呼叫者傳入的出處：`（出處：<呼叫者> <出處>）`。

## Good Example
- 決策來源寫法與 specify 一致，結尾帶 taxonomy。

```
- **重疊假期不得重複申請**（使用者於 2026-10-28 釐清選擇 1）：同一員工日期區間重疊的申請在送出時即被拒絕，不交由主管退回（Taxonomy：Domain & Data Model）。
- **訊息上限改為 300 字**（使用者於 2026-11-12 修訂）：驗收澄清時改定 300 字（出處：/spec-by-example 訊息內容與發言頻率.feature 澄清標籤）。
```

## Bad Example
- 沒有日期、看不出是使用者決定或推定，也沒有 taxonomy。

```
- **重疊假期不得重複申請**（已確認）：送出時拒絕。
```

# Rule 4 - 拍板既有推定或既有異動列時就地改寫、不並列 [MUST]
- 答案涉及某條「AI 推定」的 Assumption 時，無論使用者是確認原推定或推翻它，都直接把該條改寫成「使用者於 YYYY-MM-DD 釐清選擇 X」並附 Taxonomy，不另加一條，也不保留「AI 推定」字樣。
- 推翻時另替換 FR / NFR / Edge Cases 的既有敘述；不得同時保留新舊兩個版本或留下「原本為 …」的註記。
- 答案改變 `## 既有需求異動` 中已有的列（同一個既有編號）時，就地改寫該列的動作、新內容與確認欄，不另加一列；該列對應的 Assumption 同樣就地改寫。

## Good Example
- 確認：原推定「7 天」被使用者採納，同一條只換決策來源；推翻：原推定「允許重疊」改為使用者決策，FR 原句也直接替換。

```
確認
Before：- **逾期 7 天提醒**（AI 推定）：…
After： - **逾期 7 天提醒**（使用者於 2026-10-28 釐清選擇 1）：…（Taxonomy：Edge Cases & Failure Handling）。

推翻
Before：- **允許重疊申請、由主管退回**（AI 推定）：…
After： - **重疊假期不得重複申請**（使用者於 2026-10-28 釐清選擇 1）：…（Taxonomy：Domain & Data Model）。
Before：- **FR-007**: 系統 MAY 接受日期重疊的申請並交由主管判斷。
After： - **FR-007**: 系統 MUST 拒絕與同一員工既有未撤回申請日期重疊的新申請。

既有異動列
Before：| 1 | MODIFY | `002/FR-002` | … MUST 為 1 至 500 字元 … | 使用者要求放寬訊息長度 | 使用者於 2026-11-10 確認 |
After： | 1 | MODIFY | `002/FR-002` | … MUST 為 1 至 300 字元 … | 使用者要求放寬訊息長度 | 使用者於 2026-11-12 確認 |
```

## Bad Example
- 新舊兩條 Assumption 並列，FR 也留下矛盾的兩句；同一個既有編號在既有需求異動中出現兩列。

```
- **允許重疊申請、由主管退回**（AI 推定）：…
- **重疊假期不得重複申請**（使用者於 2026-10-28 釐清選擇 1）：…
- **FR-007**: 系統 MAY 接受日期重疊的申請並交由主管判斷。
- **FR-007a**: 系統 MUST 拒絕重疊申請。
| 1 | MODIFY | `002/FR-002` | … 1 至 500 字元 … | … | 使用者於 2026-11-10 確認 |
| 2 | MODIFY | `002/FR-002` | … 1 至 300 字元 … | … | 使用者於 2026-11-12 確認 |
```

# Rule 5 - 只新增模板內的選用標題 `## 既有需求異動` [MUST]
- 回寫只能改動既有標題底下的內容；不得新增 `## Clarifications`、`### Session …` 或任何不在 specify 模板內的標題，spec_lint 會判違規。
- 唯一例外：答案要寫入既有需求異動、而 spec.md 沒有 `## 既有需求異動` 時，依 specify 模板的位置（`## Success Criteria` 之後、`## Assumptions` 之前）新增該標題與表頭。

## Good Example
- 全部改動落在既有的 FR、Acceptance Scenarios、Key Entities、Assumptions 之下，只因答案修改了 002/FR-006 而在模板位置新增既有需求異動。

```
$ diff <(grep '^#' spec.before.md) <(grep '^#' spec.after.md)
> ## 既有需求異動
（位於 ## Success Criteria 與 ## Assumptions 之間）
```

## Bad Example
- 仿照 spec-kit 新增 Clarifications 區塊，spec_lint 回報標題不在模板內。

```
## Clarifications
### Session 2026-10-28
- Q: 重疊假期是否允許？ → A: 不允許
→ spec_lint: heading '## Clarifications' is not in the template or is out of order
```

# Rule 6 - 寫後自檢 [MUST]
- 每輪寫完存檔前逐項確認：每題在 Assumptions 恰一條留痕、無重複；該答案本應消除的模糊字眼（「快速」「適當」「視情況」）已不存在於改動區塊；沒有與新答案矛盾的舊敘述；本次 FR / NFR / SC 與既有需求異動沒有對同一件事的兩種說法；同一正規用語貫穿所有改動區塊。
- 任一項不符即修正後再存檔，不留到下一輪。

## Good Example
- 四項逐一打勾後才存檔。

```
[x] Assumptions 新增 1 條，無重複
[x] FR-004 的「快速回應」已改為「2 秒內」
[x] 無其他條目仍寫「允許重疊」
[x] 既有需求異動 #2 改了 002/FR-006，本次 FR 沒有另寫結果畫面的表情規則
[x] 全文統一用「審核人」，無「主管 / 審核者」混用
```

## Bad Example
- Success Criteria 已改為「2 秒內」，FR-004 仍寫「快速回應」，兩處不一致卻直接存檔。

```
- **FR-004**: 系統 MUST 快速回應使用者操作。
- **SC-002**: 90% 的操作在 2 秒內完成回應。
```

# Rule 7 - 改變現行需求結果的答案寫成既有需求異動列 [MUST]
- 答案讓其他 plan 的現行需求（`NNN/FR-nnn`、`NNN/NFR-nnn`、`NNN/SC-nnn`）結果改變時寫成 MODIFY，使其整條不再成立時寫成 DELETE；只改本 plan 自己的 FR / NFR / SC 時直接改寫該條目，不列異動。
- 欄位依 specify 模板：既有編號帶原 plan 前綴並沿用原編號；MODIFY 的新內容寫修改後的完整可測條文，不寫差異描述，DELETE 寫 `—`；理由寫答案帶來的變更原因；確認欄寫 `使用者於 YYYY-MM-DD 確認`。
- 新列接續表中最大的 # 加一，不重排既有列。

## Good Example
- 使用者選「結果畫面也可按表情」，修改的是 002 的需求，寫成新的異動列，新內容是完整條文。

```
| 2 | MODIFY | `002/FR-006` | 對局結束時，結果畫面 MUST 顯示本局完整聊天紀錄，MUST NOT 提供文字輸入，並 MUST 允許雙方對既有訊息按 👍、❤️、😂。 | 使用者要求結果畫面也能按表情回應 | 使用者於 2026-11-12 確認 |
```

## Bad Example
- 改寫 002 的需求卻寫成本 spec 的新 FR，truth 中 002/FR-006 仍寫「MUST NOT 提供聊天輸入」，兩條有效需求互相矛盾；另一列只寫差異、編號改成本 plan 的。

```
- **FR-005**: 結果畫面 MUST 允許對既有訊息按表情。
| 2 | MODIFY | `003/FR-006` | 結果畫面也可以按表情 | 使用者要求 | 使用者於 2026-11-12 確認 |
```
