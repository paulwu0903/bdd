# Rule 1 - 摘要寫出業務或契約上的意義 [MUST]
- 摘要說明這個異動讓系統「能做、不能做或怎麼做」有什麼不同，讀者不必打開 truth 就能理解。
- 不重述部位欄已有的檔名、operationId 或欄位名，也不只寫「新增」「修改」。

## Good Example
- 說出異動帶來的行為。

```
| ADD | `openapi.yaml › operationId applyGift` | 結帳時依訂單金額自動加贈符合門檻的贈品 | 004/FR-001 |
```

## Bad Example
- 只重述部位與動作，讀者看不出系統多了什麼能力。

```
| ADD | `openapi.yaml › operationId applyGift` | 新增 applyGift operation | 004/FR-001 |
```

# Rule 2 - MODIFY 寫出改前與改後 [MUST]
- MODIFY 的摘要以「改前 → 改後」寫出被改變的部分，只寫有變的地方。

## Good Example
- 一眼看出門檻從多少變成多少。

```
| MODIFY | `004/FR-003` | 滿額門檻 1,000 元 → 1,500 元 | spec.md 既有需求異動 #1 |
```

## Bad Example
- 只寫「調整門檻」，下游不知道新的值是多少，也無法判斷要改哪些測試。

```
| MODIFY | `004/FR-003` | 調整滿額門檻 | spec.md 既有需求異動 #1 |
```

# Rule 3 - DELETE 寫出移除後不再成立的行為 [MUST]
- DELETE 的摘要寫出移除後，系統不再提供或不再保證的行為，讓下游知道要清理哪些實作與測試。

## Good Example
- 指出哪個能力消失。

```
| DELETE | `openapi.yaml › operationId cancelGift` | 會員不再能在結帳後自行取消贈品 | clarify 2026-11-06：移除取消贈品 |
```

## Bad Example
- 只寫「刪除」，看不出失去的是什麼。

```
| DELETE | `openapi.yaml › operationId cancelGift` | 刪除 | clarify 2026-11-06：移除取消贈品 |
```

# Rule 4 - 一列一句，不寫實作細節 [SHOULD]
- 每列摘要一句話，不寫行號、程式碼片段、SQL 或檔案內部的結構描述；細節由 truth 本身表達。

## Good Example
- 一句話說完。

```
| ADD | `schema.dbml › Table gift_grants.granted_at` | 記錄贈品發放的時間，供客服查詢 | 004/FR-005 |
```

## Bad Example
- 把 DDL 與行號寫進摘要。

```
| ADD | `schema.dbml › Table gift_grants.granted_at` | 第 88 行加入 granted_at datetime(3) NOT NULL，ALTER TABLE gift_grants ADD ... | 004/FR-005 |
```
