# Rule 1 - 只收錄跨不出本次範圍的定義衝突 [MUST]
- 待和解只收錄：truth 內彼此矛盾的定義，或 truth 與實作不一致之處，且本次 plan 不在範圍內解決。
- 一般待辦、改進建議、效能優化與技術債不收錄。

## Good Example
- 同一句型在兩個表中語意不同，是 truth 內的定義衝突。

```
| 1 | `backend/平臺共用/dsl.md › When › 經過 {秒數} 秒` | When 版每秒觸發定期活動，Given 版只執行一次斷線掃描，語意不同 | /dsl-refine | 待處理 | |
```

## Bad Example
- 「之後可以加快查詢」是改進建議，不是定義衝突。

```
| 2 | `schema.dbml › Table gift_grants` | 之後可以加索引加快查詢 | /data-plan | 待處理 | |
```

# Rule 2 - 每項寫明部位、衝突內容與建議 owner [MUST]
- 部位使用與異動段落相同的寫法；衝突內容寫出兩邊各自的說法；建議 owner 寫負責該部位的 truth owner skill。

## Good Example
- 讀者知道衝突在哪、兩邊怎麼說、該由誰處理。

```
| 3 | `frontend/平臺共用/dsl.md › 附錄` | 附錄寫以 Docker Compose 啟動 MySQL，實作使用 testcontainers | /dsl-refine | 待處理 | |
```

## Bad Example
- 沒有部位，衝突內容只寫「有問題」，也沒有建議 owner。

```
| 3 | 附錄 | 有問題 |  | 待處理 | |
```

# Rule 3 - 狀態只有待處理、已處理、延後 [MUST]
- 新增的項目為「待處理」。
- 本次已解決的項目改為「已處理」，處理紀錄寫明處理的 plan 與對應的異動列部位。
- 決定交給之後的 plan 處理的項目改為「延後」，處理紀錄寫明理由；開新 plan 時會自動接續，並重新標為待處理。

## Good Example
- 已處理指向對應的異動列；延後寫明理由。

```
| 1 | `backend/平臺共用/dsl.md › When › 經過 {秒數} 秒` | … | /dsl-refine | 已處理 | 004：MODIFY backend/平臺共用/dsl.md › Given › 經過 {秒數} 秒 |
| 3 | `frontend/平臺共用/dsl.md › 附錄` | … | /dsl-refine | 延後 | 等前端測試環境改版時一併修正 |
```

## Bad Example
- 狀態自創「處理中」；延後沒有理由。

```
| 1 | `backend/平臺共用/dsl.md › When › 經過 {秒數} 秒` | … | /dsl-refine | 處理中 | |
| 3 | `frontend/平臺共用/dsl.md › 附錄` | … | /dsl-refine | 延後 | |
```
