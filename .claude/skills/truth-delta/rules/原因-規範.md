# Rule 1 - 原因指回上游依據 [MUST]
- 原因只能使用下表的寫法之一，讓下游可以順著原因找回依據：

| 依據 | 寫法 |
|---|---|
| spec 的既有需求異動 | `spec.md 既有需求異動 #n` |
| spec 的區塊（新增需求的出處） | `spec.md <區塊名稱>`，例如 `spec.md 使用者故事 1`、`spec.md Global Requirements` |
| 需求條目 | `NNN/FR-nnn`、`NNN/NFR-nnn`、`NNN/SC-nnn` |
| 技術決策 | `research NNN/Rn` |
| 驗收檢查點 | `acceptance @ac:NNN/<主題>:J-C` |
| 系統介面 | `plan.md 系統介面盤點 › <介面名稱>` |
| 使用者拍板 | `clarify YYYY-MM-DD：<拍板摘要>` |
| 連帶影響 | `連帶：<觸發部位>`（見 Rule 2） |

- 「配合需求」「重構」「優化」「依規格」這類籠統語句不算原因。

## Good Example
- 每列都能直接找回依據。

```
| ADD | `openapi.yaml › operationId applyGift` | 結帳時自動加贈贈品 | 004/FR-001 |
| ADD | `Dev Dependencies / decimal.js` | 以十進位計算門檻金額，避免浮點誤差 | research 004/R3 |
```

## Bad Example
- 原因籠統，下游無法判斷這個異動是否必要。

```
| ADD | `Dev Dependencies / decimal.js` | 以十進位計算門檻金額 | 配合需求 |
```

# Rule 2 - 連帶影響要指向已記錄的觸發列 [MUST]
- 因為其他異動而必須跟著改的項目，原因寫「連帶：<觸發部位>」。
- 觸發部位必須是本份 truth-delta 任一段落中已經記錄的列的部位，讓讀者能順著連帶鏈找回最初的依據。

## Good Example
- 欄位刪除是因為 operation 被刪除，而該 operation 已記錄在 contracts 段。

```
contracts 段：| DELETE | `openapi.yaml › operationId cancelGift` | … | clarify 2026-11-06：移除取消贈品 |
data 段：    | DELETE | `schema.dbml › Table order_gifts.cancelled_at` | 不再記錄贈品取消時間 | 連帶：openapi.yaml › operationId cancelGift |
```

## Bad Example
- 「連帶」指向一個沒有記錄在任何段落的部位，連帶鏈斷掉。

```
| DELETE | `schema.dbml › Table order_gifts.cancelled_at` | 不再記錄贈品取消時間 | 連帶：取消功能 |
```

# Rule 3 - 高影響列的原因必須追得到使用者確認 [MUST]
- 依影響判定規範判為高影響的 MODIFY、DELETE，原因必須是下列之一：
  - `spec.md 既有需求異動 #n`
  - `clarify YYYY-MM-DD：…`
  - `連帶：<觸發部位>`，且觸發列本身的原因是前兩者之一（使用者已確認的變更所必然帶出的連帶修改）
- 不得只寫需求編號或 research；這樣交付時一眼就能確認每一筆高影響變更都經過使用者同意。

## Good Example
- 刪除 operation 以 clarify 拍板為原因。

```
| DELETE | `openapi.yaml › operationId cancelGift` | 會員不再能自行取消贈品 | clarify 2026-11-06：移除取消贈品 |
```

## Bad Example
- 高影響的刪除只以需求編號為原因，看不出使用者是否同意過刪除既有能力。

```
| DELETE | `openapi.yaml › operationId cancelGift` | 會員不再能自行取消贈品 | 004/FR-003 |
```

# Rule 4 - 找不到依據的異動交回呼叫者 [MUST]
- 依據檔與 clarify 拍板結果中都找不到依據的異動，列為「超出宣告範圍」交回呼叫者，由呼叫者向使用者確認；不自行替它編寫原因，也不寫入表格。
- 使用者確認納入後，以 clarify 拍板為原因寫入；確認不納入時，由呼叫者還原該異動。

## Good Example
- api-plan 發現某個 operation 已經沒有任何介面引用，想順手刪除，但本次 spec 沒有宣告，交回確認。

```
超出宣告範圍：DELETE openapi.yaml › operationId listLegacyCoupons（無任何介面引用；本次 spec 未宣告）
```

## Bad Example
- 自行替未宣告的刪除編一個原因寫進表格。

```
| DELETE | `openapi.yaml › operationId listLegacyCoupons` | 移除舊優惠券查詢 | 004/FR-001 |
```

# Rule 5 - 多個依據以頓號並列 [SHOULD]
- 一列有多個依據時，以頓號並列，不寫成段落式說明。

## Good Example
- 兩個依據並列。

```
| ADD | `openapi.yaml › operationId applyGift` | 結帳時自動加贈贈品 | 004/FR-001、research 004/R2 |
```

## Bad Example
- 以段落說明代替依據。

```
| ADD | `openapi.yaml › operationId applyGift` | 結帳時自動加贈贈品 | 因為 004 需求要求結帳自動加贈，而且 research 決定在結帳時計算，所以新增 |
```
