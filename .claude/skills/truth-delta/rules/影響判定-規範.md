# Rule 1 - 改變或移除既有可觀察行為或契約者為高影響 [MUST]
- 下列變更判為高影響，修改前必須先交給 clarify 由使用者拍板：
  - 任何 DELETE：需求、套件、operation、資料表或欄位、Example、dsl 句型。
  - 改變請求或回應形狀（欄位新增為必填、移除、改名、改型別）的 MODIFY。
  - 改變錯誤碼、HTTP 狀態或錯誤發生條件的 MODIFY。
  - 改變資料意義（欄位語意、單位、預設值、約束）的 MODIFY。
  - 改變 Example 的 Then 結果，或改變需求語意（門檻、數量、允許與禁止的對象）的 MODIFY。
  - 套件主版本升級或降級的 MODIFY。
- 判準：使用者、前端、其他服務或既有測試會因這個變更而看到不同結果。

## Good Example
- 刪除 operation 與改變滿額門檻都會讓既有使用者看到不同結果，判為高影響。

```
DELETE openapi.yaml › operationId cancelGift          → 高影響（DELETE）
MODIFY 004/FR-003 滿額門檻 1,000 元 → 1,500 元         → 高影響（需求語意）
MODIFY schemas.GiftRule.minAmount 由選填改為必填      → 高影響（請求形狀）
```

## Bad Example
- 錯誤碼與套件主版本的改變被當成「只是小改」，沒有先問就直接改。

```
MODIFY 錯誤碼 GIFT_OUT_OF_STOCK → GIFT_UNAVAILABLE   → 判為低風險（錯）
MODIFY Dev Dependencies / vitest 4.x → 5.x           → 判為低風險（錯）
```

# Rule 2 - 不改變可觀察結果者為低風險 [MUST]
- 下列 MODIFY 判為低風險，可以直接修改：
  - 說明文字、註解或補註的增修，且不改變其描述的規則。
  - 新增選填欄位，且不改變既有欄位。
  - 在既有 Rule 下補一個 Example，且不改變既有 Example 的 Then。
  - 同語意的改寫（換句話說、修正錯字）。
  - dsl 句型從一個模組的 dsl.md 移到另一個模組，句型與語意不變。
  - 套件次版本或修補版本的升級。
- 判準：改完後，所有既有的請求、回應、資料與測試結果都不變。

## Good Example
- 補說明與搬移句型不改變任何既有結果，判為低風險。

```
MODIFY schemas.GiftRule 的 description 補上「贈品依加入購物車順序發放」 → 低風險
MODIFY backend/贈品/dsl.md › Given › {會員} 已加入購物車 搬到 平臺共用/dsl.md → 低風險
```

## Bad Example
- 「只是改說明文字」，但新的說明改變了規則（由「先到先得」改為「依金額排序」），應為高影響。

```
MODIFY schemas.GiftRule 的 description「先到先得」→「依訂單金額高低發放」 → 判為低風險（錯）
```

# Rule 3 - 已在既有需求異動中確認的項目不重問 [MUST]
- 變更內容完全落在 spec.md「既有需求異動」中某一條使用者已確認的範圍內時，標為「已確認」，不再交給 clarify。
- 變更超出該條的內容（例如該條只改門檻，owner 卻連錯誤碼也改），超出的部分仍依 Rule 1、Rule 2 判定。

## Good Example
- 既有需求異動 #1 已確認把門檻改為 1,500 元，契約中對應的範例值隨之修改，落在範圍內，標為已確認。

```
spec.md 既有需求異動 #1：MODIFY 004/FR-003 滿額門檻 1,000 → 1,500 元（使用者已確認）
MODIFY openapi.yaml › components.schemas.GiftRule（minAmount 範例值 1500） → 已確認
```

## Bad Example
- 異動 #1 只確認門檻，owner 順手把未達門檻的錯誤碼也改了，卻一併標為已確認。

```
spec.md 既有需求異動 #1：MODIFY 004/FR-003 滿額門檻 1,000 → 1,500 元
MODIFY openapi.yaml › operationId applyGift 錯誤碼 BELOW_THRESHOLD → AMOUNT_TOO_LOW → 已確認（錯，超出 #1，應依 Rule 1 判為高影響）
```
