# Rule 1 - 任務句型以動作開頭、以路徑收尾 [MUST]
- 任務描述以動作開頭（建立、實作、撰寫、整理、加入、執行等），接做的內容，以「於 `路徑`」收尾。
- 多個檔案以「、」分隔，每個路徑各自用反引號包住。
- 沒有產出檔的執行類任務（例如 `驗證` 任務）不加「於 `路徑`」。

## Good Example
- 環境任務動作在前、內容在中、以「於 `路徑`」收尾；green 任務的路徑各自反引號並以「、」分隔。

```
- [ ] T001 [P] `環境` 在後端 feature 執行設定加入本功能的後端 feature 路徑於 `backend/cucumber.mjs`
- [ ] T031 [US2] `/bdd green` 實作 `specs/truth/features/backend/聊天訊息/靜音.feature` 的行為於 `backend/src/routes/chat.ts`、`backend/src/services/mute-service.ts`
```

## Bad Example
- 沒有動作、路徑放在句首且多個路徑擠在同一組反引號裡。

```
- [ ] T001 [P] `環境` `backend/cucumber.mjs, frontend/playwright.config.ts` 的 feature 路徑
```

# Rule 2 - 路徑以 plan.md 的 Source Code 樹與 truth 結構為準 [MUST]
- 程式路徑取自 plan.md 的 Source Code 樹；MODIFY、DELETE 的既有檔另取自 `list_changes.py` 的靜態影響清單；不採用 research.md 或其他文件裡的路徑寫法。
- plan.md 未列的檔案仍可列任務，路徑放在 plan.md 樹中對應的目錄下。
- feature 檔一律從 repository root 寫成 `specs/truth/features/<端點>/<模組>/<檔>.feature`，Example 層級的範疇在後面加 `:<行>`。

## Good Example
- feature 檔用 truth 路徑，realign 的 fixture 取自靜態影響清單。

```
- [ ] T010 `/bdd realign` 對齊 `specs/truth/features/backend/聊天訊息/發言頻率.feature:13` 的測試碼於 `backend/tests/bdd/modules/聊天訊息/前置.ts`、`backend/tests/bdd/shared/fixtures/chat.ts`
```

## Bad Example
- feature 檔寫成 plan 內的相對路徑，step 檔照抄其他文件的路徑。

```
- [ ] T010 `/bdd realign` 對齊 `specs/truth/features/backend/聊天訊息/發言頻率.feature` 的測試碼於 `packages/server/tests/steps/chat.ts`
```

# Rule 3 - 輸入文件不一致時回報上游，不在 tasks.md 補註 [MUST]
- 路徑、命名這類機械不一致（例如 research.md 的路徑與 plan.md 的樹不同、research.md 與 dbml 的表名不同）以 plan.md 的樹與 `specs/truth/` 的契約為準照常展開，完成時向使用者回報需在哪份上游文件修正。
- 會改變做什麼的設計衝突（例如 feature 的預期與 `specs/truth/` 契約矛盾）不自行裁決，停下來向使用者提出。
- tasks.md 不設 Notes、Dependencies 之類的段落來記錄裁決；任務列、[P] 與 Must Read 已表達全部執行所需的資訊。

## Good Example
- 展開照 dbml 的表名，回報時指出 research.md 要改。

```
任務：- [ ] T031 [US2] `/bdd green` 實作 `specs/truth/features/backend/聊天訊息/靜音.feature` 的行為於 …（Must Read 引 `Table room_members.muted_player_id`）
回報：research.md R6 的欄位名 `mute_target` 與 specs/truth/data/schema.dbml 的 `muted_player_id` 不一致，tasks 以 dbml 為準，請修正 R6
```

## Bad Example
- 把不一致寫成 tasks.md 的 Notes 自行消化，上游文件永遠不會被修。

```
## Notes
- 欄位以 dbml 的 `muted_player_id` 為準，research.md R6 的 `mute_target` 即此欄
```

# Rule 4 - 步驟標記與十種句型 [MUST]
- 任務描述以步驟標記開頭，標記放在 [P] 與 [US] 之後，句型依步驟固定：

| 步驟 | 句型 | 所在 Phase |
|---|---|---|
| 環境 | `` `環境` <動作與內容>於 `路徑` `` | Setup；套件移除在最後一個 DELETE（或 MODIFY）Phase 末尾 |
| 基礎 | `` `基礎` <動作與內容>於 `路徑` `` | Foundational；ALTER、DROP 在 MODIFY、DELETE Phase 末尾 |
| 盤點 | `` `盤點` 盤點 <端點> 受 truth 異動影響的 feature、step、helper、fixture 與產品行為於 `specs/plans/<NNN>-<name>/impact-audit.md` `` | Truth Impact Audit |
| realign | `` `/bdd realign` 對齊 `<範疇>` 的測試碼於 `路徑` `` | MODIFY |
| red | `` `/bdd red` 撰寫 `<範疇>` 的 step 於 `路徑` `` | ADD |
| green | `` `/bdd green` 實作 `<範疇>` 的行為於 `路徑` `` | MODIFY、ADD |
| refactor | `` `/bdd refactor` 整理 `<範疇>` 的程式碼於 `路徑` `` | MODIFY、ADD |
| 移除 | `` `移除` 移除 <被刪除的行為> 的測試與產品行為於 `路徑` `` | DELETE |
| 重構 | `` `重構` <量測與重構內容>於 `路徑` `` | NFR 重構 |
| 驗證 | `` `驗證` <動作與內容> `` | Acceptance Gates |

## Good Example
- 每種步驟各用自己的標記與句型。

```
- [ ] T001 [P] `環境` 安裝 decimal.js 4.x 於 `backend/package.json`
- [ ] T003 [P] `基礎` 新增贈品發放紀錄資料表於 `backend/db/migrations/0004_gift_grants.sql`
- [ ] T005 `盤點` 盤點 backend 受 truth 異動影響的 feature、step、helper、fixture 與產品行為於 `specs/plans/004-full-amount-gift/impact-audit.md`
- [ ] T010 `/bdd realign` 對齊 `specs/truth/features/backend/訂單/訂單明細.feature:21` 的測試碼於 `backend/tests/bdd/modules/訂單/斷言.ts`
- [ ] T014 `移除` 移除會員自行取消贈品的測試與產品行為於 `frontend/src/components/GiftCancelButton.tsx`
- [ ] T020 [US1] `/bdd red` 撰寫 `specs/truth/features/backend/贈品/滿額加贈.feature` 的 step 於 `backend/tests/bdd/modules/贈品/前置.ts`
- [ ] T042 `驗證` 以 /dsl-refine 的 `check_trace.py --plan <plan 目錄>` 確認本 plan 前綴的 acceptance 檢查點都有端點 Example 覆蓋
```

## Bad Example
- 沒有步驟標記，或用了不存在的標記，執行者會走錯流程。

```
- [ ] T010 調整 `…/訂單明細.feature` 的測試於 `backend/tests/bdd/modules/訂單/斷言.ts`
- [ ] T014 `/bdd delete` 移除取消贈品於 `backend/src/routes/gift.ts`
```

# Rule 5 - 任務句不重述 feature 內容 [MUST]
- `/bdd` 任務句只寫步驟標記、feature 檔路徑與檔案路徑，不寫 Rule、Example 標題、句型或預期結果；內容由所在 Phase 的共用區塊指回 feature 檔與 dsl.md。

## Good Example
- 只有 feature 檔路徑。

```
- [ ] T030 [US2] `/bdd red` 撰寫 `specs/truth/features/backend/聊天訊息/靜音.feature` 的 step 於 `backend/tests/bdd/modules/靜音對手/操作.ts`
```

## Bad Example
- 把 Rule 名稱與預期結果抄進任務句，feature 修改後兩邊就不一致。

```
- [ ] T030 [US2] `/bdd red` 撰寫 `specs/truth/features/backend/聊天訊息/靜音.feature` 中靜音後看不到對手訊息、對手不會察覺的 step 於 `backend/tests/bdd/modules/靜音對手/操作.ts`
```

# Rule 6 - [P] 只用於環境與基礎任務 [MUST]
- 只有 `環境` 與 `基礎` 任務可標 [P]，且須與同一 Phase 其他標 [P] 的任務寫不同檔、不依賴彼此的產出。
- `/bdd`、`重構` 與 `驗證` 任務一律不標 [P]；feature Phase 之間能否平行寫在 Dependencies & Execution Order，不以 [P] 表示。

## Good Example
- 兩個基礎任務各改一個檔，彼此無依賴，都標 [P]。

```
- [ ] T005 [P] `基礎` 新增聊天訊息資料表與房間成員、對局的聊天欄位於 `backend/db/migrations/0002_chat.sql`
- [ ] T006 [P] `基礎` 讓測試資料庫的清空與資料表比對涵蓋聊天訊息資料表於 `backend/tests/bdd/shared/database.ts`、`backend/tests/bdd/shared/asserts.ts`
```

## Bad Example
- 兩個 red 任務標了 [P]，它們寫的是同一個模組的 step 檔，平行執行會互相覆寫。

```
- [ ] T022 [P] [US1] `/bdd red` 撰寫 `specs/truth/features/backend/聊天訊息/訊息內容.feature` 的 step 於 `backend/tests/bdd/modules/聊天訊息/斷言.ts`
- [ ] T013 [P] [US1] `/bdd red` 撰寫 `specs/truth/features/backend/聊天訊息/發言頻率.feature` 的 step 於 `backend/tests/bdd/modules/聊天訊息/斷言.ts`
```
