# Rule 1 - 部位只寫識別碼 [MUST]
- 契約行的每個部位只寫該文件裡可以直接定位的識別碼，不附括號說明、不列套件名與版本。
- 各文件的識別碼寫法：

| 文件 | 識別碼寫法 |
|---|---|
| `spec.md` | `使用者故事 n`、`FR-nnn`、`NFR-nnn`、`SC-nnn`、`使用者故事 n › Acceptance Scenarios a, b` |
| `features/<端點>/<檔>.feature` | 整檔只寫文件不寫部位（`- \`specs/truth/features/backend/聊天訊息/靜音.feature\``）；需要時寫 `Rule: <Rule 名稱>` |
| `features/<端點>/dsl.md` | 句型原文（如 `{玩家暱稱} 靜音對手`）、`附錄：共通規則` |
| `features/acceptance/<主題>.feature` | 整檔，或 Journey 的 Example 標題 |
| `research.md` | `R<n>. 標題`，需要時加 ` › 子段`；子段取該章節內的粗體標籤（Decision、Rationale、注意）或 bullet 開頭詞 |
| `techstack.md`、`plan.md` | 章節名，需要時加 ` › 子項` |
| `specs/truth/contracts/openapi.yaml` | 路徑（如 `/api/cart`）、`schemas.Name` |
| `specs/truth/contracts/asyncapi.yaml` | `channels.x`、`operations.x`、`messages.x`、`schemas.x` |
| `specs/truth/data/schema.dbml` | `Table 表.欄位`、`Table 表`、`TableGroup 名 › 子段` |
| `ui/frontend.md` | `章節 › 子項` |
| `ui/prototype/*` | 檔名，需要時加 `?state=` |

## Good Example
- 每個部位都是能在文件中直接找到的識別碼。

```
    - `spec.md` -> `使用者故事 1`, `FR-004`, `FR-005`, `NFR-003`
    - `specs/truth/data/schema.dbml` -> `Table cart_items.quantity`, `TableGroup 資料庫共通介面 › 購物車`
    - `research.md` -> `R8. 庫存扣減與並行控制 › 購物車`
```

## Bad Example
- 部位後面附了括號說明，techstack 的部位變成套件名與版本清單。

```
    - `research.md` -> `R8. 庫存扣減與並行控制`（加入購物車只檢查不扣庫存、累加用 ON CONFLICT）
    - `techstack.md` -> `Runtime Dependencies`（fastify 5.12.7、zod 4.6.7、pg 8.13.0）
```

# Rule 2 - spec.md 先故事段再編號 [SHOULD]
- 引用 spec.md 時，先列 `使用者故事 n`，再列該故事底下的 FR / NFR / Scenario 編號，讓執行者先讀敘述再讀規則。

## Good Example
- 故事段在前，編號在後。

```
    - `spec.md` -> `使用者故事 2`, `FR-011`, `FR-012`, `FR-013`, `NFR-005`
```

## Bad Example
- 只列編號，執行者不知道這些需求屬於哪個故事、脈絡是什麼。

```
    - `spec.md` -> `FR-011`, `FR-012`, `FR-013`, `NFR-005`
```

# Rule 3 - 任務只碰特定欄位時 dbml 寫到欄位 [SHOULD]
- 任務只讀寫資料表的部分欄位時，部位寫 `Table 表.欄位`，每個碰到的欄位各一個。
- 建立整張表或碰到全部欄位的任務才寫 `Table 表`。

## Good Example
- 結帳交易只碰庫存、冪等鍵、狀態與單價快照四個欄位，逐欄列出。

```
    - `specs/truth/data/schema.dbml` -> `Table products.stock`, `Table orders.idempotency_key`, `Table orders.status`, `Table order_items.unit_price_cents`
```

## Bad Example
- 同一個結帳交易任務只寫整張表，執行者得自己猜要看哪些欄位。

```
    - `specs/truth/data/schema.dbml` -> `Table products`, `Table orders`, `Table order_items`
```

# Rule 4 - 沒有內容的 Must Read 與 Optional 整段省略 [MUST]
- 任務層的 Must Read 或 Optional 沒有要列的部位時，整段省略，不寫「無」。
- Why 一律保留。

## Good Example
- refactor 的參照都在 Phase 共用區塊，任務層只剩 Why。

```
- [ ] T060 [US2] `/bdd refactor` 整理 `specs/truth/features/backend/聊天訊息/靜音.feature` 的程式碼於 `backend/src/services/mute-service.ts`、`backend/tests/bdd/modules/靜音對手/斷言.ts`
  - Why: 快照的隱藏過濾同時影響使用者故事 1 的聊天紀錄，整理時改動過濾條件會讓系統訊息在靜音期間被誤擋。
```

## Bad Example
- 為了湊段落寫「無」，每個任務多出兩行沒有資訊的內容。

```
- [ ] T060 [US2] `/bdd refactor` 整理 `specs/truth/features/backend/聊天訊息/靜音.feature` 的程式碼於 `backend/src/services/mute-service.ts`
  - Optional:
    - 無
  - Why: 快照的隱藏過濾同時影響使用者故事 1 的聊天紀錄，整理時改動過濾條件會讓系統訊息在靜音期間被誤擋。
```

# Rule 5 - Why 一句話說明不讀會錯在哪 [MUST]
- Why 只寫一句話，內容是不讀 Must Read 的部位時會在哪個決策或行為上做錯。
- 不重述部位清單、不重述任務內容。
- 不含程式識別碼（反引號）；要指到的識別碼放在 Must Read 的部位，Why 只用需求與文件的語言。

## Good Example
- 一句話，直接點出漏讀的後果，沒有任何程式識別碼。

```
  - Why: 同一訪客同時加入同一商品時數量要正確累加，dbml 已定下用唯一鍵衝突時更新而非先讀再寫，照直覺寫會在並行下少算。
```

## Bad Example
- 把實作細節與當場發明的函式名寫進 Why，這些是實作時才會決定的東西。

```
  - Why: `addItem` 要用 `INSERT ... ON CONFLICT DO UPDATE` 累加 `quantity`，再呼叫 `recalculateTotal` 回傳新購物車。
```

# Rule 6 - 契約行的文件必須已存在 [MUST]
- Phase 共用區塊、Must Read 與 Optional 指向的文件必須在規劃時已存在：plan 內的文件寫成以 plan 目錄為起點的路徑（`spec.md`、`plan.md`、`research.md`、`ui/frontend.md`、`truth-delta.md`）；truth 與其他 plan 的文件寫從 repository root 起算的 `specs/...` 完整路徑。
- 任務會產生的檔（程式、設定、種子資料）在規劃時還不存在，不得作為契約的文件；唯一例外是 `impact-audit.md`，它由 Truth Impact Audit Phase 產生，可作為之後 MODIFY、DELETE Phase 的契約。

## Good Example
- plan 內的文件用相對路徑，truth 的契約用完整路徑；MODIFY Phase 引用 Audit 產出的 impact-audit.md。

```
  - Must Read:
    - `specs/truth/contracts/openapi.yaml` -> `components.schemas.Order`
    - `impact-audit.md` -> `backend`
```

## Bad Example
- 指向已經不存在的 plan 內 analysis/，以及實作後才會產生的種子檔。

```
  - Must Read:
    - `specs/truth/contracts/openapi.yaml` -> `components.schemas.Order`
  - Optional:
    - `backend/tests/bdd/shared/seed-gifts.ts`
```

# Rule 7 - red 的任務層不列 feature 檔與 dsl 句型 [MUST]
- `/bdd red` 的 feature 檔與 dsl.md 附錄已在 Phase 共用區塊；用到的句型由 bdd skill 以 `list_slices.py` 逐 slice 取出，任務層不再列 feature 檔與句型。
- red 的任務層只列共用區塊以外、寫 step 時才需要的參照（例如 openapi 的回應形狀放 Optional），沒有就整段省略。

## Good Example
- red 只補一個 Optional，其餘靠共用區塊。

```
- [ ] T007 [US1] `/bdd red` 撰寫 `specs/truth/features/backend/聊天訊息/可見範圍與系統訊息.feature` 的 step 於 `backend/tests/bdd/modules/聊天訊息/前置.ts`
  - Optional:
    - `specs/truth/contracts/openapi.yaml` -> `/room/chat/messages`, `/state`
  - Why: 這是後端聊天模組的第一個 red，資料列落地與回應形狀的必查方式定在共通規則，各 step 自訂斷言標準會讓之後每個 Then 的檢查強度不一致。
```

## Bad Example
- 重列 feature 檔並手抄 17 個句型，dsl.md 修改後清單就與實際不一致。

```
  - Must Read:
    - `specs/truth/features/backend/聊天訊息/可見範圍與系統訊息.feature`
    - `specs/truth/features/backend/平臺共用/dsl.md` -> `{玩家暱稱} 離開房間`, `{玩家暱稱} 讀到以下聊天紀錄：`, `{玩家暱稱} 已離開房間`, …
```

# Rule 8 - green 的任務層只列實作契約 [MUST]
- `/bdd green` 的任務層 Must Read 只列實作要遵守、共用區塊沒有的契約：`specs/truth/contracts/` 的 openapi、asyncapi，`specs/truth/data/` 的 schema.dbml，plan 的 `ui/frontend.md` 與 research.md 決策。
- `/bdd refactor` 通常沒有共用區塊以外的參照，任務層只寫 Why。

## Good Example
- green 只列 openapi、dbml 與 research；故事、需求編號與系統介面已在共用區塊。

```
- [ ] T059 [US2] `/bdd green` 實作 `specs/truth/features/backend/聊天訊息/靜音.feature` 的行為於 `backend/src/routes/chat.ts`、`backend/src/services/mute-service.ts`
  - Must Read:
    - `specs/truth/contracts/openapi.yaml` -> `/room/chat/mute`, `/room/chat/unmute`
    - `specs/truth/data/schema.dbml` -> `Table room_members.muted_player_id`
    - `research.md` -> `R9. 靜音對手`
```

## Bad Example
- 把共用區塊已有的 feature、spec 與 plan 再列一次，三個任務各讀一遍同樣的清單。

```
  - Must Read:
    - `specs/truth/features/backend/聊天訊息/靜音.feature`
    - `spec.md` -> `使用者故事 2`
    - `plan.md` -> `系統介面的盤點 › 靜音 API 介面`
    - `specs/truth/contracts/openapi.yaml` -> `/room/chat/mute`
```

# Rule 9 - Phase 共用區塊放同 Phase 任務共讀的參照 [MUST]
- Phase 標題（與說明段）之後、第一個 `###` 小節或任務之前，以 `**Phase Must Read**:` 列出本 Phase 任務共讀的參照，格式同 Must Read 的契約行，不縮排。
- ADD Phase 一律寫，固定依序含：該 feature 檔；`specs/truth/features/<端點>/平臺共用/dsl.md` -> `附錄：共通規則`；spec.md 的故事段或既有需求異動與 `@spec` 編號（依 Rule 2）；涉及的 `plan.md` -> `系統介面的盤點 › <介面名>`。
- MODIFY、DELETE Phase 一律寫，固定含：本 Phase 處理的每一列 `truth-delta.md` -> `<部位>`（各一行）；`impact-audit.md` -> `<端點>`；`specs/truth/features/<端點>/平臺共用/dsl.md` -> `附錄：共通規則`；spec.md 的對應既有需求異動。
- Truth Impact Audit Phase 一律寫，列出 truth-delta 的全部 MODIFY、DELETE 列。
- 其他 Phase 只把被兩個以上任務共讀的參照抽到共用區塊，沒有就不寫；任務層不得重列共用區塊已有的參照。

## Good Example
- MODIFY Phase 的共用區塊列出 truth-delta 的列與 impact-audit 的端點段。

```
**Phase Must Read**:
- `truth-delta.md` -> `backend/聊天訊息/dsl.md › Given › 房間 {房間代碼} 的聊天區只有 {玩家暱稱} 在 {秒數} 秒內送出的 {則數} 則訊息`
- `truth-delta.md` -> `backend/聊天訊息/發言頻率.feature › Rule: 10 秒內至多 8 則 › Example: 第 9 則被拒絕`
- `impact-audit.md` -> `backend`
- `specs/truth/features/backend/平臺共用/dsl.md` -> `附錄：共通規則`
- `spec.md` -> `既有需求異動 #1`
```

## Bad Example
- 沒有共用區塊，realign、green、refactor 各自列一次，而且沒有指向 truth-delta，執行者不知道改了什麼。

```
- [ ] T010 `/bdd realign` …
  - Must Read:
    - `specs/truth/features/backend/聊天訊息/發言頻率.feature`
- [ ] T011 `/bdd green` …
  - Must Read:
    - `specs/truth/features/backend/聊天訊息/發言頻率.feature`
```
