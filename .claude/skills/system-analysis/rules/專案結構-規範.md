# Rule 1 - Documentation 分成 plan package 與 truth 兩段 [MUST]
- Documentation 樹的根是 `specs/`，分成兩段：
  - `plans/<NNN>-<名稱>/`：列出 `spec.md`、`features/acceptance/`、`research.md`、`plan.md`、`ui/`（Phase 3 前端委派 skill 的產出）、`truth-delta.md`，以及由後續 skill 產出的 `impact-audit.md`、`tasks.md`。
  - `truth/`：只列本次會被修改的 truth 檔（`requirements.md`、`techstack.md`、`contracts/` 下的契約、`data/schema.dbml`、`features/`），每個檔案註明本次改了什麼。
- 每個檔案以 `# 說明` 寫出內容與產出或修改它的 skill；委派 skill 的產出檔名與 truth 檔名取自該 skill 的 SKILL.md，不自行命名。
- 不列不由上述 skill 產出或修改的文件，也不列每個 plan 各一份的契約或資料表副本。

## Good Example
- plan package 與本次修改的 truth 分兩段，每檔註明產出或修改它的 skill。

```
specs/
├── plans/003-chat-reactions/      # Plan：本次要改什麼、怎麼做
│   ├── spec.md                    # 功能規格與既有需求異動（/specify 產出）
│   ├── features/acceptance/       # 驗收 Journey（/spec-by-example 產出）
│   ├── research.md                # 本次的技術決策（/technical-research 產出）
│   ├── plan.md                    # 本檔案
│   ├── ui/
│   │   ├── frontend.md            # 前端端點的畫面規格（ui-plan 產出）
│   │   └── prototype/             # 前端端點的可操作雛形（ui-plan 產出）
│   ├── truth-delta.md             # 本次對 truth 的異動紀錄（/specify 建立，各 truth owner 記錄）
│   ├── impact-audit.md            # 既有測試與程式的影響盤點（/implement 產出）
│   └── tasks.md                   # 任務清單（/tasks 產出）
└── truth/                         # Truth：系統現在是什麼（全專案一份，本次就地修改）
    ├── requirements.md            # 新增表情回應需求、修改 002/FR-002（/specify 修改）
    ├── contracts/openapi.yaml     # 新增表情回應 API、修改訊息上限與快照（api-plan 修改）
    ├── data/schema.dbml           # 新增 message_reactions、修改 chat_messages.content（data-plan 修改）
    └── features/                  # 表情回應與 500 字的端點 feature 檔（/dsl-refine 修改）
```

## Bad Example
- 根是 plan 目錄加 `analysis/`，每個 plan 各產出一份只含本次內容的契約與資料表副本，truth 沒有被修改；也漏列 truth-delta.md。

```
specs/003-chat-reactions/
├── spec.md
├── plan.md
└── analysis/
    ├── openapi.yaml
    └── schema.dbml
```

# Rule 2 - Structure Decision 說明切分理由 [SHOULD]
- 以一段話說明第一層依什麼切分、端點下依什麼分層、檔案如何對回系統介面，以及這樣切對分析與實作的好處。
- 不重述目錄樹本身。

## Good Example
- 說明切分依據、檔案與介面的對應方式與好處，沒有逐一列目錄。

```
**Structure Decision**: 第一層依 `前端端點`、`後端端點` 切成兩個可獨立建置的專案，端點下依角色分層（routes、services、storage、lib、tests），讓同類檔案放在一起；每個程式檔的說明標明對應的系統介面，介面的分析結果因此都能找到實作落點。
```

## Bad Example
- 只把目錄樹再念一次，沒有說明為什麼這樣切。

```
**Structure Decision**: 有 frontend、backend 兩個目錄，backend/src 底下有 routes、services、storage、lib。
```

# Rule 3 - Source Code 樹只列本次異動的檔案 [MUST]
- Source Code 樹以 repository 現有的檔案為基準，只列本次新增、修改、刪除的檔案，包含 repository root 與各端點層的設定檔；沒有異動的資料夾只列到目錄層，不展開其中的檔案。
- 每個檔案後以 `# 說明` 簡述本次在這個檔案做什麼，並依 Rule 6 標出異動與介面；目錄只在需要說明時才加註記。
- 首次建立（repository 還沒有該端點的程式）時，每個檔案都是新增。

## Good Example
- 只列異動的檔案，沒有異動的 `db/repositories/` 以外的資料夾只列到目錄層；新增、修改各自標出。

```
backend/
├── db/
│   └── migrations/
│       └── 0003_reactions.sql   # 新增表情回應資料表、放寬訊息內容長度（新增；資料庫共通介面、message_reactions 資料表介面、chat_messages 資料表介面）
├── src/
│   ├── routes/
│   │   └── reactions.ts         # 加上與移除表情回應（新增；表情回應 API 介面）
│   ├── domain/
│   │   └── chat-format.ts       # 字數上限 500、總量上限隨之調整（修改；聊天訊息 API 介面、聊天區介面）
│   └── services/                # 其餘服務不變更
└── tests/                       # 測試步驟由 /tasks 依 features 異動規劃
```

## Bad Example
- 從零重新設計一棵完整的樹，看不出哪些檔案已存在、哪些是本次新增或修改；未異動的檔案也逐一展開，樹會隨 plan 增加而膨脹。

```
backend/
├── package.json                 # 後端套件設定與指令
├── src/
│   ├── main.ts                  # 啟動流程
│   ├── routes/
│   │   ├── session.ts           # 以暱稱建立玩家身分
│   │   ├── chat.ts              # 送出聊天訊息
│   │   └── reactions.ts         # 表情回應
```

# Rule 4 - 說明只寫職責，不寫實作細節 [MUST]
- 檔名寫出副檔名，資料夾與檔名不帶框架或套件名稱。
- 說明只寫這個檔案負責什麼；框架、套件、API 路徑與欄位、函式呼叫、演算法等實作細節，留給 wave 分析時委派的 skill 決定。

## Good Example
- 檔名有副檔名，說明只寫職責。

```
├── db/
│   └── client.ts                # 資料庫連線與交易（新增；資料庫共通介面）
├── routes/
│   └── photos.ts                # 照片上傳、移動、刪除（新增；照片 API 介面）
```

## Bad Example
- 資料夾帶了 ORM 名稱，說明寫出建構方式與 API 路徑，提前做了 wave 才該做的分析。

```
├── prisma/
│   └── client.ts                # new PrismaClient({ adapter })；單例，關閉時 $disconnect
├── routes/
│   └── photos.ts                # /api/photos*（multer 上傳、sharp 產生縮圖）
```

# Rule 5 - 端點下依角色分層 [MUST]
- 第一層一個目錄對應一個可獨立建置的端點（例如 `frontend/`、`backend/`，root 的設定檔除外）；資料庫、檔案儲存等不自成程式專案的端點，其檔案放在存取它的端點底下（例如 `backend/db/`、`backend/src/storage/`），以 Rule 6 的介面標註對回。
- 端點下依角色分層，例如 `src/routes/`、`src/services/`、`src/lib/`、`tests/`，不再為每個系統介面開一個目錄。

## Good Example
- 端點下依 routes、services 分層，相簿與照片的檔案分散在各自的角色目錄。

```
backend/
└── src/
    ├── routes/
    │   ├── albums.ts            # 相簿的建立、改名、刪除（新增；相簿 API 介面）
    │   └── photos.ts            # 照片上傳、移動、刪除（新增；照片 API 介面）
    └── services/
        └── album-service.ts     # 相簿日期推導與封面設定（新增；相簿 API 介面）
```

## Bad Example
- 端點下為每個系統介面各開一個目錄，與角色分層的結構不符。

```
backend/
├── common/                      # 後端共通介面
├── albums/                      # 相簿 API 介面
└── photos/                      # 照片 API 介面
```

# Rule 6 - 程式檔註明異動與對應的系統介面 [MUST]
- 每個程式檔（含測試檔）的說明以全形括號寫出「（<新增|修改|刪除>；<介面>、<介面>）」：先寫本次對這個檔案的異動，分號後列出它對應的系統介面，名稱與系統介面的盤點一字不差。
- `package.json`、`tsconfig.json` 等設定檔只寫異動，不需標註介面，例如「（修改）」。

## Good Example
- 異動與介面都標出，介面名稱與盤點一字不差，設定檔只寫異動。

```
├── package.json                 # 新增表情回應的測試指令（修改）
├── src/routes/reactions.ts      # 加上與移除表情回應（新增；表情回應 API 介面）
└── src/services/snapshot.ts     # 快照帶出每則訊息的回應數量（修改；狀態同步 API 介面）
```

## Bad Example
- 第一個檔案沒有標出異動與介面；第二個寫成盤點中不存在的「回應模組」，也看不出是新增還是修改。

```
├── src/routes/reactions.ts      # 加上與移除表情回應
└── src/services/snapshot.ts     # 快照帶出回應數量（回應模組）
```

# Rule 7 - 每個系統介面至少對應一個檔案 [MUST]
- 盤點出的每個系統介面（含修改既有、刪除既有），都必須出現在至少一個程式檔的介面標註中；刪除既有的介面標在被刪除或被修改的檔案上。
- 找不到對應檔案的介面，代表漏了檔案，回頭補上。

## Good Example
- 盤點的三個後端介面都能在某個檔案的標註中找到，被修改的既有介面標在被修改的檔案上。

```
盤點：後端共通介面、表情回應 API 介面、聊天訊息 API 介面
├── src/domain/error-codes.ts    # 新增表情回應錯誤碼（修改；後端共通介面）
├── src/routes/reactions.ts      # 加上與移除表情回應（新增；表情回應 API 介面）
└── src/domain/chat-format.ts    # 字數上限 500（修改；聊天訊息 API 介面）
```

## Bad Example
- 盤點有修改既有的「聊天訊息 API 介面」，Source Code 樹卻沒有任何檔案標註它，/tasks 找不到 500 字要改在哪裡。

```
盤點：後端共通介面、表情回應 API 介面、聊天訊息 API 介面
├── src/domain/error-codes.ts    # 新增表情回應錯誤碼（修改；後端共通介面）
└── src/routes/reactions.ts      # 加上與移除表情回應（新增；表情回應 API 介面）
```
