# Rule 1 - 介面依功能拆分 [SHOULD]
- 每個端點依功能拆成多個系統介面，不以「一個端點一個介面」交差。
- 拆分依據依端點類型決定：

| 端點類型 | 拆分依據 |
|---|---|
| 前端端點 | 頁面或使用流程 |
| 後端端點 | API 資源 |
| 資料庫端點 | spec.md Key Entities 對應的資料表 |
| 檔案儲存端點 | 檔案類別 |

- 表中沒有的端點類型（硬體、手機、雲端、第三方等），比照最接近的類型拆分；功能單一的端點可以只有一個介面，並在主要介面說明。

## Good Example
- 後端依 API 資源拆成五個介面，每個介面的範圍互不重疊。

```
7. `相簿 API 介面`
8. `照片 API 介面`
9. `排序 API 介面`
10. `影像 API 介面`
11. `匯出 API 介面`
```

## Bad Example
- 整個後端只盤點出一個介面，後續分析無法平行，也看不出各資源的責任邊界。

```
2. `HTTP API 介面`
    - 端點類型：`後端端點`
    - 主要介面：相簿、照片、排序、影像、匯出的所有 API
```

# Rule 2 - 共通介面只承接跨功能需求 [SHOULD]
- 端點內有同時約束多個介面的需求（錯誤處理、安全、啟動檢查、migration、交易原子性等）時，另設一個 `<端點>共通介面` 承接，排在該端點所有介面之前。
- 端點沒有跨功能需求時不設共通介面；只約束單一介面的需求歸入該介面。

## Good Example
- 後端的錯誤碼、本機連線限制與啟動檢查同時約束所有 API，集中在共通介面；檔案儲存的空間檢查只關係原檔寫入，歸入原檔儲存介面，不放進共通介面。

```
6. `後端共通介面`
    - 主要介面：錯誤碼與 HTTP 狀態對應、本機連線限制、啟動時檢查資料庫連線與儲存目錄
16. `原檔儲存介面`
    - 主要介面：原檔目錄、寫入前空間檢查
```

## Bad Example
- 本機連線限制約束所有 API，卻分散寫進每個 API 介面，責任重複且容易漏掉其中一個。

```
7. `相簿 API 介面`
    - 主要介面：相簿建立、改名、刪除、本機連線限制
8. `照片 API 介面`
    - 主要介面：多檔照片上傳、本機連線限制
```

# Rule 3 - 需求原文依據的寫法 [MUST]
- 優先引用 spec.md Input 的使用者原話，以「」包住。
- 使用者原話未涵蓋該介面時，改寫「需求要求……」概述 spec.md 中的要求，不偽造引號。
- 句末一律以「；對應 `FR-xxx`、`NFR-xxx` 與 `NNN/FR-yyy`。」列出全部對應條目編號：本 plan 的需求寫裸號（與 spec.md 一致），既有需求異動與其他既有需求一律寫帶 plan 前綴的編號；前綴由 planner 寫入 truth 時才補上。

## Good Example
- 原話涵蓋的介面引用原話；原話沒提到字數上限，改用「需求要求」；本 plan 的 FR 寫裸號，被修改的既有需求帶前綴。

```
- 需求原文依據：使用者描述要求「可以對訊息按 👍、❤️、😂」；對應 `FR-001`、`FR-002` 與 `FR-003`。
- 需求原文依據：需求要求單則訊息的上限放寬為 500 字；對應 `002/FR-002`。
```

## Bad Example
- 第一行把 spec 條文當成使用者原話加上引號；第二行把既有需求寫成裸號，讀者會以為是本 plan 的 FR-002；第三行沒有列出對應條目，讀者無法回查。

```
- 需求原文依據：使用者描述要求「系統 MUST 提供表情回應」；對應 `FR-001`。
- 需求原文依據：需求要求單則訊息的上限放寬為 500 字；對應 `FR-002`。
- 需求原文依據：使用者描述要求「訊息可以長一點」。
```

# Rule 4 - 每條約束介面的需求至少歸屬一個介面 [MUST]
- 盤點完成後，spec.md 中約束某個介面的每條 FR 與 NFR 編號，以及「既有需求異動」表中的每一個既有編號，都必須出現在至少一個介面的需求原文依據中；連續編號可寫成 `FR-016` ~ `FR-016c`。
- DELETE 的既有編號掛在要刪除或要修改的既有介面上。
- 只約束開發流程、不屬於任何介面的條目（測試覆蓋率、測試決定性、效能量測進 CI、遙測政策等）不列入。
- 其餘找不到歸屬的條目，代表漏了介面、漏了共通介面或漏了受影響的既有介面，回頭補上，不得略過。

## Good Example
- 既有需求異動 #1 修改 `002/FR-002`，由被修改的既有介面承接；`003/NFR-002` 約束所有 API，補設後端共通介面承接。

```
6. `聊天訊息 API 介面`
    - 異動：修改既有
    - 需求原文依據：需求要求單則訊息的上限放寬為 500 字；對應 `002/FR-002`。
4. `後端共通介面`
    - 需求原文依據：需求要求表情回應在 1 秒內送達雙方……；對應 `NFR-002`。
```

## Bad Example
- 只盤點了表情回應的新介面，既有需求異動 #1 的 `002/FR-002` 沒有任何介面承接，契約與資料表的 200 字上限都不會被修改。

```
5. `表情回應 API 介面` ……對應 `FR-001`、`FR-002`
9. `message_reactions 資料表介面` ……對應 `FR-001`
（全文找不到 `002/FR-002`）
```

# Rule 5 - 主要介面只列功能範圍 [MUST]
- 主要介面只列該介面涵蓋哪些功能或責任，以名詞片語頓號串列。
- 不寫分析結果：API 路徑與欄位、schema 欄位與型別、技術選型、套件名稱都留給後續委派的分析 skill。

## Good Example
- 只說明介面負責哪些事，沒有決定任何細節。

```
- 主要介面：照片歸屬相簿、拍攝日期與日期來源、檔案路徑、內容雜湊
```

## Bad Example
- 已經寫出欄位型別與技術選型，等於提前做了系統分析。

```
- 主要介面：`photos(id BIGINT PK, album_id BIGINT FK, taken_at VARCHAR(19), sha256 CHAR(64))`，以 Prisma 管理
```

# Rule 6 - 受影響的既有介面沿用 truth 名稱並標出異動 [MUST]
- 下列任一情況成立時，對應的既有介面要列入盤點：
  - trace_refs 的命中：引用了被修改或刪除的需求編號、被 `**取代**` 的決策編號的 operation、Table、TableGroup 或 Example。
  - 新需求要擴充既有資源，例如在既有快照多帶一個欄位、在既有共通介面加一個錯誤碼。
  - 既有需求異動中的 MODIFY、DELETE 改變了某個既有介面的行為。
- 有 truth 承接的既有介面沿用 truth 的名稱，一字不差：後端介面取 openapi.yaml 或 asyncapi.yaml 的 tag，資料表介面取 `<Table 名> 資料表介面`，資料庫共通介面取 TableGroup 名。
- 每個介面在端點類型之後寫 `- 異動：新增`、`- 異動：修改既有` 或 `- 異動：刪除既有`；修改既有、刪除既有的主要介面只寫本次受影響的範圍。

## Good Example
- trace_refs 以 `002/FR-002` 命中 `sendChatMessage` 與 `Table chat_messages`，兩者以 truth 的名稱列為修改既有；表情回應是新的資源，列為新增。

```
trace_refs：openapi.yaml › operationId sendChatMessage（介面：聊天訊息 API 介面）
            schema.dbml › Table chat_messages（介面：chat_messages 資料表介面）

6. `聊天訊息 API 介面`
    - 端點類型：`後端端點`
    - 異動：修改既有
    - 主要介面：訊息字數與總量上限
9. `chat_messages 資料表介面`
    - 端點類型：`資料庫端點`
    - 異動：修改既有
    - 主要介面：訊息內容欄位的長度與限制
5. `表情回應 API 介面`
    - 端點類型：`後端端點`
    - 異動：新增
```

## Bad Example
- 被命中的既有介面改了名字，api-plan 會新增一個 `訊息 API 介面` tag，與 truth 中的 `聊天訊息 API 介面` 重複；也沒有標出異動，planner 分不出要新建還是就地修改。

```
6. `訊息 API 介面`
    - 端點類型：`後端端點`
    - 主要介面：送出訊息、500 字上限
```

# Rule 7 - 既有前端介面以程式檔與 features 模組定位 [MUST]
- 前端沒有 truth 契約承接介面名稱，前端介面名稱只在本 plan 內有效；受影響的既有前端介面可自行命名，不回頭讀取先前 plan 的 plan.md 沿用名稱。
- 修改既有、刪除既有的前端介面，主要介面最後以「；現行程式：`<檔案>`、`<檔案>`；features：`frontend/<模組>`」標出對應的程式檔與 `specs/truth/features/frontend/` 模組，讓 ui-plan 與 /tasks 找得到現況。

## Good Example
- 聊天區以本 plan 的名稱列出，並指出現行程式與 features 模組。

```
1. `聊天區介面`
    - 端點類型：`前端端點`
    - 異動：修改既有
    - 主要介面：字數提示與計數門檻、訊息下方的表情回應列；現行程式：`frontend/src/components/ChatInput.tsx`、`frontend/src/components/ChatMessageList.tsx`；features：`frontend/聊天訊息`
```

## Bad Example
- 為了沿用名稱去讀 002 的 plan.md，卻沒有指出現行程式與 features 模組，ui-plan 只能以已凍結的 002 ui/ 為基準。

```
1. `聊天區介面`（沿用 002 plan.md 的名稱）
    - 端點類型：`前端端點`
    - 異動：修改既有
    - 主要介面：字數提示、表情回應列
```
