# Rule 1 - 只依本次 Decision 增改刪，其餘既有列原樣保留 [MUST]
- 新增或修改的列只能來自本次 research.md 各 R 節 Decision 選定的執行環境與套件；Alternatives considered 中被否決或延後的技術一律不列，即使它是 registry 上的最新版。
- 本次 research 沒有提到的既有列（先前 plan 定案的套件）不得移除、改版或改寫用途。
- 刪除既有列必須有本次某個 R 節的 Decision 明寫移除該套件。

## Good Example
- R2 的 Decision 選定 TypeScript 6.0.3，techstack 只列這個版本；增量 plan 只在 R1 選定 emoji-regex 並升級 zod，其餘 001、002 的列不動。

```
| 語言 | typescript | 6.0.3 | 型別檢查 |
```

```
| 驗證 | zod | 4.7.0 | 請求本文 schema 驗證 |        ← 改版（R1）
| 驗證 | emoji-regex | 10.6.0 | 表情驗證 |           ← 新增（R1）
| 伺服器 | hono | 4.13.16 | HTTP 路由與中介層 |     ← 原樣保留
```

## Bad Example
- 把 Alternatives 中延後採用的 TypeScript 7.0.2 和 OPFS 也列進來，讀者會以為兩者都在用；增量 plan 把 truth 整份改寫成只剩本次 research 提到的套件，001、002 的 hono、mysql2 都消失。

```
| 語言 | typescript | 7.0.2 | 型別檢查 |
| 儲存 | OPFS | — | 存 Blob |
```

# Rule 2 - 版本與 research.md 一字不差 [MUST]
- 套件版本照抄 Decision 中的精確版本，不自行改成範圍或其他版本。
- 執行環境在 research.md 寫的是範圍時，就照寫範圍，不換成某個具體版本；Decision 同時寫了範圍與目前最新版時，照抄範圍。

## Good Example
- Node.js 照 R16 寫成範圍；套件照 Decision 寫精確版本。

```
| Node.js | 24 LTS（≥ 24.15） |
| @tanstack/react-virtual | 3.14.22 |
```

## Bad Example
- Node.js 換成 R16 順帶提到的最新 LTS 具體版本；套件版本被改成 caret 範圍。

```
| Node.js | 24.22.1 |
| @tanstack/react-virtual | ^3.14.0 |
```

# Rule 3 - 依是否隨正式建置散佈區分 Runtime 與 Dev [MUST]
- 會隨正式建置散佈的套件（正式環境執行時需要安裝的套件，前端 bundle 與後端部署都算）放 Runtime Dependencies；只在開發、建置、測試或 lint 時使用的放 Dev Dependencies。
- 本次新增、由 Dev 移到 Runtime 或變更版本的 Runtime 列，要列在本次 research.md「依賴授權」表；表中的每個套件也要是 Runtime 列。

## Good Example
- 測試用的 jsdom、fake-indexeddb 放在 Dev。

```
## Dev Dependencies
| 單元 / 整合測試 | jsdom | 30.1.3 | DOM 模擬環境 |
| 單元 / 整合測試 | fake-indexeddb | 6.2.6 | IndexedDB 模擬 |
```

## Bad Example
- jsdom 只在測試時使用，卻被放進 Runtime，和依賴授權表對不起來。

```
## Runtime Dependencies
| 測試 | jsdom | 30.1.3 | DOM 模擬環境 |
```

# Rule 4 - 一個套件一列 [MUST]
- 同一個 Decision 選定多個套件時，拆成多列，每列一個套件與一個版本。
- Decision 指定了子路徑入口時，以全形括號附在套件名後面。

## Good Example
- dnd-kit 的兩個套件各一列；heic-to 附上指定的入口。

```
| 互動 | @dnd-kit/core | 6.3.1 | 拖放排序 |
| 互動 | @dnd-kit/sortable | 10.0.0 | 格狀排序 |
| 影像 | heic-to（`heic-to/csp`） | 1.6.6 | HEIC 轉 JPEG |
```

## Bad Example
- 兩個套件擠在同一格，版本對應不清；heic-to 漏了 Decision 指定的 CSP 入口。

```
| 互動 | @dnd-kit/core、@dnd-kit/sortable | 6.3.1 / 10.0.0 | 拖放排序 |
| 影像 | heic-to | 1.6.6 | HEIC 轉 JPEG |
```

# Rule 5 - 用途只寫套件做什麼 [MUST]
- 用途欄用一個短語寫出這個套件在專案中負責什麼。
- 採用原因、決策細節、限制條件與 R 編號都留在 research.md，不寫進 techstack。

## Good Example
- 只說明負責什麼。

```
| 影像 | heic-to（`heic-to/csp`） | 1.6.6 | HEIC 轉 JPEG |
```

## Bad Example
- 混入了執行方式、採用原因與 R 編號。

```
| 影像 | heic-to（`heic-to/csp`） | 1.6.6 | HEIC 轉 JPEG，於 Worker 動態載入以符合 bundle 限制（R8） |
```

# Rule 6 - Source 依 plan 編號累加，Truth 說明段照模板 [MUST]
- `**Source**` 行是各 plan research.md 連結的頓號串列，格式為 `[NNN research.md](../plans/NNN-<名稱>/research.md)`，依 plan 編號遞增；本次 plan 的連結追加在末尾，既有連結不刪。
- Source 行下方的 Truth 說明段一字不差沿用 techstack 模板的固定文字；既有說明段與模板不同（例如仍寫 `changes.md`）時改回模板文字，其餘不改。

## Good Example
- 003 的連結追加在末尾，說明段指向 truth-delta.md。

```
**Source**: [001 research.md](../plans/001-pvp-1a2b/research.md)、[002 research.md](../plans/002-pvp-1a2b-chat/research.md)、[003 research.md](../plans/003-chat-reactions/research.md)

本檔屬於 Truth：…每次異動逐項記在該 plan 的 `truth-delta.md`；…
```

## Bad Example
- Source 被換成只有本次的相對連結，先前 plan 的依據找不到；說明段仍指向已不存在的 changes.md。

```
**Source**: [research.md](./research.md)

本檔屬於 Truth：…每次異動逐項記在該 plan 的 `changes.md`；…
```
