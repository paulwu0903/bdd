# Rule 1 - 列出本次新增或變更版本的 runtime 依賴 [MUST]
- 本次 R 節選定、會隨正式建置散佈，且是新增或變更版本的每個套件，都要在授權表中列一列；truth techstack 中未變動的既有套件不重列。
- 「隨正式建置散佈」指正式環境執行時需要安裝的套件，前端 bundle 與後端部署都算。
- 本次沒有新增或變更任何 runtime 套件時，不寫表格，整段只寫一行 `本次未新增或變更 runtime 依賴。`。
- 判準：逐一比對本次各 R 節的 Decision 與 truth techstack，每個新增或變更版本的 runtime 套件都能在表中找到。

## Good Example
- 第一份 plan：R2、R5、R6、R8、R11、R13 選定的 runtime 套件都在表中；之後的 plan 只新增 emoji-regex 並升級 zod 時只列這兩列，什麼都沒動時只寫一行。

```
| react / react-dom | MIT | |
| dexie | Apache-2.0 | 需保留 NOTICE |
| @dnd-kit/core、@dnd-kit/sortable | MIT | |
| @tanstack/react-virtual | MIT | |
| exifreader | MPL-2.0 | 檔案層級的 copyleft；不修改其原始碼，散佈時附上授權與原始碼位置 |
| heic-to | LGPL-3.0 | 見 R8：獨立 chunk、不修改、附授權與原始碼位置 |
```

```
| emoji-regex | MIT | |
| zod | MIT | |
```

```
本次未新增或變更 runtime 依賴。
```

## Bad Example
- 漏了 R8 選定的 heic-to，正好漏掉最需要處理的 LGPL 授權；另一份增量 plan 沒動任何 runtime 套件，卻把 truth 中所有既有套件重列一次。

```
| react / react-dom | MIT | |
| dexie | Apache-2.0 | 需保留 NOTICE |
| exifreader | MPL-2.0 | 檔案層級的 copyleft；不修改其原始碼，散佈時附上授權與原始碼位置 |
```

# Rule 2 - 有附帶義務的授權要寫出處理方式 [MUST]
- copyleft 授權（如 LGPL、MPL）與要求保留 NOTICE 的授權（如 Apache-2.0），備註欄要寫出如何履行義務。
- 處理方式已在某個 R 節詳述時，備註寫「見 R<n>」並附上摘要。
- 直接依賴自動帶入的遞移依賴有附帶義務時，寫在帶入它的直接依賴那一列的備註，不另開一列。

## Good Example
- LGPL 的處理方式連回 R8，並附上摘要。

```
| heic-to | LGPL-3.0 | 見 R8：獨立 chunk、不修改、附授權與原始碼位置 |
```

## Bad Example
- 只寫了授權名稱，備註空白，散佈時不知道要做什麼。

```
| heic-to | LGPL-3.0 | |
```

# Rule 3 - devDependencies 不列入並在表後說明 [SHOULD]
- 只用於開發與測試、不隨正式建置散佈的套件不列入表中。
- 表格後面寫一句說明，讓讀者知道是刻意排除，不是漏列。

## Good Example
- 表後一句說明排除的範圍。

```
devDependencies 不隨正式建置散佈，不列入 `THIRD-PARTY-NOTICES.md`。
```

## Bad Example
- 把測試與 lint 工具列進表中，混淆了要附授權的範圍。

```
| vitest | MIT | |
| eslint | MIT | |
```
