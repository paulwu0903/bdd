# Rule 1 - 層級為 Feature > Rule > Example [MUST]
- 每個 Example（或 Scenario Outline）都放在某個 Rule 底下，不用沒有 Rule 的 Scenario。
- 縮排固定：Rule 2 格、Example 與其正上方的 tag 4 格、步驟與步驟註解 6 格、Data Table 與 Examples 表 8 格。

## Good Example
- Example 位在 Rule 底下，縮排依層級遞增。

```
Feature: 購物車

  Rule: 重複加入同一商品必須累加數量

    @ac:003/購物車與運費:1-1
    Example: 已有 2 件的 A100 再加入 1 件
      Given "小芳" 的購物車已有 "A100" 共 2 件
      When "小芳" 把 "A100" 加入購物車
      Then "小芳" 的購物車有 "A100" 共 3 件
```

## Bad Example
- 直接在 Feature 底下寫 Scenario，沒有 Rule 說明它驗證哪條規則。

```
Feature: 購物車

  @ac:003/購物車與運費:1-1
  Scenario: 已有 2 件的 A100 再加入 1 件
    Given "小芳" 的購物車已有 "A100" 共 2 件
    When "小芳" 把 "A100" 加入購物車
    Then "小芳" 的購物車有 "A100" 共 3 件
```

# Rule 2 - Rule 名稱是一句可驗證的陳述 [MUST]
- Rule 名稱用繁體中文，講清楚驗證什麼，例如「xxx 必須 yyy」「xxx 不得 yyy」。
- 不用「且／並／還要」把兩個行為接成一條，除非它真的是不可分的單一行為。

## Good Example
- 一條 Rule 一個可驗證的行為。

```
Rule: 重複加入同一商品必須累加數量
Rule: 庫存不足的商品不得下單
```

## Bad Example
- 第一條只是主題詞，看不出驗證什麼；第二條把兩個行為接在一起。

```
Rule: 購物車
Rule: 下單必須扣庫存並清空購物車
```

# Rule 3 - Rule 拆到不能再拆 [MUST]
- 讀 Rule 底下每個 Example 的標題，若標題（或它實際驗證的事）聽起來像另一條規則，就拆成另一條 Rule；同一 Rule 底下的 Example 只能是同一規則的不同資料。
- 一個 Example 同時驗證多條規則時，拆成每條規則一個 Example：Given 與 When 相同，各自只保留屬於該規則的 Then；原本每句 Then 都恰好落在一個 Example，不遺漏。
- 行為無法分開觀察，或拆了會留下沒有意義 Then 的 Example 時，不拆。

## Good Example
- 「下單扣庫存」與「下單清空購物車」可分開觀察，拆成兩條 Rule，Then 各歸其位。

```
Rule: 下單成功必須扣減商品庫存

  @ac:003/訂單成立與付款:1-1
  Example: 下單 2 件 A100 扣減庫存
    Given "小芳" 的購物車已有 "A100" 共 2 件
    When "小芳" 下單
    Then 商品 "A100" 的庫存剩 3

Rule: 下單成功必須清空購物車

  @ac:003/訂單成立與付款:1-1
  Example: 下單 2 件 A100 後購物車清空
    Given "小芳" 的購物車已有 "A100" 共 2 件
    When "小芳" 下單
    Then "小芳" 的購物車是空的
```

## Bad Example
- 「優惠券已過期必須拒絕」聽起來就是另一條規則，卻被放在「優惠券必須折抵金額」底下。

```
Rule: 優惠券必須折抵訂單金額

  Example: NEW100 折抵 100 元
  Example: 已過期的 NEW100 被拒絕
```

# Rule 4 - Example 帶追溯 tag 且名稱同端不重複 [MUST]
- 每個 Example 與 Scenario Outline 正上方都帶至少一個追溯 tag，格式為 `@ac:<NNN>/<主題>:<Journey 序>-<檢查點序>`；NNN 為該檢查點所屬 plan 的三位數編號，主題為 acceptance 檔名去掉 `.feature`，空白改為 `_`。
- 不是由 acceptance 檢查點、而是由需求推導的 Example，追溯 tag 寫成 `@spec:<NNN>/<FR 或 NFR 編號>`，NNN 為該需求所屬 plan，例如 `@spec:003/FR-012`；修改既有需求時沿用原需求的前綴。
- 沒有 plan 前綴的追溯 tag 不合格。
- 一個 Example 驗到多個 acceptance 檢查點時，每個檢查點各帶一個追溯 tag，以空白分隔；端點 journey 另加 `@journey`。
- 追溯 tag 只放在 Example 與 Scenario Outline 正上方，不放在 Feature 或 Rule 上方（tag 會被子元素繼承）。
- 每個 Example 與 Scenario Outline 都有名稱，同一端內名稱不重複。

## Good Example
- 正上方帶有 plan 前綴的追溯 tag，驗到兩個檢查點就帶兩個；由需求推導的 Example 帶 `@spec`；名稱非空且不重複。

```
    @ac:003/購物車與運費:1-1
    Example: 已有 2 件的 A100 再加入 1 件

    @ac:003/訂單成立與付款:1-2 @ac:003/訂單成立與付款:1-3 @journey
    Example: 同一筆訂單重複送出只成立一筆

    @spec:003/FR-012
    Example: 付款失敗後收到失敗通知
```

## Bad Example
- 第一筆沒有追溯 tag 也沒有名稱；第二筆把追溯 tag 放在 Rule 上方，Rule 底下每個 Example 都繼承到同一個 tag；第三筆主題含空白，tag 會被切斷；第四筆沒有 plan 前綴，跨 plan 累積後對不到是哪個 plan 的檢查點或需求。

```
    Example:

  @ac:003/購物車與運費:1-1
  Rule: 重複加入同一商品必須累加數量

    @ac:003/LINE Pay 付款:1-1
    Example: 以 LINE Pay 付款成功

    @ac:購物車與運費:1-1 @spec:FR-012
    Example: 已有 1 件的 A100 再加入 1 件
```

# Rule 5 - Example 標題寫資料情境 [SHOULD]
- Example 名稱寫這個 Example 的資料情境（用了什麼資料、處在什麼狀況），不與所屬 Rule 同句重複。

## Good Example
- Rule 講規則，Example 標題講資料情境。

```
Rule: 庫存不足的商品不得下單

  @ac:003/訂單成立與付款:2-1
  Example: 庫存 1 件卻要買 2 件的 A100
```

## Bad Example
- Example 標題把 Rule 名稱再抄一次，看不出用了什麼資料。

```
Rule: 庫存不足的商品不得下單

  @ac:003/訂單成立與付款:2-1
  Example: 庫存不足的商品不得下單
```

# Rule 6 - 同類多列或參數超過 3 個時用 Data Table [SHOULD]
- 改用 Data Table 的情況：同一句型以不同值連續出現多列；或句型的參數超過 3 個。
- 不轉的情況：依序發生、各自獨立的使用者動作（如連續的 When）；只會重複兩次的單參數狀態句。
- 只有句型相同且前導參數（同一位會員、同一個畫面…）也相同的連續句才合併成一張表。

## Good Example
- 三種商品的庫存是同一句型連續多列，合成一張表；兩次下單是獨立動作，維持句子。

```
Given 以下商品的庫存為：
  | 商品編號 | 庫存 |
  | A100     | 5    |
  | B200     | 0    |
  | C300     | 12   |
When "小芳" 下單
And "阿德" 下單
```

## Bad Example
- 庫存句連寫三次；兩位會員各自的下單動作卻被硬塞成表。

```
Given 商品 "A100" 的庫存為 5
And 商品 "B200" 的庫存為 0
And 商品 "C300" 的庫存為 12
When 以下會員依序下單：
  | 會員暱稱 |
  | 小芳     |
  | 阿德     |
```

# Rule 7 - 影響閱讀的預設值以 `# 名稱=值` 註明 [SHOULD]
- 會影響理解的預設值，在該步驟正上方寫 `# 名稱=值`；名稱與 dsl.md 的預設參數名稱一致，值用業務用語。
- 不影響理解的預設值不註；同一 Example 只註第一次出現處；某句 Given 已明寫該值時，刪除多餘的註解。

## Good Example
- 免運門檻影響讀者理解「為什麼要付運費」，在 Then 上方註明，名稱與 dsl.md 一致。

```
      # 免運門檻="滿 1000 元"
      Then "小芳" 的訂單應付運費 80
```

## Bad Example
- 名稱與 dsl.md 不一致且用技術值；同一個值在同一 Example 註了兩次。

```
      # FREE_SHIPPING=1000
      Then "小芳" 的訂單應付運費 80
      # 免運門檻="滿 1000 元"
      And "小芳" 的訂單金額為 880
```

# Rule 8 - Given、When、Then 寫完後才判斷 Scenario Outline [MUST]
- Given、When、Then 全部寫完之前，不加 Scenario Outline 與 Examples。
- 寫完後，同一 Rule 底下只差資料的 Example 才改成 Scenario Outline；多個 Example 比一個 Outline 更明確時，維持多個 Example。
- Outline 的 `<參數>` 依型別沿用引號規則：字串寫成 `"<參數>"`，整數寫成 `<參數>`。

## Good Example
- 兩個 Example 只差購買件數與預期結果，合成一個 Outline，整數參數不加引號。

```
    @ac:003/購物車與運費:2-1 @ac:003/購物車與運費:2-2
    Scenario Outline: 一次加入 <件數> 件 A100
      Given "小芳" 的購物車是空的
      When "小芳" 把 "A100" 加入購物車 <件數> 件
      Then "小芳" 加入購物車的結果為 "<預期結果>"

      Examples:
        | 件數 | 預期結果         |
        | 10   | 成功             |
        | 11   | 超過單次購買上限 |
```

## Bad Example
- 還沒寫 Then 就先開了 Outline 與 Examples，資料欄位只能先猜。

```
    @ac:003/購物車與運費:2-1 @ac:003/購物車與運費:2-2
    Scenario Outline: 一次加入 <件數> 件 A100
      When "小芳" 把 "A100" 加入購物車 <件數> 件

      Examples:
        | 件數 |
        | 10   |
```

# Rule 9 - Background 只抽全部 Example 共用的步驟 [MUST]
- 只有 Feature 內所有 Example 都以同樣的步驟開頭時，才把那些完整步驟抽到 Feature 層級的 Background。
- 只有部分 Example 共用、或 Feature 只有一個 Example 時，不抽 Background。

## Good Example
- 檔內每個 Example 都以「會員小芳已註冊」開頭，抽成 Background。

```
Feature: 購物車

  Background:
    Given 會員 "小芳" 已註冊

  Rule: 重複加入同一商品必須累加數量
    …
  Rule: 移除商品後購物車不得留下該商品
    …
```

## Bad Example
- 「A100 庫存為 5」只有部分 Example 需要，卻被抽到 Background，其他 Example 也被迫帶著它。

```
Feature: 購物車

  Background:
    Given 會員 "小芳" 已註冊
    And 商品 "A100" 的庫存為 5
```
