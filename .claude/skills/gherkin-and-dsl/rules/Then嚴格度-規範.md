# Rule 1 - Then 寫業務結果層級 [MUST]
- 每句 Then 陳述一個完整的業務結果：後端一句一個業務事件，前端一句一個畫面上的業務事實。
- 一句業務結果的 `必查` 要涵蓋它所包含的全部 oracle 與維持不變項目。
- 只有要驗的結果本身專門在講某個細節（如金額格式、到期時刻、某段畫面文字本身就是需求）時，才另寫屬性層級的句子。

## Good Example
- 後端一句講「訂單成立」這個業務事件，金額、狀態、明細都收在它的必查裡。

```
Then "小芳" 的訂單已成立，金額為 1200
```

## Bad Example
- 把同一個業務事件拆成一欄一句，句型數暴增，PM 也看不出發生了什麼事。

```
Then 訂單狀態為 "已成立"
And 訂單金額為 1200
And 訂單會員為 "小芳"
And 訂單明細有 1 筆
```

# Rule 2 - 多位對象的同類檢查用摘要表 [SHOULD]
- 同一個 Then 要對兩位以上的對象（會員、訂單…）檢查同一種狀態時，合成一句摘要表，一列一位對象。
- 不是逐一對象的事實（如「本次促銷已結束」）維持短的結論句；只涉及一位對象時不轉表。

## Good Example
- 兩位會員的同類狀態收成一張摘要表，表外再接一句非逐一對象的結論。

```
Then 以下會員的購物車摘要如下：
  | 會員暱稱 | 商品件數 | 小計 |
  | 小芳     | 2        | 1200 |
  | 阿德     | 0        | 0    |
And 商品 "A100" 的庫存剩 3
```

## Bad Example
- 同一句型只差會員就連寫兩句。

```
Then "小芳" 的購物車有 2 件，小計 1200
And "阿德" 的購物車有 0 件，小計 0
```

# Rule 3 - 實作語意涵蓋五個通道 [MUST]
- Then 的實作語意逐一交代五個通道：`呈現結果`、`權威狀態`、`再讀確認`、`跨視角`、`不該發生`；每個通道都要列在 `必查` 或 `不必查`，不得默默省略。
- 時限與同時性寫在相關通道內（如跨視角 1 秒內、同時下單後恰一筆訂單）。
- 各通道的意義依端而定：

| 通道 | 後端 | 前端 |
|---|---|---|
| 呈現結果 | 本次操作的回應：狀態與完整形狀，不多出額外欄位 | 使用者在畫面上看到的內容與控制項狀態（可用／停用／不存在、焦點、保留的輸入） |
| 權威狀態 | 資料庫的資料列：值、筆數、關聯 | 瀏覽器外的系統事實：經後端讀到的該使用者狀態，以及頁面實際送出的請求（哪個操作、幾次、內容） |
| 再讀確認 | 該使用者重新讀取狀態，且與資料庫一致 | 重新整理或等下一次畫面更新後再讀一次 |
| 跨視角 | 另一位相關使用者讀到的狀態與此一致，必要時在時限內 | 另一位相關使用者的瀏覽器在時限內顯示同一個事實 |
| 不該發生 | 前後資料比對只有預期的變化；被拒絕的操作不改任何資料；不外洩機密 | 沒有錯誤畫面、不顯示機密或錯誤碼、不該能用的控制項真的不能用、沒有 console 錯誤與多餘請求 |

## Good Example
- 五個通道都有去向，跨視角帶時限，不必查的附原因。

```
`必查`：<br>• `呈現結果`：下單回應為成功，內容含訂單編號與金額 1200，不多出付款憑證。<br>• `權威狀態`：orders 恰新增 1 筆、金額 1200；A100 的庫存由 5 變 3。<br>• `再讀確認`：小芳重新讀取訂單清單，看到同一筆訂單且與資料庫一致。<br>• `跨視角`：阿德在 1 秒內讀到的 A100 庫存為 3。<br>• `不該發生`：除 orders、order_items、庫存與購物車外沒有其他資料變化。<br>`不必查`：無。
```

## Bad Example
- 只寫了回應，權威狀態、再讀確認、跨視角與不該發生都沒交代去向。

```
`必查`：<br>• `呈現結果`：下單回應為成功。
```

# Rule 4 - Then 實作語意依「必查／不必查／抓得到的錯誤實作」排列 [MUST]
- Then 的實作語意固定三段：`必查`（逐通道條列）、`不必查`（逐通道條列並附原因）、`抓得到的錯誤實作`。
- `不必查` 的每一項都要寫原因；沒有不必查的通道時寫「無」。

## Good Example
- 三段齊全，不必查附原因。

```
`必查`：<br>• `呈現結果`：…<br>• `權威狀態`：…<br>• `再讀確認`：…<br>• `不該發生`：…<br>`不必查`：<br>• `跨視角`：購物車只屬於小芳本人，沒有其他使用者會看到。<br>`抓得到的錯誤實作`：加入同一商品時新增一列而不是累加數量。
```

## Bad Example
- 不必查沒附原因，也沒有抓得到的錯誤實作段。

```
`必查`：<br>• `呈現結果`：…<br>• `權威狀態`：…<br>`不必查`：跨視角、再讀確認、不該發生。
```

# Rule 5 - 抓得到的錯誤實作要真的被必查抓到 [MUST]
- `抓得到的錯誤實作` 寫出這些檢查能抓到哪些具體的錯誤實作；每一項都要有某個 `必查` 通道真的會因它而失敗。

## Good Example
- 要抓「先扣庫存、付款失敗不回補」，必查的權威狀態正好比對付款失敗後庫存不變。

```
`必查`：<br>• `權威狀態`：付款失敗後 A100 的庫存仍為 5，orders 沒有新增。<br>…<br>`抓得到的錯誤實作`：先扣庫存、付款失敗後未回補，庫存變成 3。
```

## Bad Example
- 錯誤實作有寫，但必查只看回應，庫存根本沒檢查，寫了也抓不到。

```
`必查`：<br>• `呈現結果`：回應為付款失敗。<br>…<br>`抓得到的錯誤實作`：付款失敗後未回補庫存。
```

# Rule 6 - 再讀確認併入 Then [MUST]
- 「重新讀取後也看到」是同一句 Then 的 `再讀確認` 通道，不另寫「操作後看到…」與「查看時看到…」兩套句型。

## Good Example
- 一句 Then，實作語意的再讀確認負責重讀。

```
Then "小芳" 的購物車有 "A100" 共 3 件
（再讀確認：小芳重新讀取購物車，仍為 A100 共 3 件。）
```

## Bad Example
- 同一個事實寫成兩套句型，一套看回應、一套看重讀。

```
Then "小芳" 操作後看到購物車有 "A100" 共 3 件
And "小芳" 查看購物車時看到 "A100" 共 3 件
```

# Rule 7 - Given 實作語意依「怎麼做／權威狀態落地／回寫／不必查」排列 [MUST]
- `怎麼做`：狀態怎麼準備（用哪個 fixture、World 成員或操作），用文字描述。
- `權威狀態落地`：準備完後到權威處確認狀態真的存在（後端看資料庫；前端看經後端讀到的該使用者狀態，句子暗示畫面時也確認停在該畫面）；不符即讓該 Given 立即失敗。
- `回寫`：留給後續步驟用的資料（使用者身分、訂單編號、頁面、時鐘位置…）。
- `不必查`：刻意不在 Given 檢查的項目與原因。

## Good Example
- 四段齊全，權威狀態落地到資料庫確認。

```
`怎麼做`：以小芳的身分呼叫加入購物車操作兩次，商品為 A100。<br>`權威狀態落地`：cart_items 有小芳的 A100 一列、數量 2；不符即讓本步驟失敗。<br>`回寫`：會員身分表登記小芳的購物車編號。<br>`不必查`：購物車小計（屬 Then 的驗證範圍）。
```

## Bad Example
- 只說怎麼做，沒有確認狀態真的落地，準備失敗也會繼續跑到 When。

```
`怎麼做`：以小芳的身分呼叫加入購物車操作兩次。
```
