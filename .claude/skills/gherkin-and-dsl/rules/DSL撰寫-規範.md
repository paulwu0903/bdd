# Rule 1 - 預設參數寫死隱含值且只寫值 [MUST]
- 句子背後實作需要、但句子沒寫出來的值，全部寫進 `預設參數`，寫成 `• `名稱`：型別；預設為 值。`。
- 只寫值，不加解釋或理由。

## Good Example
- 運費門檻、運費與錯誤碼對照都寫死，只有值。

```
• `免運門檻`：整數；預設為 1000。<br>• `運費`：整數；預設為 80。<br>• `拒絕原因對照`：字串；預設為 庫存不足＝OUT_OF_STOCK。
```

## Bad Example
- 運費沒寫死，執行者只能猜；免運門檻後面多了一段解釋。

```
• `免運門檻`：整數；預設為 1000，因為行銷部希望提高客單價，未來可能調整。
```

# Rule 2 - 實作語意寫技術語意但不寫程式碼 [MUST]
- 實作語意用文字寫出技術上怎麼做：用哪個 fixture 或 World 成員、呼叫哪個操作或端點、讀哪張資料表、等什麼條件。
- 不寫成程式碼片段，也不只寫一句空泛的「驗證購物車正確」。

## Good Example
- 點名操作、資料表與等待條件，但是文字不是程式碼。

```
• `API 操作`：以小芳的身分呼叫 addCartItem（`POST /api/cart/items`），商品編號放入 `sku`，回應須為 201。
```

## Bad Example
- 第一筆是程式碼；第二筆空泛到推不出 step definition。

```
• `API 操作`：await world.api.post('/api/cart/items', { sku: 'A100' }); expect(res.status).toBe(201)
• `API 操作`：把商品加入購物車。
```

# Rule 3 - 前端圍繞瀏覽器與 fixture、後端圍繞 World 與 API 操作 [SHOULD]
- 前端的實作語意以瀏覽器與 BDD 框架的 fixture 為中心；後端以 World 與 API 操作為中心。
- When 的實作語意固定五個 bullet：前端為 `使用 fixture`／`Arrange 來源`／`頁面操作`／`等待條件`／`回寫資料`；後端為 `使用 World`／`Arrange 來源`／`API 操作`／`等待條件`／`回寫資料`。

## Good Example
- 前端的 When 圍繞頁面與 fixture，五個 bullet 齊全。

```
• `使用 fixture`：page、會員視角 fixture<br>• `Arrange 來源`：會員已停在商品頁<br>• `頁面操作`：依名稱找到「加入購物車」按鈕並按下<br>• `等待條件`：購物車徽章數字更新<br>• `回寫資料`：無
```

## Bad Example
- 前端的 When 寫成直接打 API，沒有任何頁面操作，測不到畫面行為。

```
• `使用 World`：API 客戶端<br>• `API 操作`：呼叫 addCartItem
```

# Rule 4 - 參考範例只取格式 [MUST]
- 參考範例（含本 skill 的 templates 範例）只借欄位、排版與寫法；句型、參數與情境一律依自己系統的規格撰寫。

## Good Example
- 自己系統的規格用「買家」「商品貨號」並以「收藏清單」為功能，借用範例的欄位與排版，句型照自己的用詞與情境寫。

```
| `{買家暱稱} 把 {商品貨號} 加入收藏清單` | … | … | 不支援 | … | … |
```

## Bad Example
- 自己系統沒有購物車功能，卻照抄範例的購物車句型與「會員暱稱」「商品編號」用詞。

```
| `{會員暱稱} 把 {商品編號} 加入購物車` | … | … | 不支援 | … | … |
```
