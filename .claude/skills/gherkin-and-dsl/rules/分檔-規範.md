# Rule 1 - 依系統功能切 feature 檔 [SHOULD]
- 各端點的 feature 檔依系統「功能」切分，同一功能的 Example 放進同一檔；不把整個端點塞進一個檔，也不一個 Example 一個檔。

## Good Example
- 後端依功能切成三個檔，每檔收同一功能的 Example。

```
features/backend/購物車.feature        @ac:購物車與運費:1-1、@ac:購物車與運費:1-2、@ac:購物車與運費:2-1
features/backend/優惠券折抵.feature    @ac:折扣疊加與互斥:1-2、@ac:折扣疊加與互斥:1-3
features/backend/下單與付款.feature    @ac:訂單成立與付款:1-1、@ac:訂單成立與付款:2-1
```

## Bad Example
- 後端所有 Example 塞進同一個檔，讀者無法從檔名找到某個功能的情境。

```
features/backend/全部.feature          @ac:購物車與運費:1-1 … @ac:訂單成立與付款:2-1
```

# Rule 2 - 檔名用繁體中文呈現受測動作或面向 [SHOULD]
- 檔名用繁體中文，讓 PM 一看就知道檔內測的是哪個動作或面向。
- 不用英文、編號或「功能一」這類看不出內容的名稱。

## Good Example
- 檔名直接說出受測的動作或面向。

```
購物車.feature
優惠券折抵.feature
庫存不足.feature
```

## Bad Example
- 英文檔名與編號式檔名都看不出測的是什麼。

```
cart.feature
功能一.feature
us2.feature
```
