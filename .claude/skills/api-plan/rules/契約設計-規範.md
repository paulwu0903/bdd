# Rule 1 - tag 名稱與後端介面一字不差 [MUST]
- plan.md 中端點類型為 `後端端點`、異動為新增或修改既有的每個介面，都要在 openapi.yaml 的 `tags` 或 asyncapi.yaml 的 `info.tags` 有一個同名 tag，名稱一字不差；修改既有的介面沿用 truth 中已有的 tag，不另立新 tag。
- 每個 operation 只掛它所屬介面的 tag；tag 的 description 寫該介面在 truth 中的完整範圍，本次的範圍併入原有內容，不覆蓋。
- 異動為刪除既有的介面，移除其 tag 與掛在該 tag 下的全部 operation。
- 共通介面（如 `後端共通介面`）沒有自己的 API 時只宣告 tag，由 `securitySchemes`、`components.parameters`、`components.responses` 與 `Error` schema 承接，不為了掛 tag 而新增 API。

## Good Example
- 新增的介面成為新 tag；修改既有的 `聊天訊息 API 介面` 沿用原 tag，description 併入本次範圍。

```
plan.md：6. `表情回應 API 介面`（新增）、7. `聊天訊息 API 介面`（修改既有）
openapi.yaml：
  - name: 表情回應 API 介面
    description: 加上、改選與移除表情回應、回應者為房間目前成員的檢查、每人每則至多一個回應
  - name: 聊天訊息 API 介面
    description: 送出訊息、發送者為房間目前成員的檢查、……、移除控制字元與字數及總量上限、10 秒 5 則的頻率限制、……
```

## Bad Example
- tag 改寫成英文；修改既有的介面整段 description 被本次範圍覆蓋，原有的頻率限制、重送去重等範圍消失。

```
openapi.yaml：
  - name: Reactions
  - name: 聊天訊息 API 介面
    description: 訊息上限 500 字
```

# Rule 2 - 行為規則寫在 description 的三段 [MUST]
- 每個 operation 的 description 依序寫「**業務規則**」條列、「**交易**」與「**對應需求**」三段，各段寫入時機如下：
    - 業務規則：有 schema 表達不了的規則時才寫
    - 交易：一次請求有兩項以上的寫入必須一起成功或一起失敗時才寫
    - 對應需求：每個 operation 都必寫
- asyncapi 的 operation 沒有交易段。
- 不用 `x-` 擴充欄位承載規則，因為 Swagger UI 的 `showExtensions` 預設為 false，`x-` 欄位不會顯示。

## Good Example
- 規則、交易與需求編號都在 description，Swagger 上直接看得到。

```yaml
description: |
  **業務規則**
  - 相同 `Idempotency-Key` 重送時回傳第一次的結果，不重複建立訂單

  **交易**：庫存檢查、庫存扣減、優惠券剩餘次數扣減、訂單建立與購物車清空在同一交易完成，任一失敗全部不生效

  **對應需求**：001/FR-008、001/FR-009、001/FR-010
```

## Bad Example
- 規則放在 `x-` 欄位，Swagger 預設畫面看不到；也沒有對應需求。

```yaml
description: 送出訂單
x-idempotent: true
x-transaction: [stock, orders, cart_items]
```

# Rule 3 - 每支 API 各自列出錯誤碼與發生情況 [MUST]
- 每個非 2xx 回應的 description 以「- `錯誤碼`：發生情況」逐條列出這支 API 在該狀態碼下可能回的全部錯誤碼。
- 多支 API 共用、發生情況相同的錯誤（如 session 缺失的 401）寫在 `components.responses`，各 API 以 `$ref` 引用。
- 錯誤本體一律用 `Error` schema，`code` 的 enum 收錄全部錯誤碼。

## Good Example
- 409 逐條列出錯誤碼與情況，共用的 401 以 `$ref` 引用。

```yaml
'401':
  $ref: '#/components/responses/SessionMissing'
'409':
  description: |
    - `CART_EMPTY`：購物車沒有任何商品
    - `OUT_OF_STOCK`：至少一項商品的數量超過目前庫存
```

## Bad Example
- 只寫狀態碼的通用說明，前端不知道會收到哪些錯誤碼；401 在每支 API 重複貼一份。

```yaml
'401':
  description: |
    - `SESSION_MISSING`：未帶 session
'409':
  description: Conflict
```

# Rule 4 - request 與 response 寫出完整 schema [MUST]
- 每個 request body、response body 與 parameter 都寫出完整的 schema：每個欄位的型別、必填、格式、範圍或 enum，以及欄位意義的 description。
- 重複出現的結構抽到 `components.schemas` 並以 `$ref` 引用。

## Good Example
- 欄位型別、必填、範圍與單位都寫明。

```yaml
CartItem:
  type: object
  required: [itemId, productId, quantity, unitPrice]
  properties:
    quantity: { type: integer, minimum: 1, maximum: 99 }
    unitPrice: { type: integer, minimum: 0, description: 新台幣，以元為單位的整數 }
```

## Bad Example
- 只寫 `type: object`，Swagger 上看不出欄位。

```yaml
CartItem:
  type: object
```

# Rule 5 - 有即時事件才產出 asyncapi，並以伺服器角度描述 [MUST]
- 後端介面需要伺服器主動推播或長連線雙向訊息時才產出 asyncapi.yaml；全部是請求與回應時不產出。
- operation 以伺服器角度寫 `action`：伺服器推播給前端為 `send`，伺服器接收前端訊息為 `receive`。
- payload 中與 HTTP API 相同意義的欄位，名稱與型別要和 openapi.yaml 的 schema 一致，並在 description 註明對應的 schema 欄位。

## Good Example
- 售完推播是伺服器送出，`itemId` 對回 openapi 的 `CartItem.itemId`。

```yaml
sendCartItemSoldOut:
  action: send
itemId:
  type: string
  description: 對應 openapi.yaml `CartItem.itemId`
```

## Bad Example
- 從前端角度把推播寫成 `receive`；欄位改名為 `cartItemId`，前端對不回購物車項目。

```yaml
receiveCartItemSoldOut:
  action: receive
cartItemId:
  type: string
```

# Rule 6 - 「交易」寫出參與的寫入與失敗處理 [SHOULD]
- 「交易」段寫出這支 API 在同一交易中完成的每一項寫入，以及任一步失敗時的處理，讓 data-plan 據此設計資料表的交易步驟與鎖定順序。

## Good Example
- 列出每一項寫入與失敗時全部不生效。

```
**交易**：庫存檢查、庫存扣減、優惠券剩餘次數扣減、訂單建立與購物車清空在同一交易完成，任一失敗全部不生效
```

## Bad Example
- 只寫「有交易」，data-plan 不知道哪些寫入要放在同一交易。

```
**交易**：有
```

# Rule 7 - 只描述現況 [MUST]
- 契約描述系統「現在」的完整行為，讀者只讀這一份就能實作；不寫「新增」「改為」「原本」「已移除」「與 NNN 的關係」「NNN 加入」這類沿革字樣。
- 沿革只寫在 plan 的 truth-delta.md 與 git 歷史。

## Good Example
- 修改後的條件直接寫成現況。

```yaml
- `CHAT_TOO_LONG`：內容處理後超過 500 個 grapheme 或 5,000 個 Unicode code point，或原始 `content` 超過 20,000 個 UTF-16 code unit
```

## Bad Example
- 描述混入沿革，讀者要自己推算現在的上限，下一次修改時也會越疊越長。

```yaml
- `CHAT_TOO_LONG`：003 起上限由原本的 200 字改為 500 字（002 的 2,000 code point 已調整）
```

# Rule 8 - 編號帶 plan 前綴，並跟著需求與決策的異動 [MUST]
- 「對應需求」與 description 中的需求、決策編號一律帶 plan 前綴：`003/FR-001`、`003/NFR-002`、`research 003/R2`；plan.md 中的裸號是本 plan 的編號，寫入時補上本 plan 的前綴。
- 被 MODIFY 的既有需求沿用原編號（例如 `002/FR-002`），不改寫成本 plan 的編號。
- 被 DELETE 的需求編號，從所有「對應需求」與 description 中移除。
- research.md 中標有 `**取代**：research NNN/Rn 的 <部分>` 的決策，契約中引用舊決策且屬於被取代部分的出處，改為引用新的決策編號，內容依新決策修改。

## Good Example
- 新需求補上本 plan 的前綴；被修改的 002/FR-002 沿用原編號；被取代的決策改引用新編號。

```yaml
**對應需求**：003/FR-001、003/FR-002、003/NFR-001
**對應需求**：002/FR-001、002/FR-002、002/FR-003
- 唯一例外是 `sendChatMessage`：……超過時回 400 `INVALID_INPUT`（research 003/R2）
```

## Bad Example
- 新需求寫成裸號，讀者不知道是哪個 plan 的 FR-001；被修改的需求改用本 plan 的新編號；research 003/R2 已取代 002/R7 的本文上限，契約仍引用舊決策。

```yaml
**對應需求**：FR-001、FR-002
**對應需求**：002/FR-001、003/FR-004、002/FR-003
- 唯一例外是 `sendChatMessage`：……超過時回 400 `INVALID_INPUT`（research 002/R7）
```

# Rule 9 - 連帶影響的掃描與範圍判定 [MUST]
- 每一項 MODIFY、DELETE 與被 `**取代**` 的決策，都要找出同一事實在契約中的每一個出處一併修改：operation 的 description 與業務規則、各錯誤回應的發生情況、`components`（schemas、parameters、responses）、`Error.code` 的 enum、tag 的 description，以及 `info.description` 的共通約定。
- 能以本次依據（spec.md 既有需求異動、本 plan 的需求、research.md 的決策）解釋的連帶修改列入清單；不能解釋的列為「超出宣告範圍」交回呼叫端，不自行修改。

## Good Example
- `002/FR-002` 由 200 字改為 500 字：錯誤條件與 schema 的上限屬於既有需求異動 #1，列入清單；500 字的原始內容可達約 20,000 個 UTF-16 code unit，超過共通約定中 `sendChatMessage` 的 16 KB 請求本文上限，且會改變 `INVALID_INPUT` 的發生條件，#1 沒有宣告，交回呼叫端。

```
MODIFY openapi.yaml › operationId sendChatMessage（CHAT_TOO_LONG 的發生條件）     ← spec.md 既有需求異動 #1
MODIFY openapi.yaml › components.schemas.SendChatMessageRequest（content 的 maxLength） ← spec.md 既有需求異動 #1
超出宣告範圍：MODIFY openapi.yaml › info（sendChatMessage 的請求本文上限 16 KB → 至少 40 KB）
```

## Bad Example
- 只改了 `CHAT_TOO_LONG` 的描述，schema 的 `maxLength` 仍是舊值；又自行把共通約定的本文上限調大，沒有經過使用者拍板。

```
MODIFY openapi.yaml › operationId sendChatMessage（CHAT_TOO_LONG 改為 500 字）
MODIFY openapi.yaml › info（請求本文上限改為 64 KB）                 ← 自行修改
（components.schemas.SendChatMessageRequest 的 maxLength 仍為 8000）
```

# Rule 10 - 契約不寫前端文案 [MUST]
- 契約只寫錯誤碼、欄位值與發生情況；使用者看到的文案歸 `specs/truth/features/frontend/`、plan 的 `ui/` 與前端程式所有，不寫進 description。
- 本次修改到的部位若有既有的文案（如「前端顯示『…』」「對應畫面文案『…』」），一併移除，不另外擴大到本次沒有修改的部位。

## Good Example
- 錯誤回應只寫錯誤碼與發生情況。

```yaml
- `CHAT_TOO_LONG`：內容處理後超過 500 個 grapheme 或 5,000 個 Unicode code point，或原始 `content` 超過 20,000 個 UTF-16 code unit
```

## Bad Example
- 錯誤回應寫了前端文案，上限改變時同一句文案散落在契約、features 與程式中，任一處漏改就互相矛盾。

```yaml
- `CHAT_TOO_LONG`：內容處理後超過 500 個 grapheme；前端顯示「訊息最多 500 字」並保留輸入框內容
```

# Rule 11 - 刪除時一併清除殘留 [MUST]
- DELETE operation 或介面時，同步清除只被它使用的部位：tag、`components`（schemas、parameters、responses）、只出現在它的錯誤回應中的 `Error.code` enum 值，以及 `info.description` 與其他 operation 描述中提到它的句子。
- 仍被其他 operation 引用的部位保留，只移除與被刪除者有關的描述。

## Good Example
- 刪除 `cancelGift` 時，只被它使用的 schema 與錯誤碼一起刪除，各自列一列 DELETE。

```
DELETE openapi.yaml › operationId cancelGift
DELETE openapi.yaml › components.schemas.CancelGiftRequest
MODIFY openapi.yaml › components.schemas.Error（移除 GIFT_NOT_CANCELLABLE）
```

## Bad Example
- 只刪除 operation，留下沒有任何引用的 schema 與錯誤碼，coverage_check 會報孤兒，前端也可能以為還有這個錯誤碼。

```
DELETE openapi.yaml › operationId cancelGift
（components.schemas.CancelGiftRequest、Error.code 的 GIFT_NOT_CANCELLABLE 仍在）
```
