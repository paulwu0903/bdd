# Rule 1 - 依 impact-audit 逐項移除並核銷 [MUST]
- `移除` 任務依 impact-audit.md 中處理任務為本任務的每一項，移除對應的 step、driver、helper、fixture、產品路由、服務函式與畫面元件。
- 回報逐項列出「已移除」或「保留」與理由（例如仍被其他未刪除的功能使用）；沒有逐項核銷不算完成。

## Good Example
- 每一項都有結果，保留的寫明原因。

```
backend/tests/bdd/modules/贈品/操作.ts:41 取消贈品 step       已移除
backend/src/routes/gift.ts:58 POST /gifts/:id/cancel            已移除
backend/src/services/gift-service.ts:120 findGrant             保留：滿額加贈仍使用
```

## Bad Example
- 只刪了路由，step 與服務函式留著，回報只寫「已移除取消功能」。

```
已移除取消功能
```

# Rule 2 - 先移除使用方，每移除一項就跑一次該端套件 [MUST]
- 依 tasks.md 的順序，先完成使用方端點的移除，再移除提供方；同一端點內一次移除一項，移除後立刻執行該端的 truth 套件，維持「除本 plan 尚未處理的異動與已知失敗外全綠」。
- 變紅時先判斷是否誤刪了仍被使用的程式，撤回後再繼續。

## Good Example
- 一次一項，每次都重跑。

```
移除 GiftCancelButton.tsx → 前端套件全綠
移除 client.cancelGift → 前端套件全綠
```

## Bad Example
- 一次刪完前後端所有檔案才跑，紅了也分不出是哪一刀造成的。

```
刪除 6 個檔案 → 前後端套件 14 個失敗
```

# Rule 3 - 以機械檢查證明移除乾淨 [MUST]
- 移除完成時，下列檢查都必須通過並附上結果：
  - 以 /bdd 的列出未使用 step 指令執行，結果為空。
  - 兩端的結構檢查指令（例如 `npm run bdd:structure`）通過。
  - 孤兒路由檢查（程式碼中有、truth 契約中沒有的路由與呼叫）沒有孤兒；檢查結果疑似誤報時，列出該路由與判斷理由。
  - 整個 truth 套件除本 plan 尚未處理的異動與已知失敗外全綠。

## Good Example
- 四項檢查都附上結果。

```
未使用 step：0
bdd:structure：backend OK、frontend OK
check_orphan_routes：0 orphan
truth 套件：backend 118 passed、frontend 71 passed（待定 3：Phase 8 尚未實作）
```

## Bad Example
- 只跑了套件全綠，殘留的路由與 step 沒有被發現。

```
truth 套件全綠 → 完成
```

# Rule 4 - DROP migration 在產品碼不再引用之後才執行 [MUST]
- 同一 DELETE Phase 中的 DROP 欄位或資料表 `基礎` 任務，必須在該 Phase 的 `移除` 任務完成、產品碼已不再引用該欄位或表之後執行。
- 執行前以搜尋確認原始碼中已沒有該欄位或表名的引用。

## Good Example
- 先確認沒有引用，再套用遷移。

```
搜尋 cancelled_at：backend/src 0 筆 → 套用 0005_drop_gift_cancel.sql
```

## Bad Example
- 先 DROP 欄位，再移除讀取它的服務，中間後端整個無法啟動。

```
套用 0005_drop_gift_cancel.sql → backend 啟動失敗：Unknown column 'cancelled_at'
```
