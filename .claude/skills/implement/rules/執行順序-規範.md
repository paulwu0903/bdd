# Rule 1 - 一次只執行一個任務 [MUST]
- 任務依序一次一個執行：同一個執行子代理以 SendMessage 接續後續任務，不為每個任務另開子代理；前一個任務交回五項回報並通過驗證、標記後，才交下一個任務。
- 執行中的任務只做該任務列的內容，不順手實作其他任務，也不把一個任務拆給多個子代理同時執行。
- 判準：每份回報只對應一個任務編號，修改的檔案都能對回該任務列的路徑或列入「任務路徑之外新增或修改的檔案」。

## Good Example
- 兩個 [P] 環境任務由同一個子代理依序完成，各自回報後才接下一個。

```
子代理 A ← T001（backend/pyproject.toml）→ 回報 T001 的五項 → 驗證通過、標記
子代理 A ← SendMessage T002（frontend/playwright.config.ts）→ 回報 T002 的五項
```

## Bad Example
- 每個任務都開新的子代理，每次重新讀規範與程式碼，拖慢整個 run；另一筆是子代理做 T001 時順手改了 T002 的檔案，一份回報混了兩個任務。

```
子代理 A ← T001 → 結束；子代理 B ← T002 → 結束；子代理 C ← T003 → 結束
子代理 A ← T001 → 同時修改 frontend/playwright.config.ts（T002 的檔案）→ 回報 T001+T002
```

# Rule 2 - 依序走完該任務的每一步，不得略過 [MUST]
- 帶 `/bdd <階段>` 標記（red、green、refactor、realign）的任務，依 bdd skill 的 SOP 從 Phase 1 走完該階段對應的 Phase，並傳入 plan 目錄。
- `盤點` 任務依序走完：讀 truth-delta 的列與靜態影響清單 → 實際閱讀每個受影響的檔案並對照基準 → 依盤點規範寫入 impact-audit.md → 自我核對完成判準 → 回報。
- `移除` 任務依序走完：讀 impact-audit 中本任務的項目 → 依移除規範一次移除一項並重跑該端套件 → 執行機械檢查 → 逐項核銷 → 回報。
- 其餘任務依序走完：讀 Must Read 部位 → 讀要 import 或修改的既有程式檔 → 實作 → 執行驗證指令 → 回讀 Why 驗收 → 五項回報。
- 任一步做不到時不得略過而進入下一步；依規範裁決或修正後補完該步，仍做不到則在回報中寫明卡在哪一步與原因。

## Good Example
- 移除任務每一步都有對應的實際動作。

```
T014 `移除` 移除會員自行取消贈品的測試與產品行為於 frontend/…
1. 讀 impact-audit › frontend 中處理任務為 T014 的 3 項
2. 移除 GiftCancelButton.tsx → 前端套件全綠；移除 client.cancelGift → 前端套件全綠
3. 未使用 step 0；bdd:structure OK；check_orphan_routes 0
4. 核銷 3 項皆已移除
5. 回報
```

## Bad Example
- 盤點任務只照抄 /tasks 的靜態清單，沒有實際閱讀檔案與對照基準。

```
T005 `盤點`
1. 把 list_changes.py 的輸出貼進 impact-audit.md
2. 回報完成
```
