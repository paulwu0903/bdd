# Rule 1 - 盤點範圍是 MODIFY、DELETE 列與使用到它們的一切 [MUST]
- 盤點涵蓋 truth-delta 中該端點的每一列 MODIFY、DELETE，以及：使用被修改或刪除句型的所有 Example（包括 truth-delta 沒有列出的）、註冊這些句型的 step、step 引用的 driver、helper、fixture、種子資料，以及實作被修改或刪除行為的產品碼。
- 只看 truth-delta 列出的 feature 不算完成盤點。

## Good Example
- 句型被修改，連帶列出使用它的另一個 feature 與 fixture。

```
### `backend/聊天訊息/dsl.md › Given › 房間 {房間代碼} 的聊天區只有 … 則訊息`（MODIFY）
| 第 9 則被拒絕 | feature | `…/發言頻率.feature:13` | 綠 | T010 |
| 對局中連續送出 | feature | `…/送出訊息與對局.feature:88` | 綠 | T010 |
| seedMessages | fixture | `backend/tests/bdd/shared/fixtures/chat.ts:14` | — | T010 |
| CHAT_RATE_LIMIT | 產品 | `backend/src/config.ts:22` | — | T011 |
```

## Bad Example
- 只列 truth-delta 寫到的 feature，同一句型的其他使用者與寫死舊門檻的 fixture 都沒列。

```
### `backend/聊天訊息/發言頻率.feature › …`（MODIFY）
| 第 9 則被拒絕 | feature | `…/發言頻率.feature:13` | 綠 | T010 |
```

# Rule 2 - 每一項寫明類型、位置、基準狀態與處理任務 [MUST]
- 每一項列出：受影響項目（Example 標題或程式符號）、類型（feature、step、helper、fixture、產品）、位置（`檔:行`）、基準狀態（取自 Phase 1 的基準：綠、紅、未定義；程式項目寫 —）、處理任務（tasks.md 的任務編號）。
- 位置必須實際讀過該檔確認，不只照抄靜態清單。

## Good Example
- 五欄齊全，位置精確到行。

```
| 取消贈品 | step | `backend/tests/bdd/modules/贈品/操作.ts:41` | — | T015 |
```

## Bad Example
- 只有檔名，沒有行號、基準狀態與處理任務，之後無法逐項核銷。

```
| 取消贈品 | backend/tests/bdd/modules/贈品/操作.ts |
```

# Rule 3 - 靜態清單之外的影響要停下回報 [MUST]
- 以實際閱讀與執行確認 /tasks 的靜態影響清單；發現清單之外、需要修改或移除的項目時，寫入「tasks.md 未涵蓋的影響」，任務回報為停止，不自行增加任務、不擴大其他任務的範圍。
- 清單中的項目經確認其實不受影響時，在該列的處理任務寫「不需處理」並說明理由。

## Good Example
- 發現一個 helper 也寫死了舊門檻，但不在任何任務的路徑中，列入未涵蓋並停止。

```
## tasks.md 未涵蓋的影響
| assertRateLimited | helper | `backend/tests/bdd/shared/asserts.ts:77` | `backend/聊天訊息/dsl.md › Given › …` | 斷言內寫死「第 6 則」 |
```

## Bad Example
- 自己把 asserts.ts 加進 T010 的範圍繼續做，tasks.md 與實際工作從此對不上。

```
（未列入未涵蓋的影響，直接在 T010 修改 backend/tests/bdd/shared/asserts.ts）
```
