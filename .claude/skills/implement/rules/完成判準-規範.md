# Rule 1 - 每批工作區三項通過，以基準判定退步 [MUST]
- 一批任務完成的判準：該批所屬工作區的型別檢查、lint 與測試通過；比較基礎是 Phase 1 的基準與已知失敗，基準中為綠、而這批之後變紅的 Example 是退步。
- 下列失敗視為待定、不計失敗：基準中已對應到本 plan truth-delta 列、且負責它的任務尚未完成的失敗；尚未執行 `/bdd red` 的 ADD feature 出現的未定義步驟；已完成 red 或 realign 但同一範疇的 `/bdd green` 尚未完成而出現的紅燈；同 Phase 內尚未執行的任務的檔案還不存在而產生的型別錯誤；已知失敗。到該 Phase 末的 Checkpoint，本 Phase 的範疇必須全綠。
- 帶 `/bdd <階段>` 標記的任務，以 bdd skill 對該任務範疇的執行結果作為該任務的驗證：red 與 realign 為範疇內每個 slice 都是合格紅燈或已確認的綠燈，green 與 refactor 為範疇全綠。

## Good Example
- 基準中被 MODIFY 的 Example 本來就紅，realign 後仍是合格紅燈，判為待定；green 後轉綠。

```
基準：發言頻率.feature:13 紅（對應 truth-delta MODIFY 列，T010–T012 負責）
批次：T010 `/bdd realign` …/發言頻率.feature:13
結果：typecheck、lint 通過；:13 紅燈（產品錯：第 6 則被拒絕）→ 待定（T011 green 尚未執行）
判定：完成
```

## Bad Example
- 基準中為綠、與本 plan 無關的 Example 在這批之後變紅，卻因為「本來就有紅燈」而當成待定。

```
基準：配對與開房.feature:20 綠
批次：T011 `/bdd green` …/發言頻率.feature:13
結果：配對與開房.feature:20 紅
判定：待定 → 繼續下一批     // 基準為綠的 Example 退步，是真失敗
```

# Rule 2 - 不改測試與輸入文件求通過；對齊 truth 的改寫例外 [MUST]
- 驗證失敗時不得修改測試的期望值、刪除斷言或跳過測試讓它通過；也不得修改 `specs/` 底下的任何輸入文件。
- 唯一例外：`/bdd realign` 與 `移除` 任務依最新 truth 改寫或刪除測試碼；每一項改寫都必須對應到 truth-delta 的某一列，並在回報中附上該列。對應不到的測試修改一律視為違反本 Rule。
- `specs/` 底下只允許兩種寫入：`盤點` 任務寫入 plan 目錄的 `impact-audit.md`，以及交付時透過 truth-delta 的「切換狀態」更新 Status。
- 測試或文件與 Must Read 部位矛盾時，依 Must Read 實作並把矛盾列入回報，不自行裁決改哪一邊。

## Good Example
- realign 修改 fixture 的門檻，附上對應的 truth-delta 列。

```
修改：backend/tests/bdd/shared/fixtures/chat.ts RATE_LIMIT 5 → 8
對應：truth-delta `backend/聊天訊息/dsl.md › Given › 房間 {房間代碼} 的聊天區只有 … 則訊息`（MODIFY）
```

## Bad Example
- green 時產品算錯，把測試的期望值改成產品目前的值；或順手修改 specs/ 裡的 feature。

```
失敗：…/發言頻率.feature:13 期望第 9 則被拒絕，實際第 6 則
處理：把 step 的期望改成第 6 則            // 沒有對應的 truth-delta 列，是遷就產品
      或修改 specs/truth/features/…/發言頻率.feature   // 修改輸入文件
```

# Rule 3 - 機械不一致照契約做並回報，設計衝突依優先序裁決 [MUST]
- 路徑、命名這類機械不一致，以 plan.md 的樹與 `specs/truth/` 的契約為準照常實作，差異列入回報。
- 會改變做什麼的設計衝突，依固定優先序自行裁決：`specs/truth/` 的契約（contracts、data）> `research.md` > `specs/truth/techstack.md` > `spec.md` > `plan.md`；裁決結果與衝突原文列入回報，不向使用者提問。
- `/bdd` 任務中 feature 檔或 dsl.md 與上述文件的衝突不在此裁決，依 bdd skill 的上游缺口判準停止並回報，由協調者終止 run。

## Good Example
- research.md 的表名與 dbml 不同屬機械不一致，照 dbml；frontend.md 與 spec.md 對空態文案不同屬設計衝突，照優先序取 frontend.md，兩者都回報。

```
機械：research.md R5 寫 purchase_orders，schema.dbml 是 Table orders → 用 orders，回報 R5
設計：frontend.md 空態文案「購物車是空的」，spec.md FR-012 寫「尚無商品」→ truth 契約優先，用「購物車是空的」，回報 FR-012 與 frontend.md 的差異
```

## Bad Example
- 碰到設計衝突停下來問使用者，或兩邊各做一半。

```
設計：同上 → 「請問文案要用哪一個？」       // 停下來問
      或 清單頁用「購物車是空的」、側欄用「尚無商品」   // 兩邊各一半
```

# Rule 4 - 只寫任務列出的路徑，repo 衛生檔例外 [SHOULD]
- 程式只寫在任務列出的路徑；Setup 任務建立的 ignore 檔與環境變數範本是固定例外。
- 其他必要的新增或修改（共用型別、輔助函式、既有檔的小改）列入回報的「任務路徑之外新增或修改的檔案」。

## Good Example
- 任務只列 cart-service.ts，實作時需要在既有 errors.ts 加一個錯誤碼，照加並回報。

```
任務路徑：backend/src/services/cart-service.ts
額外修改：backend/src/lib/errors.ts（新增 CART_ITEM_OUT_OF_STOCK）→ 列入回報
```

## Bad Example
- 額外新增了一個 utils 檔卻沒回報，plan.md 的樹與實際檔案從此對不上。

```
任務路徑：backend/src/services/cart-service.ts
額外新增：backend/src/services/cart-utils.ts → 未回報
```

# Rule 5 - Setup 任務建立一鍵驗證指令與 repo 衛生 [MUST]
- Setup 任務完成時，從程式碼根目錄能以單一指令分別執行 lint、型別檢查與測試，後續每批任務都用這些指令驗證。
- 依 techstack.md 列的工具建立或補齊 ignore 檔：git → `.gitignore`、Prettier → `.prettierignore`、ESLint flat config → `ignores`；已存在只補缺的關鍵 pattern。pattern 只列該技術堆疊與通用的，不套其他語言。
- 密鑰與連線字串只寫範本檔（如 `.env.example`），不寫實值；相依目錄、建置輸出、覆蓋率與測試結果不入庫。

## Good Example
- 根目錄一鍵指令齊全，Node 堆疊的 ignore 檔只列相關 pattern，密鑰只有範本。

```
package.json scripts: lint / typecheck / test
.gitignore:       node_modules/  dist/  coverage/  test-results/  *.log  .env*  .DS_Store
.prettierignore:  node_modules/  dist/  coverage/  package-lock.json
eslint.config.js: ignores: ["node_modules/", "dist/", "coverage/"]
backend/.env.example: DATABASE_URL=mysql://user:pass@localhost:3306/app
```

## Bad Example
- 沒有一鍵指令，每批驗證要自己拼指令；ignore 檔貼了 Python、Java 的 pattern；.env 寫了真實密碼。

```
package.json scripts: （無）
.gitignore: __pycache__/  target/  *.class  node_modules/
backend/.env: DATABASE_URL=mysql://root:MyRealPassword@...
```

# Rule 6 - 回報固定包含五項 [MUST]
- 子代理完成任務的回報固定包含：執行的驗證指令與結果、任務路徑之外新增或修改的檔案、文件未規定而自行決定的事項、發現的文件不一致與裁決、Why 驗收結果。
- 沒有內容的項目寫「無」，不省略。

## Good Example
- 五項齊全，沒有內容的寫「無」。

```
驗證：npm run typecheck ✔、npm run lint ✔、npm test -w backend ✔（31 通過）
額外檔案：backend/src/lib/errors.ts（新增 CART_ITEM_OUT_OF_STOCK）
自行決定：購物車逾時清理間隔文件未定，取 60 秒
文件不一致：無
Why 驗收：累加用 ON DUPLICATE KEY UPDATE，通過
```

## Bad Example
- 只回一句「完成」，協調者無從驗證也無從彙整當責紀錄。

```
T031 完成，測試都過。
```

# Rule 7 - 基礎與重構任務的完成判準 [MUST]
- `基礎` 任務完成的判準：遷移與測試支援能實際執行（測試資料庫套用遷移成功、每個情境開始時資料表為空），既有情境仍全綠，且沒有任何尚未進行 green 的 feature 因此由紅轉綠。
- `重構` 任務完成的判準：以任務 Why 所述的量測方式實際執行，結果達到所在 Phase Checkpoint 的門檻，且兩端全套 feature 仍全綠；量測未達門檻時重構任務路徑中的產品程式後重測，不得調低門檻或縮小負載。

## Good Example
- 基礎任務確認 red 仍會失敗；重構任務附上量測數字與門檻。

```
T005 `基礎`：migrate ✔、每情境聊天表為空 ✔、001 全綠 ✔、002 的 feature 仍為未定義步驟（沒有任何轉綠）
T070 `重構`：npm run bdd:nfr 三次中位數 p95 = 0.41 s（門檻 1 s）✔、001 延遲門檻 ✔、兩端全套 feature 全綠 ✔
```

## Bad Example
- 基礎任務順手寫了送出服務，讓下一個 red 直接綠燈；重構任務只說「已優化」，沒有量測結果。

```
T005 `基礎`：建表並完成送出 API，可見範圍與系統訊息.feature 已全綠
T070 `重構`：已優化長輪詢喚醒，應該能達標
```

# Rule 8 - 盤點任務的完成判準 [MUST]
- `盤點` 任務完成的判準：impact-audit.md 中該端點的每一項都有類型、`檔:行`、基準狀態與處理任務；truth-delta 中該端點的每一列 MODIFY、DELETE 都有一節；「tasks.md 未涵蓋的影響」為空。
- 未涵蓋的影響不為空時，任務回報為停止，由協調者終止 run 並請使用者重跑 /tasks。

## Good Example
- 每一列 truth-delta 都有一節，未涵蓋的影響為空。

```
impact-audit.md › backend：4 節（MODIFY 2、DELETE 2）、17 項，皆有位置與處理任務；未涵蓋的影響：無
判定：完成
```

## Bad Example
- 只寫了 MODIFY 的一節，DELETE 的列沒有盤點就回報完成。

```
impact-audit.md › backend：1 節（MODIFY 1）
判定：完成     // DELETE 列沒有被盤點
```

# Rule 9 - MODIFY 任務以對齊證據判定完成 [MUST]
- MODIFY Phase 的完成判準：impact-audit 中處理任務為本 Phase 的每一項（feature、step、helper、fixture）都已逐項對照最新的 truth，回報中列出「已改寫」或「已核對、不需改寫」；每個 slice 都有「預期暫時改回舊值會變紅」的證據；Phase 末的範疇全綠，整個 truth 套件除本 plan 尚未處理的異動與已知失敗外全綠。
- 只有「測試綠了」而沒有對齊證據，不算完成。

## Good Example
- 逐項核對結果與證據都附上。

```
T010 realign：前置.ts 已改寫、fixtures/chat.ts 已改寫、asserts.ts 已核對不需改寫
證據：:13 暫改回「第 6 則被拒絕」→ 紅；:88 暫改回 5 則 → 紅；皆已還原
T012 refactor 後：範疇 2 passed；truth 套件其餘全綠
```

## Bad Example
- realign 後兩個 slice 都是綠的就判為完成，沒有證明測試能分辨新舊值。

```
T010 realign：:13 綠、:88 綠 → 完成
```

# Rule 10 - 移除任務以逐項核銷與機械檢查判定完成 [MUST]
- `移除` 任務完成的判準：impact-audit 中處理任務為本任務的每一項都已核銷（已移除，或保留並說明理由），且 `rules/移除-規範.md` Rule 3 的機械檢查全部通過並附上結果。

## Good Example
- 核銷清單與四項檢查都齊全。

```
核銷 6 項：已移除 5、保留 1（findGrant 仍被滿額加贈使用）
未使用 step 0；bdd:structure OK；check_orphan_routes 0；truth 套件其餘全綠
```

## Bad Example
- 刪了檔案、套件全綠就回報完成，沒有核銷也沒有孤兒路由檢查。

```
已刪除 GiftCancelButton.tsx、gift.ts 的 cancel 路由；套件全綠 → 完成
```
