# Rule 1 - Table 名稱對應資料表介面 [MUST]
- Table 名稱與 plan.md 的資料表介面名稱去掉「 資料表介面」後一字不差；異動為新增或修改既有的每個資料表介面都要有一個 Table，修改既有的沿用 truth 中的表名，不另立新表。
- Table 的 Note 以「`<table> 資料表介面`：」開頭，後接此表在 truth 中的完整職責，本次的範圍併入原有內容。
- 異動為刪除既有的資料表介面，移除其 Table、在 TableGroup 的成員，以及指向或來自它的 Ref。

## Good Example
- plan.md 的 `cart_items 資料表介面` 對應 `Table cart_items`，Note 以介面名稱開頭。

```
Table cart_items {
  ...
  Note: '''
  `cart_items 資料表介面`：商品與數量；單價不存在此表，每次讀取以 `products.unit_price` 計算。

  **對應需求**：001/FR-003、001/FR-004、001/FR-005
  '''
}
```

## Bad Example
- 表名改成單數駝峰，與介面名稱對不上；Note 沒有以介面名稱開頭，無法反查是哪個介面；刪除既有的 `order_gifts 資料表介面` 只刪了 Table，TableGroup 成員與 Ref 仍在。

```
Table CartItem {
  ...
  Note: '購物車明細'
}

TableGroup 資料庫共通介面 {
  order_gifts
}
Ref: order_gifts.order_id > orders.id
```

# Rule 2 - 一致性規則的位置 [MUST]
- 跨表交易、冪等等牽涉多張表的一致性規則，寫在 `資料庫共通介面` TableGroup 的 Note，依規則類別分段。
- 只牽涉單一欄位的限制寫在該欄位的 note，不寫進 TableGroup。

## Good Example
- 冪等規則牽涉 `checkout_requests` 與 `orders`，寫在 TableGroup；數量範圍只關乎單一欄位，寫在欄位 note。

```
TableGroup 資料庫共通介面 {
  ...
  Note: '''
  **冪等**
  - `checkout_requests` 以 (`session_id`, `idempotency_key`) 唯一，重送時讀回第一次的 `order_id`
  '''
}

Table cart_items {
  quantity int [not null, note: '1–99']
}
```

## Bad Example
- 冪等規則寫在單一表的 Note，讀 TableGroup 的人看不到；單欄的數量範圍反而寫進 TableGroup。

```
Table checkout_requests {
  Note: '重送時讀回第一次的訂單'
}

TableGroup 資料庫共通介面 {
  Note: '''
  - cart_items.quantity 為 1–99
  '''
}
```

# Rule 3 - openapi 交易逐一落到交易步驟 [MUST]
- openapi.yaml 中 description 有「**交易**」段的每支 API，以 operationId 在 TableGroup Note 的「**交易**」段列出一條。
- 每條寫出該交易內的每個寫入、鎖定的表與順序，以及失敗時的回滾範圍。
- 交易寫入的資料在 plan.md 沒有對應的資料表介面時，不自行新增 Table，回傳給呼叫端，由使用者決定要回到 system-analysis 補盤點或改變存放位置。
- 設計資料表時發現契約需要修改（交易段寫不出來、錯誤碼缺漏、欄位與 schema 不一致），不修改 `specs/truth/contracts/`，把需要的修改回傳給呼叫端，由呼叫端重新委派 api-plan。

## Good Example
- `createOrder` 的交易提到庫存扣減、優惠券剩餘次數扣減、訂單建立與購物車清空，每個寫入都有步驟，並寫出先鎖哪張表與全部回滾。

```
**交易**
- `createOrder`：鎖定 `products` 相關列（SELECT ... FOR UPDATE）→ 檢查並扣減 `stock` → 有套用優惠券時鎖定 `coupons` 該列並將 `remaining` 減 1 → 寫入 `orders`、`order_items` → 刪除 `cart_items` → 寫入 `checkout_requests`，同一交易完成，任一失敗全部回滾
```

## Bad Example
- 只寫「同一交易」，漏了購物車清空與冪等紀錄兩個寫入，也沒有鎖定順序與回滾範圍。

```
**交易**
- `createOrder`：扣庫存並建立訂單，同一交易
```

# Rule 4 - 判斷錯誤碼的欄位標出錯誤碼 [MUST]
- openapi.yaml 的錯誤碼若由某個欄位的值判斷，在該欄位的 note 寫出判斷條件與錯誤碼。
- 由「查無資料列」判斷的錯誤碼（如 `NOT_FOUND`），標在查詢所用的主鍵或外鍵欄位。

## Good Example
- `COUPON_INVALID` 與 `COUPON_EXPIRED` 各自標在判斷它們的欄位上。

```
remaining int [not null, note: '剩餘可領用次數，0 對應 COUPON_INVALID']
expires_at datetime [not null, note: '過期對應 COUPON_EXPIRED']
```

## Bad Example
- 欄位沒有標錯誤碼，實作者不知道 `COUPON_INVALID` 要看哪個欄位。

```
remaining int [not null]
expires_at datetime [not null]
```

# Rule 5 - 欄位型別與限制 [MUST]
- 每個欄位都寫型別，型別取自 techstack.md 指定的資料庫。
- 每個欄位都寫出限制：`not null` 或 `null`、需要時的 `default` 與 `unique`，數值欄位的範圍寫在 note 或 `check`。
- `pk` 欄位本身即不可空，只寫 `pk` 即可。

## Good Example
- techstack 指定 MySQL，型別皆為 MySQL 型別；空值、預設值與範圍都有寫。

```
stock int [not null, default: 0, note: '>= 0，只在 createOrder 交易內扣減']
is_listed boolean [not null, default: true, note: 'false 表示已下架，對應 PRODUCT_UNAVAILABLE']
```

## Bad Example
- techstack 指定 MySQL，卻用了 PostgreSQL 專屬的 `timestamptz`；兩欄都沒寫是否可空、預設值與範圍。

```
updated_at timestamptz
stock int
```

# Rule 6 - 訂單類表存快照 [SHOULD]
- 之後會變動的值（價格、商品名稱等），在訂單類表存一份結帳當下的快照，不以外鍵即時讀取。

## Good Example
- `order_items` 存名稱與單價快照，商品改價後訂單內容不變。

```
Table order_items {
  product_id varchar(26) [not null, ref: > products.id]
  name varchar(100) [not null, note: '結帳當下的商品名稱快照']
  unit_price int [not null, note: '結帳當下的單價快照']
  quantity int [not null]
}
```

## Bad Example
- 只存 `product_id`，商品改價或改名後，已成立的訂單金額跟著變。

```
Table order_items {
  product_id varchar(26) [not null, ref: > products.id]
  quantity int [not null]
}
```

# Rule 7 - 只描述現況 [MUST]
- schema.dbml 描述資料表「現在」的完整定義；Note 與欄位 note 不寫「新增」「改為」「原本」「由 NNN 加入」這類沿革字樣，沿革只寫在 plan 的 truth-delta.md 與 git 歷史。
- Project Note 只寫遷移的慣例（遷移檔所在目錄、依序套用、DDL 以本檔為準），不列出個別遷移檔；遷移檔清單屬於程式的事實，由 /tasks 依 data 段產生 migration 任務。

## Good Example
- 欄位直接寫現在的上限；Project Note 只寫慣例。

```
content "varchar(20000)" [null, note: '玩家訊息的內容，處理後 1 至 500 個 grapheme']

Note: '''
- 實際 DDL 由 `backend/db/migrations/` 依檔名順序套用的遷移檔組成，內容以本檔為準
'''
```

## Bad Example
- note 混入沿革；Project Note 列出每個遷移檔與來自哪個 plan，每個 plan 都得多改一次 Project。

```
content "varchar(20000)" [null, note: '003 起由 2000 改為 20000']

Note: '''
- 實際 DDL 由 `0001_init.sql`（001 加入）、`0002_chat.sql`（002 加入）、`0003_reactions.sql`（003 加入）組成
'''
```

# Rule 8 - 編號帶 plan 前綴，並跟著需求與決策的異動 [MUST]
- 「對應需求」與 Note 中的需求、決策編號一律帶 plan 前綴：`003/FR-001`、`research 003/R2`；plan.md 中的裸號是本 plan 的編號，寫入時補上本 plan 的前綴。
- 被 MODIFY 的既有需求沿用原編號，被 DELETE 的需求編號從所有「對應需求」與 Note 中移除。
- research.md 中標有 `**取代**：research NNN/Rn 的 <部分>` 的決策，schema 中引用舊決策且屬於被取代部分的出處，改為引用新的決策編號，內容依新決策修改。

## Good Example
- 新表補上本 plan 的前綴；被修改的 002/FR-002 沿用原編號。

```
Table message_reactions { … **對應需求**：003/FR-001、003/FR-002、003/NFR-003 }
Table chat_messages     { … **對應需求**：002/FR-002、002/FR-003、002/FR-005 }
```

## Bad Example
- 新表寫成裸號；被修改的需求改用本 plan 的編號，truth 中找不到 `003/FR-004` 的定義。

```
Table message_reactions { … **對應需求**：FR-001、FR-002 }
Table chat_messages     { … **對應需求**：003/FR-004、002/FR-003 }
```

# Rule 9 - 連帶影響的掃描與範圍判定 [MUST]
- 依 truth-delta contracts 段的每一列、本次的既有需求異動與被 `**取代**` 的決策，找出 schema 中同一事實的每一個出處一併修改：
  - 由需求上限推出的欄位長度與 `check` 限制。
  - TableGroup 的成員、鎖定順序與交易段。
  - 清除作業與啟動作業涵蓋的表。
  - 欄位 note 上的錯誤碼。
- 能以本次依據解釋的連帶修改列入清單；不能解釋的列為「超出宣告範圍」交回呼叫端，不自行修改。

## Good Example
- `002/FR-002` 由 200 字改為 500 字：欄位長度、check 與欄位 note 一併修改；新增 `message_reactions` 帶出 TableGroup 成員、鎖定順序與 24 小時清除的修改。

```
MODIFY schema.dbml › Table chat_messages.content（varchar(2000) → 依 500 grapheme 的總量上限）  ← spec.md 既有需求異動 #1
MODIFY schema.dbml › Table chat_messages（chk_chat_messages_content 與 Note）                    ← spec.md 既有需求異動 #1
MODIFY schema.dbml › TableGroup 資料庫共通介面（成員、鎖定順序、表情回應交易、24 小時清除）       ← 連帶：openapi.yaml › operationId addReaction
```

## Bad Example
- 只新增了 `message_reactions`，`chat_messages.content` 仍是 `varchar(2000)`、check 仍為 2000，500 字的訊息會在資料庫層被拒絕；鎖定順序也沒有加入新表。

```
ADD schema.dbml › Table message_reactions
（Table chat_messages.content、TableGroup 資料庫共通介面 未修改）
```
