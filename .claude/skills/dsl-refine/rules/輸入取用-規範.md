# Rule 1 - 依來源的取用範圍讀取 [MUST]
- 每份上游只讀下表規定的範圍；不讀的來源一律不讀，避免把澄清前的寫法或與本步無關的內容帶進推導。

| 來源 | 取用範圍 |
|---|---|
| `features/acceptance/*.feature` | 全讀，含已澄清標籤 |
| spec.md | 只讀 FR、NFR、Success Criteria、Edge Cases 與 Assumptions；不讀 Input 原文與 User Story 敘述 |
| plan.md | 只讀「系統介面的盤點」 |
| `analysis/openapi.yaml`、`asyncapi.yaml` | 按需讀分配到的 operation、schema、錯誤碼、事件 |
| `analysis/frontend.md` | 按需讀分配到的畫面段落（四態、版面文字、欄位驗證、互動與呼叫表），不讀視覺風格 |
| `analysis/schema.dbml` | 按需讀分配到的資料表與欄位 |
| research.md | 只讀狀態存放位置、即時同步方式、時間與亂數的可控方式三類已定案決策 |
| techstack.md | 只讀測試與 BDD 框架 |
| 同一 spec package 已有的端點 feature 與 dsl.md | 全讀 |
| 其他 spec package 的 `analysis/` 契約 | 只在本 package 的契約明寫「以 <NNN> 契約為準」時，讀被指名的那幾個 operation 或畫面段落 |
| `analysis/prototype/`、test-plan.md、原始碼、其他 spec package 的其餘檔案 | 不讀 |

## Good Example
- 只讀盤點段落、三類決策與 spec 的需求條目，prototype 與 User Story 敘述不讀。

```
plan.md        → 「系統介面的盤點」
research.md    → 狀態存放、即時同步、時間與亂數可控方式
spec.md        → FR、NFR、Success Criteria、Edge Cases、Assumptions
prototype/     → 不讀
```

## Bad Example
- 讀了 prototype 的 HTML，把雛形的 class 名稱寫進實作語意；讀了 plan.md 的 Source Code 樹，在 dsl.md 裡指向原始碼檔案。

```
prototype/room.html class="chat-input" → 實作語意寫「找到 .chat-input」
plan.md Source Code → 實作語意寫「呼叫 backend/src/routes/orders.ts」
```

# Rule 2 - analysis 只讀分配到的部分 [SHOULD]
- 只讀職責分配後該端點用得到的 operation、畫面段落與資料表，不整份載入。

## Good Example
- 後端只分配到送出訂單與付款，只讀這兩個 operation 與相關資料表。

```
openapi.yaml → createOrder、payOrder 與其 schema、錯誤碼
schema.dbml  → orders、order_items、products
```

## Bad Example
- 整份 openapi.yaml 與 schema.dbml 都讀進來，含退貨、會員等完全沒分配到的部分。

```
openapi.yaml → 全部 operation
schema.dbml  → 全部資料表
```

# Rule 3 - 找不到 BDD 框架時詢問 [MUST]
- techstack.md 沒寫該端點的 BDD 框架時，停下向使用者詢問，不從 package.json 或其他檔案推測。

## Good Example
- techstack.md 只有 vitest 與 @playwright/test，沒有 BDD 框架，向使用者詢問。

```
techstack.md：vitest、@playwright/test
→ 詢問：後端與前端的 BDD 框架分別是什麼？
```

## Bad Example
- 從 package.json 看到 cucumber 就直接採用。

```
backend/package.json："bdd": "cucumber-js" → 採用 cucumber-js
```
