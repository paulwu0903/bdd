# Rule 1 - 只動本 plan 的 ADD 與受 MODIFY、DELETE 影響的內容 [MUST]
- 修改範圍只限三類：本 plan 檢查點與補充需求推出的 ADD、spec.md「既有需求異動」與 truth-delta 的 contracts、data 段 MODIFY 與 DELETE 影響到的 Example 與 dsl.md 列，以及兩者必然帶出的連帶影響。
- 範圍外的既有 Example 與 dsl.md 列一字不動：不因追不回本 plan 的檢查點而列為待刪，不補 tag，也不為了統一風格而改寫。
- 範圍內要改的內容，只改受影響的值、句子或 tag，其餘的句型、參數與實作語意保留原寫法。

## Good Example
- 003 只新增表情回應並把訊息上限由 200 改為 500；001 留下的配對 Example 雖然追不回 003 的任何檢查點，仍原樣保留；受影響的 Example 只改數值。

```
backend/配對與房間/配對與開房.feature（001）  → 不在範圍內，不動
backend/聊天訊息/訊息內容.feature「阿明送出 201 字的訊息」
  原：When "阿明" 送出一則 201 字的訊息
  改：When "阿明" 送出一則 501 字的訊息
```

## Bad Example
- 把 001、002 留下、與 003 無關的 Example 全部列為「追不回」等待刪除；又順手把受影響 Example 的句子換成另一種說法。

```
追不回（待確認是否刪除）：backend/配對與房間/配對與開房.feature 全部 12 個 Example
原：When "阿明" 送出一則 201 字的訊息
改：When "阿明" 輸入 501 個字後按下送出
```

# Rule 2 - 每個影響候選判為需修正、刪除或不受影響 [MUST]
- find_impact 列出的每個候選都要判定，並寫出一句理由：
  - 需修正：Example 或 dsl.md 列以改變的值、條件或行為作為測試意圖（驗的就是這個上限、門檻或結果）。
  - 刪除：Example 只驗被 DELETE 的需求或行為，或 dsl.md 列只被要刪除的 Example 使用。
  - 不受影響：字面值只是剛好相同的資料，與改變的規則無關；或句型的改動不改變該 Example 要驗的結果。
- 判定依的是測試意圖，不是有沒有 `@spec` tag：沒有該需求 tag、但以該上限作為測試意圖的 Example 仍需修正。

## Good Example
- 上限 200 → 500：以上限長度測版面的 Scenario Outline 需修正（tag 是 `@spec:002/NFR-008`，不是 FR-002）；`純文字呈現` 的 200 字只是資料，不受影響。

```
frontend/聊天訊息/版面.feature › … › Scenario Outline: 寬度 <寬度> px 時收到 200 字沒有空白的訊息
  → 需修正：以上限長度驗不撐出水平捲動，上限改為 500 後應測 500 字
frontend/聊天訊息/純文字呈現.feature › … › Example: 小華送出 200 字的純文字
  → 不受影響：200 字只是內容長度，驗的是純文字原樣顯示
```

## Bad Example
- 只依 tag 判定：沒有 `@spec:002/FR-002` 的版面 Scenario Outline 被判為不受影響；字面值剛好是 200 的純文字 Example 反而被改成 500。

```
版面.feature（@spec:002/NFR-008）→ 不受影響（沒有 FR-002 tag）
純文字呈現.feature 200 字 → 需修正為 500 字
```

# Rule 3 - 檢查點已被既有 Example 驗到時改寫既有 Example [MUST]
- 本 plan 的檢查點（如 acceptance 為 MODIFY 寫的新邊界與舊值對照）與某個既有 Example 驗的是同一條規則、只差數值或文字時，就地改寫該既有 Example，不另寫一個驗同一規則的新 Example。
- 只有該檢查點驗的是既有 Example 都沒驗過的規則時，才新增 Example。

## Good Example
- 003 的檢查點驗「501 字被拒絕」，與既有「阿明送出 201 字的訊息」驗同一條規則，改寫既有 Example 的值與 Rule 標題。

```
@ac:003/訊息上限調整:1-1
Rule: 超過 500 字的訊息必須被拒絕
  Example: 阿明送出 501 字的訊息
```

## Bad Example
- 保留舊的 201 字 Example，又另寫一個 501 字的 Example；舊 Example 在新上限下變成錯誤的期望。

```
Rule: 超過 200 字的訊息必須被拒絕
  Example: 阿明送出 201 字的訊息        ← 新上限下 201 字應被接受
Rule: 超過 500 字的訊息必須被拒絕
  Example: 阿明送出 501 字的訊息
```

# Rule 4 - 修改後的追溯 tag 換成現行依據 [MUST]
- 需修正的 Example 改完後，原本指向凍結 acceptance 或舊需求的追溯 tag，換成現行依據：
  - 本 plan 的 acceptance 有對應檢查點時，換成 `@ac:<本 plan 編號>/<主題>:<J>-<C>`。
  - 沒有對應檢查點時，換成 `@spec:<需求所屬 plan>/<FR 或 NFR 編號>`，編號沿用被修改需求的原前綴。
- 不保留舊 tag、不新舊並列；異動歷史由 truth-delta 的原因欄記錄。
- 判為不受影響的 Example，tag 不動。

## Good Example
- 有 003 檢查點的換成 `@ac:003/…`；沒有檢查點的版面 Scenario Outline 換成被修改需求的 `@spec`。

```
原：@ac:002/訊息內容與發言頻率:1-2     → 改：@ac:003/訊息上限調整:1-1
原：@spec:002/NFR-008（版面，200 字）   → 改：@spec:002/FR-002
```

## Bad Example
- 第一組保留指向凍結 acceptance 的舊 tag，該檢查點仍寫 200 字，tag 指向的內容與 Example 矛盾；第二組新舊並列；第三組改成本 plan 前綴的 `@spec`，requirements.md 沒有這個編號。

```
@ac:002/訊息內容與發言頻率:1-2
Example: 阿明送出 501 字的訊息

@ac:002/訊息內容與發言頻率:1-2 @ac:003/訊息上限調整:1-1

@spec:003/FR-002
```

# Rule 5 - 新句型先在整個端點找可重用者 [MUST]
- 要新增句型前，先比對同一端點全部 dsl.md 的句型欄與業務語意；有語意完全相同的既有句型就沿用，不在本次要寫的模組另定義一個近似句型。
- 只在整個端點都找不到時才新增，寫進的模組依 gherkin-and-dsl 的分檔規範決定。

## Good Example
- 表情回應需要「兩人同在房內」的前置狀態，聊天訊息模組已有同義句型，直接沿用。

```
需要：兩位玩家同在房間 4821，尚未開始
沿用：backend/聊天訊息/dsl.md › Given › {房主暱稱} 與 {對手暱稱} 都在房間 {房間代碼}，尚未開始遊戲
```

## Bad Example
- 只看了表情回應模組的 dsl.md，另定義一個同義句型，step definition 會出現兩份一樣的實作。

```
新增：backend/表情回應/dsl.md › Given › {玩家暱稱} 和 {玩家暱稱 2} 一起待在房間 {房間代碼}
```

# Rule 6 - 連帶影響一併處理，超出範圍的交給使用者決定 [MUST]
- 下列連帶影響與觸發它的異動一起處理：
  - 只被要刪除的 Example 使用的句型，一併刪除。
  - 被修改的共用句型、預設參數或實作語意，逐一確認對其他使用它的 Example 仍正確；不正確的依 Rule 2 判定。
  - 指向已刪除需求的 `@spec` tag，依 Rule 4 換成現行依據，或隨 Example 刪除。
- 連帶影響超出「既有需求異動」與本次 acceptance 的範圍時（例如要改到另一條沒有宣告異動的需求所驗的 Example），不自行修改，列入交給 clarify 的清單，由使用者決定。

## Good Example
- 拒絕句型的預設參數「拒絕原因對照」改為 500 字，確認其他使用它的 Example 都仍正確；發現發言頻率的 Example 也用同一句型，但拒絕原因不同，不受影響。

```
MODIFY backend/聊天訊息/dsl.md › Then › {玩家暱稱} 送出的訊息因 {拒絕原因} 被拒絕，沒有任何改變
  拒絕原因對照：訊息最多 200 字＝CHAT_TOO_LONG → 訊息最多 500 字＝CHAT_TOO_LONG
  使用者：訊息內容.feature「阿明送出 501 字的訊息」→ 已一併修正
          發言頻率.feature「第 2 輪阿明 10 秒內第 6 次發言」→ 不受影響：拒絕原因為發言太頻繁
```

## Bad Example
- 刪了 Example 卻留下只被它使用的句型，gate 報 V4；又順手修改了沒有宣告異動的發言頻率門檻。

```
DELETE backend/聊天訊息/取消訊息.feature（句型 `{玩家暱稱} 收回訊息 {內容}` 留在 dsl.md）
MODIFY backend/聊天訊息/發言頻率.feature 10 秒 5 則 → 10 秒 8 則   ← 不在既有需求異動內
```
