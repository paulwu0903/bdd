# Rule 1 - 檢查點依職責拆給每個有實作職責的端點 [MUST]
- 一個檢查點裡，每個端點各自要實作的部分是一段「職責段」；每個有職責段的端點都分到這個檢查點，各端只驗自己那一段。
- 不把整個檢查點原樣複製給每個端點，也不只挑一個端點負責。

## Good Example
- 〈訂單成立與付款〉第 1 條 Journey 的檢查點 1：後端負責建立待付款訂單並扣可售數量，前端負責畫面顯示待付款，各拿自己那一段。

```
@ac:訂單成立與付款:1-1
  When "小芳" 送出訂單
  Then "小芳" 的訂單狀態為 "待付款"
  And "無線耳機" 的可售數量為 9

backend  ← 建立狀態為待付款的訂單；可售數量由 10 變 9
frontend ← 送出後畫面顯示訂單狀態「待付款」
```

## Bad Example
- 第一組把整個檢查點原樣投影給兩端，前端也要驗可售數量的資料列；第二組只分給後端，前端沒有任何 Example 驗到「顯示待付款」。

```
backend  ← 待付款、可售數量 9
frontend ← 待付款、可售數量 9（直接讀資料庫比對）

backend  ← 待付款、可售數量 9
frontend ← （無）
```

# Rule 2 - 職責歸屬依 plan.md 的主要介面判定，不得藉此新增情境 [MUST]
- 判斷某段職責屬於哪個端點時，看 plan.md「系統介面的盤點」中各介面的 `端點類型` 與 `主要介面`。
- 主要介面只用來決定歸屬；主要介面列了、但沒有任何 acceptance 檢查點寫到的行為，不得因此寫成 Example。

## Good Example
- 「扣可售數量」寫在後端的訂單 API 介面的主要介面裡，所以這段歸後端。

```
plan.md：`訂單 API 介面`（後端端點）主要介面：建立訂單、保留可售數量、保留逾時取消
@ac:訂單成立與付款:1-1 的「可售數量為 9」 → backend
```

## Bad Example
- 主要介面列了「付款重試次數上限」，acceptance 沒有任何檢查點寫到上限，卻新增了一個 Example。

```
plan.md：`付款 API 介面` 主要介面：付款受理、付款重試次數上限
backend 新增：Example: 第 4 次重試付款被拒絕   ← 沒有對應的 acceptance 檢查點
```

# Rule 3 - 依有觀察面的端點類型產出端點目錄 [MUST]
- plan.md 中每一種有自己觀察面的端點類型產出一個端點目錄：`前端端點` → `features/frontend/`，`後端端點` → `features/backend/`。
- 資料庫、檔案儲存這類被動儲存不另開目錄，而是寫入它的那個端點在 Then 的權威狀態通道。
- 出現 gherkin-and-dsl skill 尚未定義五通道的端點類型（如手機、硬體、第三方）時，停下向使用者詢問，不自行定義。

## Good Example
- 三種端點類型只產出兩個目錄，資料庫端點併入後端的權威狀態。

```
plan.md 端點類型：前端端點、後端端點、資料庫端點
產出：features/frontend/、features/backend/
orders、products 資料表 → backend Then 的 `權威狀態`
```

## Bad Example
- 為資料庫另開目錄；手機端點沒有五通道定義，卻自己編了一套。

```
產出：features/frontend/、features/backend/、features/database/
產出：features/mobile/（自訂通道：推播結果、離線快取…）
```

# Rule 4 - 既有功能的檢查點依 acceptance Rule 的不變條件歸屬 [MUST]
- 檢查點驗的是先前 spec package 已實作的行為（如訂單付款成功、扣減庫存），本次 plan.md 沒有任何主要介面負責它時，看該檢查點所屬 acceptance Rule 的不變條件（如「加贈贈品不得改變訂單金額與付款流程」），把它歸給主要介面負責該不變條件的端點，寫成「本次功能發生後，既有行為照常」的 Example。
- 既有行為本身的細節（如付款方式的各種失敗情形）不另外展開，只驗該檢查點寫到的結果。

## Good Example
- 「訂單付款成功」是先前訂單功能的行為；本次滿額贈品的 Rule 要求加贈不改變付款流程，`贈品 API 介面` 的主要介面有「加贈不改變訂單金額與狀態」，因此歸後端，Given 帶入已加贈的贈品。

```
@ac:滿額贈品與條件:1-2
Rule: 訂單附贈品後，付款成功必須照常成立訂單
  Given "小芳" 有一筆附贈 "運動水壺" 的待付款訂單，金額為 2650
  When "小芳" 以 "信用卡" 付款成功
  Then "小芳" 的訂單為已付款
```

## Bad Example
- 因為找不到負責的主要介面就不分配，check_trace 回報未覆蓋；或反過來把整套付款規則（額度不足、逾時取消）都重寫一次。

```
@ac:滿額贈品與條件:1-2 → （無端點）
@ac:滿額贈品與條件:1-2 → backend：Rule 額度不足時付款失敗、Rule 逾時未付款取消訂單…
```
