# Rule 1 - 逐檢查點、逐端點比對七個面向 [MUST]
- 每個檢查點的每個職責段，都依下表逐項確認被該端的 Example 覆蓋：

| 檢查點面向 | 對到哪裡 | 合格條件 |
|---|---|---|
| 前置步驟（含 Background） | Given | 折疊後的每個狀態元素都有建立，值相同 |
| When 段 | When | 行動者、值、先後或同時關係相同 |
| Then 段中屬於該端的結果 | Then 的 `必查` | 對象、值或文字、時限都對 |
| 「仍為／仍有／沒有」句 | 某句 Then 的 `必查` | 每一項都被驗到 |
| 規則可能的錯誤實作 | 該 Then 的 `抓得到的錯誤實作` | 有列出，且必查真的抓得到 |
| 屬於其他端點的結果 | 該 Then 的 `不必查` | 不斷言，並註明屬哪個端點 |
| 數值 | 步驟、表格、註解中的每個字面值 | 與 acceptance 一致，畫面文字逐字相同（含全形標點） |

## Good Example
- 一個職責段的七個面向逐項打勾。

```
@ac:003/訂單成立與付款:3-2（backend）
前置：小美的訂單已取消、可售數量 10        → Given 兩句 ✔
When：小美對已取消的訂單再次付款          → When ✔
結果：付款因訂單已取消被拒絕              → 必查・呈現結果 ✔
維持不變：訂單仍為已取消                  → 必查・權威狀態 ✔
錯誤實作：取消後仍受理付款                → 抓得到的錯誤實作 ✔
他端：畫面上的拒絕文案                    → 不必查（屬 frontend）✔
數值：10                                  → 一致 ✔
```

## Bad Example
- 只核對了結果，維持不變與數值沒有比對，可售數量寫成 9 也沒發現。

```
@ac:003/訂單成立與付款:3-2（backend）
結果：付款因訂單已取消被拒絕              → Then ✔
（Given 寫成：可售數量為 9）
```

# Rule 2 - 句子連同 dsl.md 一起讀 [MUST]
- 判斷某項是否被覆蓋時，把步驟文字、對應 dsl.md 那一列的參數、預設參數與實作語意，以及步驟上方的 `# 名稱=值` 註解一起讀；只看句子不算覆蓋。

## Good Example
- 句子沒寫「訂單仍為已取消」，但對應那一列的必查・權威狀態有寫，算覆蓋。

```
Then "小美" 的 "付款" 因 "訂單已取消" 被拒絕，沒有任何改變
dsl.md 必查・權威狀態：orders 該筆仍為 cancelled，products 可售數量不變。 → 維持不變 ✔
```

## Bad Example
- 只看句子就判定「沒有任何改變」已覆蓋，沒發現那一列的必查只檢查了回應。

```
Then "小美" 的 "付款" 因 "訂單已取消" 被拒絕，沒有任何改變
dsl.md 必查：• `呈現結果`：回應為拒絕。 → 判為維持不變 ✔（錯）
```

# Rule 3 - 每個端點 Example 都追得回且不多驗 [MUST]
- 反方向逐一檢查每個端點 Example：它的追溯 tag 指向的檢查點，真的含有它所驗的每一項；驗到檢查點沒有的行為就是多寫。

## Good Example
- Example 驗的兩項都在檢查點 1-1 裡。

```
@ac:003/訂單成立與付款:1-1（backend）
驗：待付款、可售數量 9   ← 檢查點 1-1 都有 ✔
```

## Bad Example
- 同一個 Example 多驗了「寄出訂單確認信」，檢查點 1-1 沒有這一項。

```
@ac:003/訂單成立與付款:1-1（backend）
驗：待付款、可售數量 9、寄出訂單確認信   ← 第三項不在檢查點內 ✘
```

# Rule 4 - 有落差就直接修正，只補 acceptance 與 spec 要求的內容 [MUST]
- 找到缺漏或不一致時直接修正 feature 與 dsl.md；需要的新句型先寫進 dsl.md 再用。
- 改的是多個 Example 共用的 dsl.md 列時，確認修正後對所有使用它的 Example 都仍正確。
- 只補 acceptance 與 spec 要求的內容，不加兩者都沒有的行為。

## Good Example
- 共用的拒絕句型補上可售數量不變的檢查，並確認其他使用它的 Example 仍成立。

```
落差：@ac:003/訂單成立與付款:3-2 的可售數量不變沒被驗到
修正：拒絕句型的必查・權威狀態補上「products 可售數量與操作前相同」
確認：其他使用此句型的 Example 也都不該改動可售數量 ✔
```

## Bad Example
- 只回報落差沒有修正，又順手加了 acceptance 與 spec 都沒有的「寄送取消通知信」。

```
落差：@ac:003/訂單成立與付款:3-2 的可售數量不變沒被驗到 → 已列入回報
另加：Then "小美" 收到訂單取消通知信
```

# Rule 5 - 本 plan 的每條 FR、NFR 與 MODIFY 需求都要有去向 [MUST]
- 逐條列出本 plan spec.md 的 FR 與 NFR，以及「既有需求異動」中 MODIFY 的既有編號，每一條都必須落在三種去向之一：被某個 acceptance 檢查點涵蓋（寫出是哪個檢查點）、被某個 `@spec` Example 涵蓋，或列為純量測需求。
- 範圍只限本 plan；先前 plan 的需求不在本步稽核。
- 找不到去向的，依 `rules/規格補充-規範.md` 補寫後再稽核一次。

## Good Example
- 新需求與 MODIFY 的需求都寫出去向。

```
FR-001      → @ac:003/訂單成立與付款:1-1、1-2
FR-012      → @spec:003/FR-012（backend、frontend）
NFR-002     → 純量測需求（1000 人結帳 p95）
002/FR-004  → @ac:003/退貨與退款:1-2（既有需求異動 #1）
```

## Bad Example
- 只核對 acceptance 檢查點與新需求，FR-012 沒有去向，MODIFY 的 002/FR-004 也沒有被任何 Example 驗到新的 10 天期限，稽核卻判定完成；又把 001 的需求全列進來要求補 Example。

```
24 個檢查點全部覆蓋 → 稽核完成
（FR-012 付款失敗通知 → 無去向）
（002/FR-004 退貨期限改為 10 天 → 無去向）
001/FR-003 → 要求補寫 @spec:001/FR-003
```

# Rule 6 - 既有需求異動的每一條都有落點 [MUST]
- spec.md「既有需求異動」的每一列，都在回報中寫出落點：改了或刪了哪些 Example 與句型（以 truth-delta features 段的部位表示），或寫明 features 沒有受影響的理由。
- 判定為不受影響的候選，也要列出理由，讓使用者能核對沒有漏改。

## Good Example
- MODIFY 與 DELETE 各有落點，沒受影響的寫出理由。

```
#1 MODIFY 002/FR-002 訊息上限 200 → 500 字
   → MODIFY backend/聊天訊息/訊息內容.feature › Rule: 超過 500 字的訊息必須被拒絕 › Example: 阿明送出 501 字的訊息
   → MODIFY backend/聊天訊息/dsl.md › Then › {玩家暱稱} 送出的訊息因 {拒絕原因} 被拒絕，沒有任何改變（拒絕原因對照）
   → 不受影響 frontend/聊天訊息/純文字呈現.feature：200 字只是資料，與上限無關
#2 DELETE 002/FR-011 → features 不受影響：該需求只有純量測去向，沒有 Example
```

## Bad Example
- 只寫「已依既有需求異動修正」，看不出改了哪些 Example，也看不出版面的 200 字 Scenario Outline 是否檢查過。

```
#1 MODIFY 002/FR-002 → 已修正
#2 DELETE 002/FR-011 → （未提）
```
