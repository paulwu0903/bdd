# Rule 1 - 既有內容分成四類 [MUST]
- 端點目錄已有的每個 Example 與 dsl.md 列，依下表分類並處理：

| 分類 | 判定條件 | 處理 |
|---|---|---|
| 有效 | 追得回某個檢查點，行為與數值都與 acceptance 一致 | 保留 |
| 需修正 | 追得回，但行為、數值或畫面文字與 acceptance 不一致 | 依 acceptance 修正 |
| 缺漏 | 檢查點有該端的職責段，卻沒有任何 Example 驗到 | 補齊，句型優先沿用既有 dsl.md |
| 追不回 | 找不到任何對應的檢查點 | 列清單，使用者確認後才刪除 |

## Good Example
- 四種情況各歸一類。

```
Example「送出訂單後可售數量剩 9」      → 有效
Example「逾時 10 分鐘取消」（應為 16） → 需修正
@ac:訂單成立與付款:3-2 後端無 Example  → 缺漏
Example「訂單可改收件地址」            → 追不回
```

## Bad Example
- 只分「保留」與「重寫」，數值錯誤的 Example 被當成有效保留，追不回的被歸成需修正後改寫成別的情境。

```
Example「逾時 10 分鐘取消」 → 保留
Example「訂單可改收件地址」 → 改寫成「訂單可取消」
```

# Rule 2 - 有效內容保留原寫法 [MUST]
- 有效的 Example 與 dsl.md 列保留原本的句型、參數與實作語意，只補追溯 tag 與 gherkin-and-dsl 標準要求的格式修正，不為了統一風格而重寫。

## Good Example
- 只在原 Example 上方補追溯 tag，句子不動。

```
    @ac:訂單成立與付款:1-1
    Example: 購物車有 1 件無線耳機時送出訂單
      When "小芳" 送出訂單
```

## Bad Example
- 原句型有效，卻改成另一種說法，dsl.md 也跟著多出近似句型。

```
原：When "小芳" 送出訂單
改：When "小芳" 下了一筆訂單
```

# Rule 3 - 追不回的內容不刪，列清單待確認 [MUST]
- 追不回的 Example 與只被它們使用的 dsl.md 列，原樣留在檔案中，在回報中逐項列出檔案與名稱，經使用者確認後才刪除。

## Good Example
- 保留原檔，回報中列出待確認項目。

```
回報：追不回（待確認是否刪除）：
- features/backend/訂單.feature「訂單可改收件地址」
- dsl.md When 句型 `{會員暱稱} 修改 {訂單} 的收件地址`
```

## Bad Example
- 未經確認直接刪除，repository 不在 git 下，刪了就無法復原。

```
已刪除 features/backend/訂單.feature「訂單可改收件地址」
```
