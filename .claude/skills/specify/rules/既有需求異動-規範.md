# Rule 1 - 改變現行需求結果的要求判為修改，不另立新需求 [MUST]
- 要求與現行需求針對同一個行為、門檻或對象，而且會讓該需求描述的結果改變時，判為修改該條既有需求，列入既有需求異動。
- 本次 spec 不得再寫一條與現行需求重複或矛盾的新 FR、NFR、SC；同一件事在 truth 中只能有一條有效的需求。

## Good Example
- 「訊息上限改成 500 字」與 002/FR-002 的 200 字上限是同一個門檻，判為修改。

```
功能描述：「把訊息上限從 200 字改成 500 字」
現行需求：002/FR-002 訊息 … MUST 為 1 至 200 字元 …
→ 既有需求異動 #1：MODIFY `002/FR-002`
```

## Bad Example
- 在本次 spec 另寫一條 500 字的新需求，truth 中同時存在 200 字與 500 字兩條有效需求。

```
→ FR-004：訊息 MUST 為 1 至 500 字元
（002/FR-002 仍寫 200 字，未列入既有需求異動）
```

# Rule 2 - 使現行需求不再成立的要求判為刪除，含隱含失效 [MUST]
- 使用者明說要拿掉的功能或限制，判為刪除對應的既有需求。
- 使用者沒有明說，但新要求實作後既有需求必然不再成立時，也要列入：整條失效判為刪除；只有部分失效判為修改，新內容寫出仍成立的部分。
- 判定時逐條掃描與功能描述相關的現行需求，不只比對使用者點名的編號。

## Good Example
- 新增「對局中也能靜音」後，002/FR-012 的「房內有對手時才能靜音」仍成立，不列；新增「結果畫面可繼續聊天」使 002/FR-006 的「MUST NOT 提供聊天輸入」部分失效，判為修改。

```
功能描述：「對局結束後，雙方可以在結果畫面繼續聊天 3 分鐘」
→ 既有需求異動 #1：MODIFY `002/FR-006`
   新內容：對局結束時，結果畫面 MUST 顯示本局完整聊天紀錄，並在結束後 3 分鐘內 MUST 提供聊天輸入；…
```

## Bad Example
- 只新增結果畫面的聊天需求，沒發現 002/FR-006 禁止結果畫面輸入，兩條需求互相矛盾。

```
→ FR-001：結果畫面 MUST 在對局結束後 3 分鐘內提供聊天輸入
（002/FR-006「MUST NOT 提供聊天輸入」未列入既有需求異動）
```

# Rule 3 - 修改的新內容寫成完整條文並沿用原編號 [MUST]
- 新內容寫成修改後的完整需求條文，依需求歸屬規範寫成可測試的 MUST 單句；不寫「改為 500 字」這類差異描述。
- 既有編號維持原 plan 前綴與原編號，不改用本次 spec 的新編號。

## Good Example
- 新內容可直接取代原條文，編號不變。

```
| 1 | MODIFY | `002/FR-002` | 訊息先移除控制字元與雙向控制字元、再去除頭尾空白後 MUST 為 1 至 500 字元，可包含 emoji（每個 emoji 計為 1 字元）；… 超過 500 字元時 MUST 被拒絕並提示「訊息最多 500 字」，且 MUST 保留輸入框內容。 | 使用者要求放寬訊息長度 | 使用者於 2026-11-10 確認 |
```

## Bad Example
- 新內容只寫差異，同步後 truth 中的條文只剩一句「上限改為 500 字」；編號還改成本次的新編號。

```
| 1 | MODIFY | `003/FR-002` | 上限改為 500 字 | 放寬 | 使用者於 2026-11-10 確認 |
```

# Rule 4 - 不改變現行需求結果的補充判為新增 [MUST]
- 要求在現行需求之外增加新的行為或約束，而且所有現行需求的結果都不變時，判為新增，寫成本次 spec 的新 FR、NFR、SC，不列入既有需求異動。
- 新需求需要引用現行需求時，寫出帶 plan 前綴的編號（例如 `002/FR-001`）。

## Good Example
- 表情回應是新行為，不改變任何訊息規則，判為新增，並引用既有需求的前提。

```
功能描述：「可以對訊息按 👍、❤️、😂」
→ FR-001：依 002/FR-001 可送出訊息的玩家 MUST 能對任一則訊息按 👍、❤️、😂 其中之一
```

## Bad Example
- 新行為沒有改變任何既有需求，卻把相關的既有需求都列成修改，造成不必要的確認與下游對齊工作。

```
→ 既有需求異動 #1：MODIFY `002/FR-003`（訊息顯示加上表情）
→ 既有需求異動 #2：MODIFY `002/FR-009`（四態加上表情）
```
