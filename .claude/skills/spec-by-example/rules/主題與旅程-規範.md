# Rule 1 - 一個主題是一個大情境，寫成一個 feature 檔 [MUST]
- 主題取自 spec.md 中能獨立 demo 的一個大情境（如「折扣疊加與互斥」「退貨與退款」），一個主題只寫一個 feature 檔，檔名即主題名。
- 一個檔案只講一個大情境，review 時讀完一檔就能判斷這個情境的驗收標準是否正確；不把多個大情境塞進同一檔，也不把同一個大情境拆到多個檔。
- 主題依 FR 中的業務能力與規則群組切分，不依 User Story 的數量切分；不為了湊足主題數而拆開同一個大情境。

## Good Example
- 電商範例整組切成 6 個主題，每檔一個大情境；完整檔案見 `templates/acceptance.example.feature`（折扣疊加與互斥）與 `templates/電商範例/features/` 下其餘 5 檔。

```
features/acceptance/
  折扣疊加與互斥.feature    會員折扣、折扣碼與運費優惠依序疊加，互斥折扣碼被拒絕
  運費分區與免運.feature    運費依收件地區與免運門檻重算，不配送地區不得結帳
  滿額贈品與條件.feature    達門檻附贈品、贈品送完照常成立、退貨後處理贈品
  庫存預留與超賣.feature    搶購時預留不超賣、逾時未付款釋出名額
  訂單成立與付款.feature    待付款、付款成功才成立、失敗重試、逾時取消
  退貨與退款.feature        退貨期限內依折扣比例退款並回補庫存
```

## Bad Example
- 折扣、運費與退貨三個大情境擠在同一檔，review 時得讀完整檔才能判斷任何一個情境；付款又被拆成兩檔，同一個大情境要對照兩份才看得完整。

```
features/acceptance/
  電商結帳.feature          折扣疊加、運費分區、退貨退款全部寫在一起
  信用卡付款.feature
  LINE Pay 付款.feature
```

# Rule 2 - Journey 是 demo 時要走的關鍵主流程加少數變化情境 [MUST]
- 每個 Example 是一條較長的 Journey：從一個確定狀態出發，依序走完 demo 時會操作的多個動作，中途以 Then 檢查結果。
- 一個主題先寫一條關鍵主流程，再挑少數與主流程走向不同的變化情境（失敗、拒絕、逾時、門檻未達）；不為每個資料組合或單一動作各寫一個短 Example。

## Good Example
- 〈訂單成立與付款〉一條主流程走到出貨，再加兩條走向不同的變化情境：失敗後重試成功、失敗後逾時取消。

```
Example: 會員下單後以信用卡付款成功，訂單一路走到出貨
Example: 第一次付款失敗，在保留時間內改用 LINE Pay 付款成功
Example: 付款失敗後超過保留時間，訂單自動取消並釋放庫存
```

## Bad Example
- 每個 Example 只驗一個動作或一種資料，像單元測試切片，PM 無法從中看出 demo 要怎麼走。

```
Example: 送出訂單後狀態為待付款
Example: 信用卡付款成功
Example: LINE Pay 付款成功
Example: 付款成功後狀態為已付款
Example: 出貨後狀態為已出貨
```

# Rule 3 - 每檔 1～3 個 Journey，整組 1～8 個 feature [MUST]
- 每個 feature 檔寫 1～3 個 Example；整組 `features/acceptance/` 為 1～8 個 feature 檔，最多 8 個。
- 依業務能力切出幾個主題就寫幾檔；5～8 檔只是全新產品第一份 plan 的建議規模，增量 plan 只有 1～2 個主題時照實寫，不拆檔湊數。
- 變化情境多於 3 個時，只留走向最不同、最值得 demo 的幾個；主題多於 8 個時，合併相近的大情境。

## Good Example
- 電商範例 6 檔，每檔 2～3 個 Journey，共 14 個；另一份增量 plan 只加了表情回應並放寬訊息上限，切出 2 個主題，照實寫 2 檔。

```
| 主題           | Journey 數 |
| 折扣疊加與互斥 | 2          |
| 運費分區與免運 | 2          |
| 滿額贈品與條件 | 2          |
| 庫存預留與超賣 | 3          |
| 訂單成立與付款 | 3          |
| 退貨與退款     | 2          |
```

```
features/acceptance/
  對訊息按表情回應.feature
  訊息長度上限.feature
```

## Bad Example
- 〈退貨與退款〉把每種付款方式與折扣組合都寫成 Journey，一檔 6 個，review 時抓不到重點；另一份增量 plan 只有 1 個業務能力，卻把〈對訊息按表情回應〉拆成「對局中按表情」「結果畫面按表情」「取消表情」湊到 3 檔。

```
Feature: 退貨與退款
  Example: 信用卡訂單部分退貨
  Example: LINE Pay 訂單部分退貨
  Example: 使用折扣碼的訂單部分退貨
  Example: 使用會員折扣的訂單部分退貨
  Example: 整筆退貨
  Example: 超過退貨期限的申請被拒絕
```

# Rule 4 - 前置操作以 Given 帶過，不展開 [MUST]
- 註冊、登入、瀏覽商品、加入購物車等不在本主題驗收範圍內的前置操作，以一句 Given 描述它造成的狀態，不寫成一連串 When。
- When 只寫本主題要驗收的動作。

## Good Example
- 〈訂單成立與付款〉要驗的是下單與付款，購物車內容以 Given 帶過。

```
Given "小芳" 的購物車中有 "無線耳機" 1 件
When "小芳" 送出訂單
Then "小芳" 的訂單狀態為 "待付款"
```

## Bad Example
- 註冊、登入、搜尋與加入購物車都被展開成 When，真正要驗收的下單被埋在後面。

```
When "小芳" 註冊會員
And "小芳" 登入
And "小芳" 搜尋 "無線耳機"
And "小芳" 把 "無線耳機" 加入購物車
And "小芳" 送出訂單
Then "小芳" 的訂單狀態為 "待付款"
```

# Rule 5 - 只有 PM 能在 demo 中觀察到的 NFR 才寫成 Journey 檢查點 [MUST]
- spec.md 的 NFR 與 Success Criteria 中，行為能在 demo 時被 PM 直接看到的（如「1 秒內雙方同時看到結果」「斷線 60 秒內恢復」），寫成相關 Journey 中的 Then 檢查點。
- 需要工具量測的 NFR（效能量測、覆蓋率、無障礙掃描、資料外洩檢查等）留給之後的 /dsl-refine 判定，不寫成 Journey，也不另開主題。

## Good Example
- 「付款成功後 3 秒內會員收到確認通知」是 demo 時看得到的行為，寫進〈訂單成立與付款〉主流程的檢查點；「結帳 API p95 小於 300ms」留給 /dsl-refine 判定。

```
      When "小芳" 以 "信用卡" 付款成功
      Then "小芳" 的訂單狀態為 "已付款"
      And "小芳" 在 3 秒內收到訂單確認通知，金額為 2990
```

## Bad Example
- 把量測型 NFR 寫成 Journey，PM 在 demo 中無從判斷是否通過。

```
    Example: 結帳頁效能與無障礙符合標準
      When 以 1000 位會員同時進行結帳
      Then 結帳的 p95 回應時間小於 300 毫秒
      And 結帳頁通過無障礙掃描
```

# Rule 6 - PM 看得到的 MODIFY 寫成 Journey 檢查點，DELETE 不寫 [MUST]
- spec.md 既有需求異動中的每個 MODIFY，只要改變的行為能在 demo 中被 PM 直接看到，就必須寫進本次某條 Journey 的檢查點：同時驗新邊界（例如 500 字可送出、501 字被拒），並至少一個舊規則下結果不同的值（例如舊上限 200 時會被拒的 201 字），讓 PM 看得出改了什麼。
- 需要工具量測才看得到的 MODIFY 依 Rule 5 不寫成 Journey。
- DELETE 不寫 Journey，也不寫「不再能 …」的檢查點，只在回報中列出。

## Good Example
- 既有需求異動 #1 把 002/FR-002 的上限從 200 字改為 500 字，Journey 同時驗舊規則下會被拒的值與新邊界。

```
  Example: 小芳送出超過舊上限的長訊息成功，超過 500 字被拒
    Given "小芳" 與 "阿哲" 在同一房間對局中
    When "小芳" 送出 201 字的訊息
    Then "阿哲" 看到這則 201 字的訊息
    When "小芳" 送出 500 字的訊息
    Then "阿哲" 看到這則 500 字的訊息
    When "小芳" 送出 501 字的訊息
    Then 系統拒絕，提示 "訊息最多 500 字"
    And "小芳" 的輸入框仍保留這 501 字
```

## Bad Example
- 500 字上限沒有任何檢查點，/dsl-refine 修改 truth 中 200 字的 Example 時找不到本次驗收可以依據；被刪除的 002/FR-012 反而寫成一條 Journey。

```
（既有需求異動 #1 MODIFY 002/FR-002 未出現在任何 Journey）
  Example: 房內不再能靜音對手
    When "小芳" 嘗試靜音 "阿哲"
    Then "小芳" 看不到靜音按鈕
```

# Rule 7 - 未受影響的現行行為以 Given 或「仍」檢查點帶過 [SHOULD]
- 現行需求中未被本 plan 新增或異動的行為，只以 Given 描述它造成的狀態，或在相關 Journey 中寫成一句含「仍」的檢查點，確認它沒被本次改動破壞。
- 不為現行行為另寫 Journey 或主題重新驗一次；它們已有前一個 plan 的驗收。

## Good Example
- 表情回應的 Journey 以 Given 帶過既有的房內聊天，並以「仍」確認訊息本身沒被改動。

```
    Given "小芳" 與 "阿哲" 在同一房間對局中，"阿哲" 已送出訊息 "加油"
    When "小芳" 對 "加油" 按 "👍"
    Then "阿哲" 看到 "加油" 下方顯示 "👍 1"
    And "加油" 的內容仍為 "加油"
```

## Bad Example
- 為了表情回應，又把房內聊天與發言頻率重寫成兩個主題，與 002 的驗收重複。

```
features/acceptance/
  對訊息按表情回應.feature
  房內即時聊天.feature        （002 已驗收，本次未改）
  訊息內容與發言頻率.feature  （002 已驗收，本次未改）
```

# Rule 8 - 補齊模式不改既有的主題與 Journey 順序 [MUST]
- `features/acceptance/` 已有 feature 檔時就地補齊：沿用既有的檔名、主題順序與每檔 Journey 的順序，新的 Journey 追加在該主題末尾，新主題追加在 demo 順序末尾。
- 修改既有 Journey 時只改需要改的步驟與數字，保留已澄清的標籤；不刪除再重寫整檔，讓 `@ac:<NNN>/<主題>:J-C` 的編號維持穩定。

## Good Example
- 上游修訂後補一條 Journey，追加在第 3 條，既有 J1、J2 與已澄清標籤不動。

```
Feature: 對訊息按表情回應
  Rule: …
    # [CLARIFIED: 同一人能否對同一則訊息按多種表情？→「只能一種，再按其他表情即替換」]
    Example: 小芳對阿哲的訊息按讚後改成愛心          ← J1，未動
    Example: 對局結束後在結果畫面按表情              ← J2，未動
    Example: 對已撤回的訊息按表情被拒                ← J3，本次追加
```

## Bad Example
- 補齊時整檔重寫，新 Journey 插在最前面，原本的 J1、J2 變成 J2、J3，已澄清標籤也被重新寫成待澄清。

```
    # [NEEDS CLARIFICATION: 同一人能否對同一則訊息按多種表情？本範例暫以「只能一種」撰寫]
    Example: 對已撤回的訊息按表情被拒                ← 原本沒有，現在是 J1
    Example: 小芳對阿哲的訊息按讚後改成愛心          ← 原 J1，現在變 J2
```
