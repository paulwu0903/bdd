# Rule 1 - 一個主題是一個大情境，寫成一個 feature 檔 [MUST]
- 主題取自 spec.md 中能獨立 demo 的一個大情境（如「折扣疊加與互斥」「退貨與退款」），一個主題只寫一個 feature 檔，檔名即主題名。
- 一個檔案只講一個大情境，review 時讀完一檔就能判斷這個情境的驗收標準是否正確；不把多個大情境塞進同一檔，也不把同一個大情境拆到多個檔。
- 主題依 FR 中的業務能力與規則群組切分，不依 User Story 的數量切分；不為了湊足主題數而拆開同一個大情境。

## Good Example
- 電商範例整組切成 6 個主題，每檔一個大情境；完整檔案見 `templates/acceptance.example.feature`（折扣疊加與互斥）與 `templates/電商範例/features/` 下其餘 5 檔。

```
features/acceptance/
  折扣疊加與互斥.feature    會員折扣、折扣碼與運費優惠依序疊加，互斥折扣碼被拒絕
  運費分區與免運.feature    運費依收件地區與免運門檻重算，不配送地區不得結帳
  滿額贈品與條件.feature    達門檻附贈品、贈品送完照常成立、退貨後處理贈品
  庫存預留與超賣.feature    搶購時預留不超賣、逾時未付款釋出名額
  訂單成立與付款.feature    待付款、付款成功才成立、失敗重試、逾時取消
  退貨與退款.feature        退貨期限內依折扣比例退款並回補庫存
```

## Bad Example
- 折扣、運費與退貨三個大情境擠在同一檔，review 時得讀完整檔才能判斷任何一個情境；付款又被拆成兩檔，同一個大情境要對照兩份才看得完整。

```
features/acceptance/
  電商結帳.feature          折扣疊加、運費分區、退貨退款全部寫在一起
  信用卡付款.feature
  LINE Pay 付款.feature
```

# Rule 2 - Journey 是 demo 時要走的關鍵主流程加少數變化情境 [MUST]
- 每個 Example 是一條較長的 Journey：從一個確定狀態出發，依序走完 demo 時會操作的多個動作，中途以 Then 檢查結果。
- 一個主題先寫一條關鍵主流程，再挑少數與主流程走向不同的變化情境（失敗、拒絕、逾時、門檻未達）；不為每個資料組合或單一動作各寫一個短 Example。

## Good Example
- 〈訂單成立與付款〉一條主流程走到出貨，再加兩條走向不同的變化情境：失敗後重試成功、失敗後逾時取消。

```
Example: 會員下單後以信用卡付款成功，訂單一路走到出貨
Example: 第一次付款失敗，在保留時間內改用 LINE Pay 付款成功
Example: 付款失敗後超過保留時間，訂單自動取消並釋放庫存
```

## Bad Example
- 每個 Example 只驗一個動作或一種資料，像單元測試切片，PM 無法從中看出 demo 要怎麼走。

```
Example: 送出訂單後狀態為待付款
Example: 信用卡付款成功
Example: LINE Pay 付款成功
Example: 付款成功後狀態為已付款
Example: 出貨後狀態為已出貨
```

# Rule 3 - 每檔 1～3 個 Journey，整組預設 5～8 個 feature [MUST]
- 每個 feature 檔寫 1～3 個 Example；整組 `features/acceptance/` 預設 5～8 個 feature 檔，最多 8 個。
- spec.md 規模小、依業務能力只切得出不到 5 個主題時，照實際主題數寫（不少於 3 個），不拆檔湊數。
- 變化情境多於 3 個時，只留走向最不同、最值得 demo 的幾個；主題多於 8 個時，合併相近的大情境。

## Good Example
- 電商範例 6 檔，每檔 2～3 個 Journey，共 14 個。

```
| 主題           | Journey 數 |
| 折扣疊加與互斥 | 2          |
| 運費分區與免運 | 2          |
| 滿額贈品與條件 | 2          |
| 庫存預留與超賣 | 3          |
| 訂單成立與付款 | 3          |
| 退貨與退款     | 2          |
```

## Bad Example
- 〈退貨與退款〉把每種付款方式與折扣組合都寫成 Journey，一檔 6 個，review 時抓不到重點；另一份小規格只有 3 個業務能力，卻把〈訂單成立與付款〉拆成「信用卡付款」「LINE Pay 付款」湊到 5 檔。

```
Feature: 退貨與退款
  Example: 信用卡訂單部分退貨
  Example: LINE Pay 訂單部分退貨
  Example: 使用折扣碼的訂單部分退貨
  Example: 使用會員折扣的訂單部分退貨
  Example: 整筆退貨
  Example: 超過退貨期限的申請被拒絕
```

# Rule 4 - 前置操作以 Given 帶過，不展開 [MUST]
- 註冊、登入、瀏覽商品、加入購物車等不在本主題驗收範圍內的前置操作，以一句 Given 描述它造成的狀態，不寫成一連串 When。
- When 只寫本主題要驗收的動作。

## Good Example
- 〈訂單成立與付款〉要驗的是下單與付款，購物車內容以 Given 帶過。

```
Given "小芳" 的購物車中有 "無線耳機" 1 件
When "小芳" 送出訂單
Then "小芳" 的訂單狀態為 "待付款"
```

## Bad Example
- 註冊、登入、搜尋與加入購物車都被展開成 When，真正要驗收的下單被埋在後面。

```
When "小芳" 註冊會員
And "小芳" 登入
And "小芳" 搜尋 "無線耳機"
And "小芳" 把 "無線耳機" 加入購物車
And "小芳" 送出訂單
Then "小芳" 的訂單狀態為 "待付款"
```

# Rule 5 - 只有 PM 能在 demo 中觀察到的 NFR 才寫成 Journey 檢查點 [MUST]
- spec.md 的 NFR 與 Success Criteria 中，行為能在 demo 時被 PM 直接看到的（如「1 秒內雙方同時看到結果」「斷線 60 秒內恢復」），寫成相關 Journey 中的 Then 檢查點。
- 需要工具量測的 NFR（效能量測、覆蓋率、無障礙掃描、資料外洩檢查等）留給之後的 /dsl-refine 判定，不寫成 Journey，也不另開主題。

## Good Example
- 「付款成功後 3 秒內會員收到確認通知」是 demo 時看得到的行為，寫進〈訂單成立與付款〉主流程的檢查點；「結帳 API p95 小於 300ms」留給 /dsl-refine 判定。

```
      When "小芳" 以 "信用卡" 付款成功
      Then "小芳" 的訂單狀態為 "已付款"
      And "小芳" 在 3 秒內收到訂單確認通知，金額為 2990
```

## Bad Example
- 把量測型 NFR 寫成 Journey，PM 在 demo 中無從判斷是否通過。

```
    Example: 結帳頁效能與無障礙符合標準
      When 以 1000 位會員同時進行結帳
      Then 結帳的 p95 回應時間小於 300 毫秒
      And 結帳頁通過無障礙掃描
```
