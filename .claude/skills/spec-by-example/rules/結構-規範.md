# Rule 1 - 層級為 Feature（＋業務描述）>（可選的 Background）> Rule > Example [MUST]
- 每個檔案依序為：`Feature: <主題>`、下一行一句業務描述、需要時才有的一個 `Background:`（依 Rule 2）、一到多個 `Rule:`，每個 `Example:` 放在某個 Rule 底下。
- 業務描述用一句話講清楚這個大情境在業務上要達成什麼；不用沒有 Rule 的 `Scenario:`。

## Good Example
- Feature 後接一句業務描述；兩條 Journey 都要用運費規則表，所以抽成 Background 放在 Rule 之前，Example 在 Rule 底下。

```
Feature: 運費分區與免運
  運費依收件地區計算，各地區有自己的免運門檻；不配送的地區必須在結帳時就擋下。

  Background:
    Given 商店的運費規則如下：
      …

  Rule: 運費必須依收件地區與免運門檻即時重算，不配送的地區不得結帳

    Example: 會員湊到本島免運後改寄離島，運費重新計算
      …
```

## Bad Example
- Feature 沒有業務描述，讀者不知道這組驗收要守住什麼；Journey 直接寫成沒有 Rule 的 Scenario。

```
Feature: 運費分區與免運

  Background:
    Given 商店的運費規則如下：
      …

  Scenario: 會員湊到本島免運後改寄離島，運費重新計算
    …
```

# Rule 2 - Background 只抽真正共用的步驟，不硬寫 [MUST]
- 本步的顆粒度是流程：每條 Journey 照流程從頭寫到尾，前提就寫在該 Example 的 Given。Background 不是每個檔案的必備段落。
- 只有兩條以上 Journey 共用、而且帶著測試語意的步驟（例如它們的數字都要依賴的規則表、生效順序、保留時間），才抽成 Background。
- 只有一條 Journey 用到的規則或狀態，留在那條 Journey 的 Given，不搬進 Background；檔案裡沒有共用步驟時，整段不寫 Background。
- 各 Journey 自己的會員與購物車狀態一律寫在該 Example 的 Given。

## Good Example
- 〈折扣疊加與互斥〉兩條 Journey 都要依賴優惠表、生效順序與運費，抽成 Background；只有第一條 Journey 會撞到的互斥規定，留在該 Journey 的 Given。

```
  Background:
    Given 商店提供以下優惠：
      | 優惠名稱            | 類型     | 適用條件                 | 內容             |
      | 白金會員折扣        | 自動折扣 | 白金會員                 | 商品小計 95 折   |
      | 品牌券 SPORT200     | 折扣碼   | 指定品牌 SPORT-X 滿 2000 | 折抵 200         |
      …
    And 商店規定優惠生效順序如下：
      | 順序 | 規則             |
      | 1    | 先計算會員折扣   |
      | 2    | 再套用折扣碼     |
      | 3    | 最後計算運費優惠 |
    And 本島運費為 80 元
```

- 〈滿額贈品與條件〉只有第一條 Journey 要用商品單價推算是否達門檻（第二條直接給已收貨的訂單金額），商品表留在該 Journey 的 Given；兩條都要用的贈品規則才放 Background。

```
  Background:
    Given 商店的滿額贈品規則如下：
      | 贈品     | 門檻（折後商品金額） | 贈品價值 | 可送數量 |
      | 運動水壺 | 2000                 | 300      | 1        |

  Rule: …

    Example: 第一位達門檻的會員拿到最後一個贈品，第二位會員的訂單照常成立
      Given 商店有以下商品：
        | 商品     | 單價 |
        | 越野跑鞋 | 1800 |
        | 壓縮腿套 | 450  |
        | 運動毛巾 | 400  |
      And "小芳" 的購物車中有以下商品：
        …
```

- 主題只有一條 Journey，沒有共用可抽，整個檔案不寫 Background，流程照順序寫完。

```
Feature: 會員等級升級
  會員累積消費達門檻即升級，升級後的下一筆訂單立即適用新等級折扣。

  Rule: 會員必須在達到門檻的那筆訂單付款後立即升級

    Example: 一般會員累積消費跨過門檻後升為白金，下一筆訂單享 95 折
      Given 商店規定累積消費滿 10000 升級為白金會員
      And "小芳" 是一般會員，累積消費 9500
      When "小芳" 以 800 元的訂單付款成功
      Then "小芳" 的會員等級為 "白金會員"
      …
```

## Bad Example
- 只有一條 Journey 卻硬抽 Background，流程被拆成兩段，讀者要上下對照才看得懂這條 Journey 的前提。

```
Feature: 會員等級升級
  會員累積消費達門檻即升級，升級後的下一筆訂單立即適用新等級折扣。

  Background:
    Given 商店規定累積消費滿 10000 升級為白金會員
    And "小芳" 是一般會員，累積消費 9500

  Rule: 會員必須在達到門檻的那筆訂單付款後立即升級

    Example: 一般會員累積消費跨過門檻後升為白金，下一筆訂單享 95 折
      When "小芳" 以 800 元的訂單付款成功
      …
```

- Background 放了只有單一 Journey 用到的會員狀態；兩條 Journey 都要依賴的優惠表與生效順序反而沒抽出來，只能從數字反推。

```
  Background:
    Given "小芳" 是白金會員

  Rule: 可疊加的優惠必須依順序生效，互斥的優惠必須明確拒絕且不影響已套用的優惠

    Example: 白金會員先後套用品牌券與免運券，再嘗試套用互斥的新品券
      Given 會員折扣為 95 折
      …
```

# Rule 3 - Rule 寫一句業務目標，不需原子化 [MUST]
- 一個主題通常一條 Rule，用一句話寫出這個大情境必須達成的業務目標；同一句可以涵蓋主流程與變化情境。
- 不把 Rule 拆到每條只驗一個行為；Rule 底下的 Journey 可以走向不同。

## Good Example
- 一句 Rule 同時涵蓋「依序疊加」與「互斥拒絕」，兩條 Journey 都在它底下。

```
  Rule: 可疊加的優惠必須依順序生效，互斥的優惠必須明確拒絕且不影響已套用的優惠

    Example: 白金會員先後套用品牌券與免運券，再嘗試套用互斥的新品券
    Example: 一般會員未達品牌券門檻，改用新品券後再補上免運券
```

## Bad Example
- 依原子化標準拆成多條 Rule，每條只掛一個短 Example，Journey 被切碎。

```
  Rule: 會員折扣必須先於折扣碼計算
    Example: 白金會員套用品牌券
  Rule: 互斥的折扣碼必須被拒絕
    Example: 已套用 SPORT200 再套用 NEWITEM10
  Rule: 未達門檻的折扣碼必須被拒絕
    Example: 一般會員套用 SPORT200
```

# Rule 4 - Example 標題寫情境描述，不加 US／FR 編號 [MUST]
- Example 標題用一句話描述這條 Journey 的情境與走向，讓 PM 看標題就知道 demo 要演什麼。
- 不加 spec.md 的 User Story、FR 或案例卡編號。

## Good Example
- 標題講出誰、做了什麼、走向如何。

```
    Example: 預留者逾時未付款，名額由先前被拒絕的會員補上
```

## Bad Example
- 標題前綴 US／FR 編號，且只剩規則名稱，看不出情境走向。

```
    Example: US2 FR-007 逾時釋放庫存
```

# Rule 5 - Journey 內以 When／Then 交錯作為檢查點 [MUST]
- 一條 Journey 有多個動作時，每個會改變狀態或數值的動作之後緊接 Then 檢查結果，形成 When → Then → When → Then 的檢查點序列。
- 不把所有 When 寫完才在最後一次 Then，否則中途哪一步算錯無從判斷。
- 例外：只有在連續的 When 合起來是同一個業務事件，或中間狀態無法觀察時，才可以連寫（如「送出訂單」後緊接「付款失敗」）。

## Good Example
- 每次改變購物車或地區後都有一個 Then 檢查摘要表。

```
      When "小芳" 進入結帳流程
      Then 訂單摘要如下：
        …
      When "小芳" 在購物車加入 "運動毛巾" 1 件
      Then 訂單摘要如下：
        …
      When "小芳" 將收件地區改為 "離島"
      Then 訂單摘要如下：
        …
```

## Bad Example
- 三個各自改變數值的動作連續寫完，只驗最後的應付總額，中途的免運是否生效沒有被驗到。

```
      When "小芳" 進入結帳流程
      And "小芳" 在購物車加入 "運動毛巾" 1 件
      And "小芳" 將收件地區改為 "離島"
      Then 應付總額為 1750
```

# Rule 6 - 無法事先確定結果的情境只驗必然成立的結果，後續拆成獨立 Journey [MUST]
- 同時搶購等無法事先知道誰成功的情境，Then 只寫必然成立的結果（如「恰好 2 位」「另 1 位被拒絕」），不指定是哪一位。
- 需要接著驗證的後續流程，另寫一條從確定狀態開始的 Journey，以 Given 直接指定誰處於什麼狀態。

## Good Example
- 第一條只驗人數與可售數量；第二條從「小芳、阿哲待付款」這個確定狀態開始驗逾時釋出。

```
    Example: 三位會員同時搶購兩雙限量鞋，只有兩位成功預留
      …
      Then 恰好 2 位會員的訂單狀態為 "待付款"
      And 另 1 位會員被拒絕，原因為 "庫存不足"
      And "限量聯名鞋" 的可售數量為 0

    Example: 預留者逾時未付款，名額由先前被拒絕的會員補上
      Given 以下會員已送出訂單：
        | 會員 | 訂單狀態 |
        | 小芳 | 待付款   |
        | 阿哲 | 待付款   |
```

## Bad Example
- 同時送出卻指定小芳與阿哲成功，實際執行時結果可能不同；後續流程又接在同一條 Journey 上，前提不成立就整條失敗。

```
      When 以下會員同時送出訂單：
        …
      Then "小芳" 的訂單狀態為 "待付款"
      And "阿哲" 的訂單狀態為 "待付款"
      And "小美" 被拒絕，原因為 "庫存不足"
      When "阿哲" 經過 16 分鐘仍未付款
      …
```

# Rule 7 - 只產 Gherkin，不沿用下游的落地標準 [MUST]
- 本步只產 feature 檔，不產 dsl.md；不分前端與後端，整組只有一份 `features/acceptance/`。
- 不沿用 /gherkin-and-dsl 的五通道 Then 嚴格度、Rule 原子化與前後端分檔；那些標準屬於之後落地到 step definition 的階段。

## Good Example
- 整組只有 feature 檔，全部放在 `features/acceptance/`。

```
specs/<NNN>-<專案名>/features/acceptance/
  折扣疊加與互斥.feature
  運費分區與免運.feature
  …
```

## Bad Example
- 把驗收拆成前端與後端兩份並各附 dsl.md，驗收變成兩組落地規格，PM 無法以單一總驗收 review。

```
specs/<NNN>-<專案名>/features/acceptance/
  frontend/
    dsl.md
    折扣疊加與互斥.feature
  backend/
    dsl.md
    折扣疊加與互斥.feature
```
