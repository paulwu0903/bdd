# Rule 1 - 句子只用業務語言 [MUST]
- 步驟、註解與 Data Table 值都用 PM 讀得懂的業務語意；被拒絕時寫業務原因，不寫錯誤碼。
- 不出現技術詞：API、端點路徑、JSON、token、HTTP、狀態碼、錯誤碼識別字、資料表、request／response 等。

## Good Example
- 套用折扣碼與被拒絕的原因都用業務語言描述。

```
      When "小芳" 套用折扣碼 "NEWITEM10"
      Then 系統拒絕折扣碼 "NEWITEM10"，原因為 "不可與 SPORT200 同時使用"
```

## Bad Example
- 句子寫了端點、狀態碼與錯誤碼，PM 讀不懂。

```
      When "小芳" 呼叫 POST /api/cart/coupons 帶 "NEWITEM10"
      Then 回應狀態碼為 409，錯誤碼為 COUPON_CONFLICT
```

# Rule 2 - 語意完全一致就用同一句型 [MUST]
- 兩句語意完全一致時，整組 feature 檔都寫成同一句型，只換參數值；不另造只差幾個字的近似句型。

## Good Example
- 不同主題的拒絕結果共用「系統拒絕…，原因為…」，訂單狀態共用「…的訂單狀態為…」。

```
Then 系統拒絕退貨，原因為 "已超過收貨後 7 天的退貨期限"
Then 系統拒絕結帳，原因為 "此地區不提供配送"
Then "小芳" 的訂單狀態為 "已付款"
Then "阿哲" 的訂單狀態為 "已取消"
```

## Bad Example
- 同樣是「被拒絕」與「訂單狀態」，在不同檔案換了說法，多出近似句型。

```
Then 系統拒絕退貨，原因為 "已超過收貨後 7 天的退貨期限"
Then "阿哲" 無法結帳，因為 "此地區不提供配送"
Then "小芳" 的訂單狀態為 "已付款"
Then "阿哲" 的訂單變成 "已取消"
```

# Rule 3 - 參數與欄位名稱用繁體中文且與規格用詞一致 [MUST]
- 句中參數所指的概念與 Data Table 欄位名稱用繁體中文，用詞與 spec.md 一致；同一概念在各檔用同一個名稱。

## Good Example
- 購物車表的欄位用規格的「商品」「單價」「數量」，各檔一致。

```
      And "小芳" 的購物車中有以下商品：
        | 商品     | 品牌     | 屬性 | 單價 | 數量 |
        | 越野跑鞋 | SPORT-X  | 常規 | 1800 | 1    |
```

## Bad Example
- 欄位用英文，且同一個「數量」在另一檔寫成「件數」。

```
      And "小芳" 的購物車中有以下商品：
        | sku      | brand    | price | qty |
        | 越野跑鞋 | SPORT-X  | 1800  | 1   |
      And "阿哲" 的購物車中有以下商品：
        | 商品     | 件數 |
        | 越野跑鞋 | 1    |
```

# Rule 4 - 字串參數加雙引號、參與運算的數值不加，Data Table 不加引號 [MUST]
- 數量、金額、秒數、分鐘數、次數等會拿來運算或比較大小的數值，直接寫整數，不加引號。
- 由數字組成但只用來識別的值（商品編號、訂單編號、折扣碼、房間代碼、謎底、猜測等）屬於字串，必須加雙引號；有前導零（如 "0421"）或全形數字（如 "０４２１"）的值一律視為字串。
- 其他字串參數（會員、商品、狀態、原因）也寫在雙引號內；Data Table 儲存格一律不加引號，也不用「」。

## Good Example
- 會員、商品、狀態與數字組成的商品編號加雙引號，件數與金額不加；表格值不加引號。

```
      Given "小芳" 的購物車中有 "無線耳機" 1 件
      And "小芳" 的購物車中有商品編號 "004215" 的 "瑜珈墊" 2 件
      Then "小芳" 的訂單狀態為 "待付款"
      And 應付總額仍為 2840
        | 商品     | 單價 |
        | 瑜珈墊   | 1200 |
```

## Bad Example
- 件數加了引號、商品改用「」；商品編號沒加引號，前導零會被當成數字 4215；表格值多了引號。

```
      Given "小芳" 的購物車中有 「無線耳機」 "1" 件
      And "小芳" 的購物車中有商品編號 004215 的 "瑜珈墊" 2 件
        | 商品     | 單價 |
        | "瑜珈墊" | 1200 |
```

# Rule 5 - 同類多列或參數超過 3 個時用 Data Table [SHOULD]
- 同一句型以不同值連續出現多列，或一句的參數超過 3 個時，改寫成 Data Table。
- 依序發生、各自獨立的動作（連續的 When）維持句子，不塞成表。

## Good Example
- 三件商品各有品牌、屬性、單價與數量，寫成一張表。

```
      And "小芳" 的購物車中有以下商品：
        | 商品     | 品牌     | 屬性 | 單價 | 數量 |
        | 越野跑鞋 | SPORT-X  | 常規 | 1800 | 1    |
        | 壓縮腿套 | SPORT-X  | 常規 | 450  | 1    |
        | 新款風衣 | CITY-LAB | 新品 | 950  | 1    |
```

## Bad Example
- 同一句型連寫三次，每句又有四個參數，讀者很難對齊比較。

```
      And "小芳" 的購物車中有 "SPORT-X" 品牌的 "常規" 商品 "越野跑鞋" 單價 1800 共 1 件
      And "小芳" 的購物車中有 "SPORT-X" 品牌的 "常規" 商品 "壓縮腿套" 單價 450 共 1 件
      And "小芳" 的購物車中有 "CITY-LAB" 品牌的 "新品" 商品 "新款風衣" 單價 950 共 1 件
```

# Rule 6 - 影響閱讀的預設值以 `# 名稱=值` 註明 [SHOULD]
- Background 與 Given 都沒寫、但會影響讀者理解數字的預設值，在該步驟正上方寫 `# 名稱=值`，名稱與值用業務用語。
- 同一 Example 只註第一次出現處；Background 或 Given 已寫明的值不再註。

## Good Example
- Journey 沒寫收件地區，但運費 80 取決於它，在第一個出現運費的檢查點上方註明。

```
      When "小芳" 進入結帳流程
      # 收件地區=本島
      Then 系統自動套用 "白金會員折扣"
```

## Bad Example
- 名稱用技術值；保留時間已寫在 Background，又重複註一次。

```
      # SHIPPING_REGION=TW_MAIN
      Then 系統自動套用 "白金會員折扣"
      # 待付款訂單保留時間=15 分鐘
      When 經過 16 分鐘
```

# Rule 7 - Then 的每個數字都能由 Background（有的話）與 Given 推算 [MUST]
- Then 中出現的每個狀態或數值（金額、數量、時間等），讀者只看 Background（有的話）與該 Journey 的 Given、When 就能算出來。
- 算不出來時，把缺的規則或狀態補進該 Journey 的 Given；多條 Journey 都缺同一條規則時才補進 Background（依 結構-規範 Rule 2）；規則本身有疑問時加澄清標籤，不憑空寫數字。

## Good Example
- 每個數字都能由 Background 的優惠表、生效順序與運費算出。

```
# 商品小計 1800 + 450 + 950 = 3200
# 會員折扣 3200 × 5% = 160（白金會員 95 折，先計算會員折扣）
# 運費 80（本島運費為 80 元）
# 應付總額 3200 − 160 + 80 = 3120
      Then 訂單摘要如下：
        | 項目     | 金額 |
        | 商品小計 | 3200 |
        | 會員折扣 | 160  |
        | 折扣碼   | 0    |
        | 運費     | 80   |
        | 應付總額 | 3120 |
```

## Bad Example
- Background 只寫了退貨期限，沒寫退款依折扣比例分攤，讀者算不出分攤折扣 40 與退款 360 從何而來。

```
  Background:
    Given 商店規定收貨後 7 天內可申請退貨

      …
      Then "小芳" 看到退款明細如下：
        | 項目     | 金額 |
        | 商品原價 | 400  |
        | 分攤折扣 | 40   |
        | 退款金額 | 360  |
```

# Rule 8 - 被拒絕後寫明哪些沒有改變 [MUST]
- 每個「系統拒絕…」之後，緊接至少一句 Then／And 寫明被拒絕的動作原本會改變、而實際沒有改變的狀態或數值（以「仍為」「仍有」表達）。

## Good Example
- 退貨被拒絕後，寫明訂單狀態與可售數量都沒變。

```
      Then 系統拒絕退貨，原因為 "已超過收貨後 7 天的退貨期限"
      And "阿哲" 的訂單狀態仍為 "已收貨"
      And "越野跑鞋" 的可售數量仍為 5
```

## Bad Example
- 只寫被拒絕，讀者無法確認訂單與庫存是否被誤改。

```
      Then 系統拒絕退貨，原因為 "已超過收貨後 7 天的退貨期限"
```

# Rule 9 - 有變化的檢查點列完整摘要表，未變化時只寫關鍵值 [SHOULD]
- 動作造成狀態或數值變化時，該檢查點列出完整的摘要表（如電商的訂單摘要每一列），讓讀者看出哪一項變了。
- 只需確認沒有變化時（如被拒絕後），寫關鍵值即可，不重列整張表。

## Good Example
- 套用免運券後列完整訂單摘要；被拒絕後只確認應付總額不變。

```
      When "小芳" 套用折扣碼 "SHIPFREE"
      Then 訂單摘要如下：
        | 項目     | 金額 |
        | 商品小計 | 3200 |
        | 會員折扣 | 160  |
        | 折扣碼   | 200  |
        | 運費     | 0    |
        | 應付總額 | 2840 |
      When "小芳" 套用折扣碼 "NEWITEM10"
      Then 系統拒絕折扣碼 "NEWITEM10"，原因為 "不可與 SPORT200 同時使用"
      And 應付總額仍為 2840
```

## Bad Example
- 套用免運券後只寫應付總額，看不出是運費歸零還是折扣碼變動造成的變化。

```
      When "小芳" 套用折扣碼 "SHIPFREE"
      Then 應付總額為 2840
```

# Rule 10 - 人名沿用規格中的名字，規格沒有時用中文 [SHOULD]
- spec.md 已為使用者或角色取了名字時，Journey 直接沿用那些名字，不另取新名。
- spec.md 沒有命名時，會員與角色用中文人名（如小芳、阿哲、小美）；整組沿用同一批名字。

## Good Example
- spec.md 沒有為會員命名，Journey 用中文人名。

```
      Given "小芳" 是白金會員
      And "阿哲" 是一般會員
```

## Bad Example
- 用英文代號或編號當會員名，PM 讀起來像測試資料而非業務情境；或 spec.md 已寫了「小芳」，Journey 卻另取「王小姐」。

```
      Given "user_01" 是白金會員
      And "Bob" 是一般會員
```
