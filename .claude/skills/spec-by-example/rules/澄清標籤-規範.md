# Rule 1 - spec 沒寫清楚之處必加標籤，整組最多 10 個 [MUST]
- 對 spec.md 沒寫清楚、寫法或數字會因答案而不同的地方，必須加上澄清標籤；整組 `features/acceptance/` 合計 0～10 個。
- 計數包含待澄清標籤與澄清後改寫成的已澄清標籤（依 Rule 6），所以澄清前後的總數不變。
- 沒有下限：spec.md 已經 /clarify-over-specs 釐清、Journey 的每個數字都能在 spec.md 找到依據時，可以一個都不加，不為湊數編出疑問；多於 10 個時只留最會改變 Journey 寫法或數字的幾個。

## Good Example
- 電商範例 6 檔共 8 個標籤，分散在各主題。

```
| 主題           | 標籤數 |
| 折扣疊加與互斥 | 2      |
| 運費分區與免運 | 1      |
| 滿額贈品與條件 | 1      |
| 庫存預留與超賣 | 1      |
| 訂單成立與付款 | 2      |
| 退貨與退款     | 1      |
| 合計           | 8      |
```

## Bad Example
- 整組沒有任何標籤，但 spec.md 並未寫明免運門檻的計算基準與互斥處理方式，Journey 的數字被默默假設成某個答案；另一份 spec 每個數字都有依據，卻為了湊數加上「表情是否要有動畫」這類 spec 早已拍板的疑問。

```
| 主題           | 標籤數 |
| 折扣疊加與互斥 | 0      |
| 運費分區與免運 | 0      |
| …              | 0      |
| 合計           | 0      |
```

# Rule 2 - 標籤格式寫明問題與暫定答案 [MUST]
- 格式固定為 `# [NEEDS CLARIFICATION: <問題>？暫以「<暫定答案>」撰寫]`（可寫成「本範例暫以」）。
- 暫定答案就是目前 feature 檔實際採用的寫法，讀者看標籤就知道下方的數字是依哪個假設算的。

## Good Example
- 問題後接暫定答案，下方 Background 的數字依「原價」計算。

```
    # [NEEDS CLARIFICATION: 品牌券「SPORT-X 滿 2000」的門檻，是以折扣前的原價計算，還是扣掉會員折扣後的金額計算？本範例暫以「原價」撰寫]
```

## Bad Example
- 只有問題沒有暫定答案，讀者不知道下方的數字是依哪個假設算的。

```
    # [NEEDS CLARIFICATION: 品牌券門檻是以原價還是折後金額計算？]
```

# Rule 3 - 一個標籤只問一個決策，並盡量列出選項 [SHOULD]
- 一個標籤只問一個需要使用者拍板的決策；問句中盡量列出可選的答案，讓使用者能直接挑。

## Good Example
- 只問互斥時的處理方式，並列出兩個選項。

```
      # [NEEDS CLARIFICATION: 互斥時是一律拒絕後者，還是讓會員選擇改用較划算的那張（自動替換 SPORT200）？本範例暫以「一律拒絕後套用的折扣碼」撰寫]
```

## Bad Example
- 問句籠統、沒有選項，使用者無從選起。

```
      # [NEEDS CLARIFICATION: 折扣碼的規則對嗎？本範例暫以「目前寫法」撰寫]
```

# Rule 4 - 標籤緊貼在答案會改變的那一行正上方 [MUST]
- 依答案影響的範圍決定位置，標籤與目標行之間不留空行：
  - 影響規則前提 → 放在寫出該規則的步驟正上方：規則抽在 Background 就放在該 Background 步驟上方，沒有 Background 而寫在 Example 的 Given 就放在該 Given 上方。
  - 只影響單一 Journey 的前提狀態 → 放在該 Example 內的 Given 步驟正上方（接續 Given 的 And 也可以）。
  - 影響整條 Journey 的走向 → 放在該 Example 正上方。
  - 只影響單一檢查點的預期值 → 放在預期值會因答案改變的那個 Then 或 And 步驟正上方（接續 Then 的 And 也可以）。
  - 答案會改變動作本身（動作能不能做、怎麼做） → 放在該 When 步驟正上方（接續 When 的 And 也可以）。

## Good Example
- 五種位置各一例：免運門檻基準在 Background 步驟上方、退貨期限起算點只改變這條 Journey 的前提而放在 Example 內的 Given（And）步驟上方、候補機制在 Example 上方、重試次數會改變「能否再付款」這個動作而放在該 When（And）步驟上方、互斥處理方式只改變拒絕結果而放在該 Then 步驟上方。

```
  Background:
    # [NEEDS CLARIFICATION: 免運門檻是以商品原價計算，還是以扣除折扣後的商品金額計算？本範例暫以「商品原價小計」撰寫]
    Given 商店的運費規則如下：
…
      Given "阿哲" 有一筆已收貨的訂單：
        …
      # [NEEDS CLARIFICATION: 退貨期限的 7 天是從物流顯示送達起算，還是從會員按下「確認收貨」起算？本範例暫以「物流顯示送達」撰寫]
      And "阿哲" 的訂單在 8 天前收貨
…
    # [NEEDS CLARIFICATION: 被拒絕的會員要自己再次送出訂單，還是系統應提供候補並在名額釋出時自動通知或自動預留？本範例暫以「會員自行再次送出訂單」撰寫]
    Example: 預留者逾時未付款，名額由先前被拒絕的會員補上
…
      When 經過 10 分鐘
      # [NEEDS CLARIFICATION: 保留時間內重試付款是否有次數上限？達上限後訂單如何處理？本範例暫以「不限次數」撰寫]
      And "阿哲" 以 "LINE Pay" 付款成功
…
      When "小芳" 套用折扣碼 "NEWITEM10"
      # [NEEDS CLARIFICATION: 互斥時是一律拒絕後者，還是讓會員選擇改用較划算的那張（自動替換 SPORT200）？本範例暫以「一律拒絕後套用的折扣碼」撰寫]
      Then 系統拒絕折扣碼 "NEWITEM10"，原因為 "不可與 SPORT200 同時使用"
```

## Bad Example
- 標籤全部集中在 Feature 描述下方，讀者看不出每個疑問會改變哪一行。

```
Feature: 訂單成立與付款
  會員下單後訂單先保留待付款，付款成功才算成立；付款失敗可在保留時間內重試，逾時即取消並釋放庫存。
  # [NEEDS CLARIFICATION: 15 分鐘保留時間是從送出訂單起算，還是每次付款失敗後重新起算？本範例暫以「從送出訂單起算」撰寫]
  # [NEEDS CLARIFICATION: 保留時間內重試付款是否有次數上限？達上限後訂單如何處理？本範例暫以「不限次數」撰寫]

  Background:
```

# Rule 5 - 已寫明且可驗算的數字不標 [SHOULD]
- Background 與 Given 已寫明規則、讀者能自行算出的數字，不再加澄清標籤；標籤只留給 spec.md 真的沒寫清楚的決策。

## Good Example
- 會員折扣 160 可由 Background 的「商品小計 95 折」算出，不標；門檻計算基準 spec.md 沒寫，才標在 Background。

```
    # [NEEDS CLARIFICATION: 品牌券「SPORT-X 滿 2000」的門檻，是以折扣前的原價計算，還是扣掉會員折扣後的金額計算？本範例暫以「原價」撰寫]
    Given 商店提供以下優惠：
      …
      Then 訂單摘要如下：
        | 項目     | 金額 |
        | 會員折扣 | 160  |
```

## Bad Example
- 會員折扣 160 已能由 95 折算出，仍加標籤，佔掉名額又讓使用者確認不需確認的事。

```
      # [NEEDS CLARIFICATION: 會員折扣是否為 160？本範例暫以「160」撰寫]
      Then 訂單摘要如下：
        | 項目     | 金額 |
        | 會員折扣 | 160  |
```

# Rule 6 - 澄清後不刪標籤，改寫成已澄清標籤並留在原位 [MUST]
- 使用者回答後，依答案修改下方的步驟與數字，再把該標籤改寫成 `# [CLARIFIED: <問題>？→「<定案答案>」]`，留在原本的位置當作決策紀錄。
- 定案答案寫使用者實際選的答案；與暫定答案不同時，下方的步驟與數字必須先改成依定案答案計算。
- 不刪除已澄清標籤，也不另外搬到檔首或其他文件。

## Good Example
- 使用者選了與暫定不同的「100 字」，步驟數字先改成 101 字被拒絕，標籤改寫後留在原位。

```
      # [CLARIFIED: 單則訊息上限要訂多少字（100、200 或 500 字）？→「100 字」]
      Given 每則訊息最多 100 字
      …
      When "阿明" 送出一則 101 字的訊息
      Then 系統拒絕送出訊息，原因為 "訊息最多 100 字"
```

## Bad Example
- 澄清後直接刪掉標籤，之後讀者分不出「100 字」是使用者拍板的，還是撰寫時隨手寫的；或只改了標籤，下方數字仍依暫定的 200 字。

```
      Given 每則訊息最多 100 字
      …
      # [CLARIFIED: 單則訊息上限要訂多少字（100、200 或 500 字）？→「100 字」]
      When "阿明" 送出一則 201 字的訊息
```
