# Rule 1 - 對齊的依據是最新 truth 與改前改後的差異 [MUST]
- 改寫測試碼時，依據只有三樣：最新的 feature 與 dsl.md、`git diff <Base>` 中被修改的句型與 Example 的改前改後內容，以及 truth-delta 對應列的摘要。
- 目前產品的行為不是依據；不得為了讓 slice 維持綠燈而照產品現況改寫預期。

## Good Example
- 句型的種子則數由 dsl.md 改前的 5 則改為改後的 8 則，step 依改後的值改寫。

```
git diff：dsl.md「…送出的 {則數} 則訊息」實作語意「頻率上限 5 則」→「頻率上限 8 則」
改寫：driver.seedMessages(limit) 的上限由 5 改為取自 dsl.md 的 8
```

## Bad Example
- 產品仍回 5 則就拒絕，於是把 step 的預期改成 5 則，讓 slice 保持綠燈。

```
產品目前第 6 則就回 CHAT_RATE_LIMITED → 把 Then 的預期改回「第 6 則被拒絕」
```

# Rule 2 - 受影響範圍包含隱含舊值的支援程式 [MUST]
- 除了 step definition，還要逐項核對 driver、helper、fixture、種子資料、常數與 parameter type 中隱含的舊 truth 值（數字、文案、錯誤碼、欄位名、預設參數）。
- 每一項都要在回報中列出「已改寫」或「已核對、不需改寫」與理由。

## Good Example
- 逐項列出核對結果，連沒改的也寫明理由。

```
modules/聊天訊息/前置.ts      已改寫：種子則數改由參數決定
shared/fixtures/chat.ts       已改寫：RATE_LIMIT 常數 5 → 8
shared/asserts.ts             已核對、不需改寫：只比對錯誤碼，不含門檻值
```

## Bad Example
- 只改了 step，fixture 裡寫死的 5 沒有人檢查，測試仍用舊門檻佈置資料。

```
modules/聊天訊息/前置.ts      已改寫
（shared/fixtures/chat.ts 未核對，RATE_LIMIT = 5 留著）
```

# Rule 3 - 證明 Then 檢查的是新值 [MUST]
- 每個 slice 改寫完成後，把被修改的預期值暫時改回改前的值重跑，必須變紅；確認後還原，並在回報中附上這次重跑的失敗訊息。
- 沒有被修改預期值的 slice（只因句型語意改變而受影響），改為把 step 或支援程式中改寫的值暫時改回舊值，重跑必須變紅。

## Good Example
- 暫時改回舊值會變紅，證明 Then 真的在檢查新的 8 則。

```
暫改：Then 預期「第 9 則被拒絕」→「第 6 則被拒絕」
結果：AssertionError: 第 6 則 expected CHAT_RATE_LIMITED, got 201 → 還原
```

## Bad Example
- 改寫後 slice 是綠的就記為完成，沒有證明測試能分辨新舊值。

```
發言頻率.feature:13 綠燈 → 完成
```

# Rule 4 - 對齊不寫產品碼 [MUST]
- realign 只修改 step definition、driver、helper、fixture、種子資料與 parameter type；產品碼的改動留給同範疇的 `/bdd green`。
- 改寫後的紅燈屬於「產品未實作」或「產品錯」時，即為合格紅燈。

## Good Example
- 測試端對齊後，產品仍是 5 則上限，slice 變紅並交給 green。

```
發言頻率.feature:13 紅燈（產品錯：第 6 則被拒絕，truth 要求第 9 則才拒絕）→ 交給 /bdd green
```

## Bad Example
- 為了讓 realign 結束時是綠的，順手把產品的上限改成 8。

```
修改 backend/src/config.ts CHAT_RATE_LIMIT = 8
```

# Rule 5 - 每一項改寫都指回 truth-delta 的列 [MUST]
- 回報中每一項改寫都寫明它對應的 truth-delta 列（部位）。
- 指不回任何一列的改寫不做；若發現 truth 有改變卻沒有被記錄，依上游缺口判準停止並交還。

## Good Example
- 每項改寫都有對應的列。

```
shared/fixtures/chat.ts RATE_LIMIT 5 → 8   ← backend/聊天訊息/dsl.md › Given › 房間 {房間代碼} 的聊天區只有 … 則訊息
```

## Bad Example
- 順手改了與本次異動無關的斷言寫法，回報中找不到對應的列。

```
shared/asserts.ts 改用 deepStrictEqual   ← （無）
```
