# Rule 1 - 以下情況屬於上游缺口 [MUST]
- feature 與 dsl.md 是 /dsl-refine 的產出，也是 bdd 的必要輸入；出現下表任一情況時，就算是上游缺口，不是 bdd 能自行補上的問題。

| 缺口類型 | 判準 |
|---|---|
| 句型缺漏 | 步驟對不到 dsl.md 任何句型，或 dsl.md 缺檔、缺段 |
| 語意無法落地 | dsl.md 的實作語意點名的操作、端點、資料表或欄位，在 openapi.yaml、schema.dbml 或既有程式中不存在，或彼此矛盾 |
| 隱含值缺漏 | 實作 step 需要的值在句子、Gherkin 參數與預設參數中都找不到 |
| 預期衝突 | Then 的預期與 acceptance 或 spec.md 的需求互相矛盾 |
| 句型撞名 | 同一句話在不同 dsl.md 的語意不同，dry-run 出現 ambiguous |
| 既有功能衝突 | 範疇外既有功能的 Example，因本範疇規格刻意改變行為而失敗 |

## Good Example
- dsl.md 寫了單次送出上限，卻沒寫錯誤碼對照；Then 需要比對錯誤碼才能實作，判定為隱含值缺漏。

```
句型：{玩家暱稱} 的訊息因 {拒絕原因} 被拒絕
缺什麼：預設參數沒有「拒絕原因對照」，無法得知「超過長度」對應哪個錯誤碼
判定：上游缺口（隱含值缺漏）→ 停止並交還 /dsl-refine
```

## Bad Example
- 同樣缺錯誤碼對照，卻當成測試端問題，自己從產品碼裡找一個錯誤碼填進 step。

```
句型：{玩家暱稱} 的訊息因 {拒絕原因} 被拒絕
處理：看 backend/src/routes/chat.ts 回的是 MESSAGE_TOO_LONG，就把它寫死在 step 裡
```

# Rule 2 - 交還時列出位置、類型與證據 [MUST]
- 發現缺口就停止當前階段，在對話中逐項列出：檔案與行號（或 dsl.md 句型）、Rule 1 的缺口類型、證據（錯誤訊息、互相矛盾的兩處原文）、建議的上游處理方式。
- 衝突類缺口（預期衝突、句型撞名、既有功能衝突）要列出衝突雙方的檔案、行號與 trace tag。
- 交還前已完成的 step、driver 與產品碼保留，並在回報中列出，讓上游修正後可以接續。

## Good Example
- 既有功能衝突列出雙方位置與 trace tag，讓上游能決定退役或更新舊 feature。

```
缺口類型：既有功能衝突
舊：specs/truth/features/backend/配對與房間/房間.feature:42 @ac:001/配對與房間:2-1「房間最多 2 人」
新：specs/truth/features/backend/觀戰/觀戰.feature:15 @ac:003/觀戰:1-2「房間可有 2 名玩家與 4 名觀戰者」
證據：全套執行時舊 Example 失敗，expected 加入被拒絕，actual 加入成功
建議：由 /specify 或 /dsl-refine 決定退役或更新 001 的這個 Example
```

## Bad Example
- 只說「feature 有問題」，沒有位置、類型與證據，上游無從修起。

```
dsl.md 好像有些問題，請檢查一下再執行。
```

# Rule 3 - 不改 feature 與 dsl.md，也不在測試端繞過 [MUST]
- 遇到缺口時，不修改 feature 檔與 dsl.md，不刪除或停用舊 feature，也不從框架設定移除既有的 feature 路徑。
- 不在 step、driver 或 fixture 裡自行補上 dsl.md 沒寫的值、放寬斷言，或跳過步驟，讓 slice 繞過缺口跑下去。

## Good Example
- Then 預期與 spec 衝突時保留原樣並交還。

```
Then "阿明" 的聊天紀錄共 0 則   ← spec FR-012 要求靜音者仍看得到系統訊息，應為 1 則
處理：feature 與 step 不動，停止並以「預期衝突」交還 /dsl-refine
```

## Bad Example
- 為了讓舊功能的 Example 不再失敗，直接加 tag 把它排除，舊行為的回歸保護就此消失。

```
在 001 的 房間.feature:42 加上 @skip，並在 cucumber.mjs 的 tags 加 not @skip
```
