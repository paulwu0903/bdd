# Rule 1 - 合格紅燈的失敗原因落在產品端 [MUST]
- 合格紅燈只有三種：產品未實作、斷言顯示產品行為不符（產品錯），或他端未實作。
- 比對、資料、定位、狀態清理這四類是測試端問題，修正之前都不算紅燈完成。

## Good Example
- step 都已定義、driver 呼叫的端點存在，失敗在斷言上，而且原因是產品還沒有這個行為。

```
slice：第 2 輪阿明靜音小華（靜音.feature:9）
結果：AssertionError: expected muted=true, got false
類別：斷言／產品錯 → 合格紅燈
```

## Bad Example
- 失敗原因是 driver 的 payload 欄位名寫錯，卻被當成合格紅燈交給 green。

```
slice：第 2 輪阿明靜音小華（靜音.feature:9）
結果：400 Bad Request: unknown field "mute"（openapi 的欄位是 "muted"）
判定：合格紅燈，交給 green 處理
```

# Rule 2 - red 不寫產品碼 [MUST]
- red 只新增或修改 step definition、driver、fixture 與 parameter type。
- 為了讓測試端能編譯或啟動而需要的產品碼（新模組、新端點、新畫面），一律留給 green；這時的紅燈歸為產品未實作。

## Good Example
- 後端還沒有靜音端點，red 讓 driver 照 dsl.md 呼叫它，接受 404 的紅燈。

```
driver：muteOpponent() 呼叫 POST /api/rooms/{code}/mute
紅燈：404 Not Found → 產品未實作，留給 green
```

## Bad Example
- 為了讓紅燈看起來「比較接近」，先在產品碼加一個空的路由回 200。

```
backend/src/routes/chat.ts 新增 app.post('/api/rooms/:code/mute', c => c.json({}))
```

# Rule 3 - red 時就已經綠的 slice 要確認 Then 有真的在查 [MUST]
- red 階段就綠燈，只有兩種合理原因：產品已經具備這個行為，或 step 沒有落實 dsl.md 的必查。
- 逐項對照該句型 `必查` 的每個 bullet（呈現結果、權威狀態、再讀確認、不該發生），確認 step 都有對應的 assertion，並以「暫時把預期值改錯會變紅」驗證過；確認後才能記為已綠，並在回報中說明依據。

## Good Example
- 已綠的 slice 逐項對照必查，並以改錯預期驗證會失敗，才記為已綠。

```
slice：開局前阿明靜音後小華送出訊息（已綠）
必查對照：呈現結果 ✓ 權威狀態 ✓ 再讀確認 ✓ 不該發生 ✓
驗證：預期改成 1 則時變紅 → 確認產品已具備此行為
```

## Bad Example
- Then 只查了回應狀態碼，沒查 dsl.md 要求的資料列與再讀確認，就直接記為已綠。

```
Then("{玩家暱稱} 的聊天紀錄共 {數量} 則", async function () {
  assert.equal(this.lastResponse.status, 200)
})
```
