# Rule 1 - 產品缺口只能用產品碼補 [MUST]
- 判定為產品未實作或產品錯時，在本端的產品碼補上行為，讓 slice 經由真正的產品路徑變綠。
- 不在 step、driver、fixture 或 stub 裡寫假邏輯讓 slice 變綠；端點 Example 就是唯一的測試網，不另寫 function 層級的單元測試。

## Good Example
- 在後端的聊天服務實作靜音過濾，step 與 driver 不動。

```ts
// backend/src/services/chat.ts
export function visibleMessages(room: Room, viewer: PlayerId): ChatMessage[] {
  return room.messages.filter(m => !room.isMutedBy(viewer, m.senderId, m.sentAt))
}
```

## Bad Example
- 在 driver 裡自己過濾掉被靜音者的訊息，slice 變綠了，產品根本沒有靜音。

```ts
async chatHistoryOf(player: string) {
  const all = await this.api.getChat(player)
  return all.filter(m => !this.mutedSenders.has(m.sender))
}
```

# Rule 2 - 只寫剛好讓當前 slice 通過的產品碼 [MUST]
- 只補當前 slice 需要的行為，不預先寫範疇內後續 slice 的行為，也不加推測性功能或設定。
- 後續 slice 會逼出的行為，留到輪到它時再寫。

## Good Example
- 當前 slice 只要求「靜音後看不到對手訊息」，只實作這個過濾。

```
當前 slice：對局中阿明靜音後小華送出訊息
實作：visibleMessages 依靜音紀錄過濾
未實作：換對手後不再套用靜音（屬於後面的 slice）
```

## Bad Example
- 當前 slice 只要求過濾，卻順手做了靜音期限、靜音名單上限與取消靜音。

```
當前 slice：對局中阿明靜音後小華送出訊息
實作：visibleMessages 過濾 + muteExpiresAt + MAX_MUTED=5 + unmute 端點
```

# Rule 3 - 不越界寫其他端點的產品碼 [MUST]
- green 只修改範疇所屬端點的產品碼。
- slice 的紅燈原因落在其他端點時，停止並回報缺少的端點與操作；不在本端改寫他端程式，也不在本端的 fixture 裡模擬他端行為。

## Good Example
- 前端範疇遇到後端操作不存在，停止並回報。

```
範疇：specs/truth/features/frontend/聊天訊息/訊息收發.feature
紅燈：POST /api/rooms/4821/chat-messages → 404
回報：缺 backend 的「送出訊息」操作，建議先執行 /bdd red 與 /bdd green（specs/truth/features/backend/聊天訊息/送出訊息與對局.feature）
```

## Bad Example
- 前端範疇的 green 直接去後端新增路由。

```
範疇：specs/truth/features/frontend/聊天訊息/訊息收發.feature
修改：backend/src/routes/chat.ts 新增 POST /api/rooms/:code/chat-messages
```
